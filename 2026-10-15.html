2026 年维护者峰会

作者：Jonathan Corbet 2026年10月12日 英文原文

2026 年维护者峰会

Maintainers Summit（维护者峰会）是一场为期一天、仅限邀请参加的聚会，约有 30 名内核开发者出席；每年举办一次，用于讨论那些往往难以通过电子邮件解决的政策性问题。2026 年的峰会定于 10 月 8 日在捷克布拉格举行。不出所料，讨论的焦点集中在大型语言模型（LLM）及其对开发社区的影响上，不过也抽出了一些时间谈论安全缺陷和长期的接班规划。

与往年不同，2026 年峰会没有一份明确议程来指定由哪位开发者牵头各个话题的讨论。对话相当自由发散，本文的写法也将与这种结构（或者说缺乏结构）相匹配。为了给出更连贯的综述，做了一些最小限度的顺序调整。

TL;DR

对于不想通读下文的读者，这里是最重要结论的摘要。请注意，这完全是我个人的解读，并非峰会给出的任何官方传达。

  • Sashiko 不再报告在审查补丁时发现的既有缺陷；对这一改变的反应不一。人们欣赏 Sashiko，但一些维护者担心它会助长新提交者容易陷入的“快速修改再重发”循环。
  • Linus Torvalds 认为，把内核社区的问题归咎于 LLM 是错误的，真正的问题在于那些既不了解如何使用 LLM、也不了解内核如何运作的 LLM 用户。经过妥善训练的 LLM 是有用的工具，但达到那一步需要投入大量时间。
  • Torvalds 等人反复表示，来自新开发者的低质量贡献应当被降低优先级，社区应该停止刻意让贡献变得“容易”。许多开发者一再强调，试图指导这些开发者几乎总是浪费时间——他们根本听不进去。
  • 对于公司借助 LLM 维护私有内核存在一些担忧，但似乎也没有太多可做的。
  • 不应要求内核开发者必须使用 LLM 才能在社区中工作，但那些确实使用的人需要拥有足够的资源来产出可接受的结果。
  • 为借助 LLM 创建的补丁添加 Assisted-by 标签的要求将被取消，但维护者仍然希望了解补丁是如何产生的。
  • 开发社区正在勉力应对安全补丁的洪流，而且这种状况还会持续一段时间。一些最紧急的修复可能会绕过维护者、直接送到 Torvalds 手中。维护者被提醒，不要在公开披露之前把漏洞信息告诉自己的雇主。
  • 每位维护者简要陈述了开发流程中令他们痛苦的一个方面；许多人谈到审查流程、应付工作负担，以及对学习不感兴趣的提交者。
  • Torvalds 表示，社区应当开始更多思考领导层接班应该如何运作，以便若干年后他决定退休时已有预案可用。

Sashiko 与补丁审查

最初的话题是自动化补丁审查，尤其是 Sashiko 审查系统。当 Sashiko 审查某个具体补丁时，它往往会识别（并报告）该补丁所修改的代码中早已存在的问题。开发者对由此产生的报告又爱又恨：了解这些缺陷固然是好事，但没有人会乐于收到一张待修复问题的长长的清单，尤其当它被视为一道必须跨越的障碍、否则就无法合入自己真正想实现的改动时。

最近，Sashiko 的开发者 Roman Gushchin 宣布，补丁审查将不再包含既有缺陷；这些缺陷将被存入一个单独的数据库，供维护者查阅。Ted Ts'o 以这一变化开启了峰会上的讨论，指出 Sashiko 审查中不再出现的问题已积压了大量存量。Peter Zijlstra 询问为什么要做出这个改变，因为了解这些缺陷仍然很重要；Gushchin 回答说，缺陷仍然在被检测，只是被从报告中隐藏起来，搁置一旁等待有人去处理。

Christoph Hellwig 说，把既有问题保留在补丁审查中会更好，但也许可以用不同的方式加以标注，让提交者知道他们并不被要求处理它们。他说，不应把老问题强加给新的提交者。Mark Brown 表示赞同，说提交者不应为了合入一个拼写修复而被要求先修复结构性问题。Hellwig 补充说，直接移除既有条目反而更糟，因为那些问题终究需要修复。Gushchin 重申，这些问题已被收集起来，供有兴趣修复它们的人使用。

Zijlstra 抱怨说，某些维护者在 Sashiko 报告未发现任何问题之前拒绝考虑补丁。不过 Hellwig 认为，Sashiko 审查对提交者来说是一个很好的测试；如果他们清楚自己在做什么，就应该能够解释为什么某条警告是错误的。Thomas Gleixner 回应说，最差的提交者只会把审查结果喂给他们的 LLM，然后把生成的回复发出来。

Ts'o 建议，最佳实践会因子系统而异。在较大的子系统中，子维护者可能不具备判断某个缺陷报告是否有效的能力；他们应对误报更加吃力。由专家维护者掌管的小子系统则能更好地处理这些报告。他说，解决方案有一部分在于文化层面：需要告诉人们，他们可以忽略既有问题。Dave Airlie 建议把报告拆成两封邮件，一封是对补丁的审查，另一封列出既有问题。

Hellwig 把话题稍微挪动了一下，抱怨 Sashiko 在回复中丢掉了大部分收件人；他说，回复应该发给所有人，否则讨论线索就会断裂。David Hildenbrand 立刻表示不同意；在内存管理子系统中，Sashiko 的邮件被视为对维护者有用，但不应自动发回给提交者或邮件列表。他抱怨说（这种抱怨在当天被听到过好几次），提交者花费时间提交多个版本的补丁集来回应 Sashiko 的意见，而人类审查者甚至还没来得及判断这些补丁到底有没有意义。Sashiko 的审查总体上往往会打击人类审查的积极性。他的建议是，Sashiko 应当作为最后一道防线而非第一道；何时进行自动审查应由维护者来决定。

审查实践

由此引出了关于审查实践、以及人类审查者应当在何时介入提交的讨论。Ts'o 说，在 ext4 文件系统中，这取决于补丁系列的规模和提交者的声誉。来自陌生贡献者的单个补丁很可能是 LLM 生成的垃圾，所以在待审查工作的优先级列表中被排得很低。而较大的系列需要架构层面的审查，因此他往往主要看 cover letter，并把意见限制在总体设计上。

Jiri Kosina 说，把陌生贡献者一律降级处理是个太省事的解决办法；根据他的经验，这些人提交的补丁往往是有效的。Brown 说，与硬件的接近程度会有影响，针对底层代码的一次性补丁往往价值不大。Paolo Abeni 说，在网络子系统中有一套复杂的审查优先级方案，取决于贡献者的声誉、其完成审查的数量，以及其雇主的声誉。Airlie 警告说，追踪声誉会带来隐私问题，并诱使开发者钻系统的空子；他理解这种做法的吸引力，但需要找到更好的方式。Konstantin Ryabitsev 也同意，任何声誉系统都会被钻空子。

Laurent Pinchart 说，一些开发者感到沮丧：他们必须针对 Sashiko 的批评为自己的工作辩护，而其他一些 LLM 生成的补丁却似乎立即被接受了。不过 Abeni 为自动审查辩护，说引入缺陷的补丁数量已显著下降。Zijlstra 说，虽然阅读 LLM 生成的审查会“让我大脑宕机”，他仍然认为这个工具有用；它能发现真实的问题。

Linus 发言

此时，一直保持沉默的 Torvalds 开口了。他说，问题在于我们收到了越来越多来自不了解内核的人的补丁。把矛头指向 LLM，维护者是在怪错了对象。LLM 本可以做好工作，但驱动它们的是一群毫无头绪的人，结果自然难看。他建议，或许可以把 Sashiko 的报告延迟 24 小时发布；这样可以让那些不明就里的开发者无法立即得到反馈、进而源源不断地产出新版本。

几个月来，他一直在一个独立的项目上试用 LLM，以学习这项技术，但直到上周才在内核上使用。他拿出一个旧补丁让 LLM 修改；其结果让他不愿意再在没有 LLM 的情况下工作。他计划在某个时候发布那个补丁系列。他问道，既然工具能够自动修复一个刚被修改的函数的所有调用点，何必费力自己去搜索？但他说，花了六个月的时间才把工具调校到不产生糟糕回应的程度。他说，如果你是一位称职的开发者，LLM 会是一个极好的工具——但前提是先投入那些准备功夫。他拒绝了公开自己 LLM 训练材料的建议，说每个开发者都需要各自经历这个过程。

他总结说，围绕如何对待使用 LLM 的人的争论方向本身就错了；开发者应该专注于如何用好这些工具。Hildenbrand 说，Torvalds 是专家，但我们仍然要面对所有提交补丁的非专家；Torvalds 说，把他们的优先级降下去就是了。

Sasha Levin 建议在代码仓库中放入更多信息来引导这些工具；他随后发布了构建这类信息的第一部分内容。Ts'o 说，为愿意投入精力的开发者提供更好的输入会很有用。不过 Alexei Starovoitov 回应说，教人类如何在内核上工作并不是维护者的职责。当然，社区正在通过邮件列表“教育”机器人，而这正在加剧补丁被快速重发的问题。

Gushchin 说，最终 Sashiko 或许能够告诉贡献者：某个补丁整体上就是个坏主意，不应该再修改下去了。Greg Kroah-Hartman 说，我们可以预期在未来 18 个月里一直面对消防水管般的洪流，之后我们会修复大部分缺陷，日子会好起来。Pinchart 回应说，光修缺陷是不够的；内核里满是糟糕的 API，它们用错比用对还容易。Kroah-Hartman 说，缺陷终将被修完，届时就会有空间去处理 API 了。

Ryabitsev 说，问题在于向内核做贡献从来都是设有门槛的；对许多开发者来说实在太难。而 LLM 让创建内核补丁变得容易了。Pinchart 说，很多使用 LLM 的贡献者只是想让自己的名字出现在变更日志里；他们不会留下来，所以花在他们身上的指导精力都是白费。Torvalds 重申，维护者应该直接降低这些贡献的优先级。Hildenbrand 问具体怎么做；Zijlstra 建议对补丁做出回应，看看回来的是不是 LLM 生成的文本。那些得不到明确的人类回应的评论可以直接忽略。Kroah-Hartman 说，这正是指出琐碎问题（比如头文件包含顺序不对）的价值所在。Christian Brauner 说，过于冗长的变更日志往往是使用 LLM 的迹象。

Airlie 建议为 LLM 添加指引，禁止它们撰写变更日志。Levin 一段时间以来一直尝试添加这类指引；这一努力可能会继续推进。现场达成了普遍共识：即使代码由 LLM 编写，随附的变更日志也应由这项工作背后的人类来写。

私有内核

Brauner 说，内核社区的工作方式正在发生根本性变化，这对 Linux 意味着什么尚不明朗。公司对维护内核私有分支而不理会上游的兴趣日益增长。Zijlstra 建议去问问 Google 这条路走得如何；Gleixner 补充说，围绕维护内核的基本经济规律并没有改变。Brauner 说，在座的开发者是在开源软件占主导的环境中成长起来的，参与其中可以带来良好的职业前景；如果情况不再如此，还有谁愿意回馈上游呢？

不少与会者表示，任何想拿私有分支碰运气的公司尽管去试。Kroah-Hartman 说，社区的目标一直是让在上游工作比维护私有代码更便宜。Miguel Ojeda 问现在这是否仍然可能；他认识有人用 LLM 变出了一个完整的 Rust 语言内核。在上游工作怎么能比这更便宜？Torvalds 说，如果真到那一步，社区可能就不再可行了，但现在还不是那种局面。Starovoitov 说他知道有五个这样生成、并且能运行的内核；Torvalds 回应说，为它们操心毫无意义。

Ts'o 说，如果有人想为特定用例变出一个快速的微内核，现在就能做到，但一个能应对各种随机边角情况、面向通用用途的内核则是另一回事。他认为对 Linux 内核的需求还会持续相当一段时间。Starovoitov 强调，需要理解为什么有人有兴趣生成私有内核；他说，Linux 到处是没被足够快修复的窟窿，向内核做贡献又太难。

太难，还是太容易？

这是我分享几则特意为这次聚会留着的轶事的机会。在追踪 linux-kernel 邮件列表这条永无止境的跑步机上，我最近遇到一个超过 100 个补丁的系列，全部来自一个新身份、在一个小时之内发出，对内核树的各处做出了重大改动。以这种方式看，这些补丁显然是一台被放出的机器人的产物，最好直接忽略；但大多数维护者只会看到其中少数几个，看不出规律，于是认真对待发送者。结果，这些补丁中有相当多被合入了。

首次贡献者的洪流令人难以置信（仅 7.3 版本就接近 800 人），把社区埋在了补丁之下。已经有大量首次贡献者在短时间内对多个子系统做出非平凡改动的案例。在我看来，很明显这些提交者中有许多人并不理解自己在做什么，他们也不会留下来修复或维护那些补丁。但大量这样的代码正在进入内核。我担心的是，我们正在积累一批没有人理解的代码，某一天我们会猛然发现，已经完全失去了对内核的控制。

Airlie 回应说，我们其实从来就没有真正控制过它。Torvalds 说，是时候让新人向内核贡献代码变得更难一些了。像 Kroah-Hartman 这样的人花了多年时间教人们如何做贡献；他说，是时候停止这样做了。Ojeda 说，需要降低这些贡献者的优先级，但我们仍然需要找到有才华的人加入社区。这意味着要设法聚焦于真正重要的人。例如，愿意花时间参加开发者大会的人留下来的可能性要大得多。新贡献者的补丁绝大多数不值得理会，但其中一些是值得的，而甄别它们很难。

Shuah Khan 说，她能相当快地辨认出哪些人会留下来，而且一些新来的人非常出色。因此她仍然花很多时间处理提交拼写修复的人。Hellwig 说，开发者应该可以随意使用任何工具。对于任何非平凡的工作，总会有问题需要修复；到那时，关键在于能否与贡献者进行真正的对话。不过 Abeni 反对说，这种做法对较大的子系统来说无法扩展。

生成代码

Ojeda 提出了在哪些场景下用 LLM 生成代码是合理的这一话题。他说，在有明确规格说明和具体问题的情况下，LLM 可以产出不错的结果。这些工具适合用来验证概念；甚至可能不必查看生成的代码，就可以把它扔掉，然后正确地实现那个被验证成功的概念。生成测试是 LLM 可以胜任的另一个领域。Brauner 说，LLM 适合用于原型开发。

Hildenbrand 说，讨论一直聚焦在新贡献者身上，这没问题，但我们如何让其他维护者知道：忽略这些人的补丁是可以接受的？Hellwig 说，忽略补丁永远都是可以接受的；我回应说，多年来我们一直在努力防止补丁被漏掉。

Torvalds 建议添加一个 AGENTS.md 文件，让生成内核代码变得“昂贵”。他每次会话都以一次冗长的清理收尾，要运行几个小时，执行诸如确保代码与注释一致之类的任务。这种工作量靠一个免费的 LLM 账户是无法完成的。我问这是否有风险切断我们更愿意留住的优秀新开发者；Torvalds 回答说，内核项目只想要认真的开发者。这包括拥有在这个世界里正常运作所需的足够资源。

Pinchart 说，他听到一些开发者担心自己会被迫离开社区；Torvalds 回应说，写代码、发邮件永远都是可能的。关键在于过滤掉那些自己做不到这一点的人。Pinchart 请 Torvalds 确认他并不打算排挤不使用 LLM 的开发者；Torvalds 同意他不是。Pinchart 补充说，把这个信息传达给社区很重要。Torvalds 补充说，他不想吓跑想写代码的人；他传达的信息是：要么花力气学习，要么在 LLM 上投入大量资金，才能参与进来。

Airlie 表示担心，那些人可能已经没有东西可写了；一个想法刚被提出，马上就有人能从 LLM 那里召唤出一个实现。Alice Ryhl 同意这可能是个问题。Ojeda 建议建立一种机制，把某个项目在一段时间内指派给某位开发者；Hellwig 说，这样做的唯一理由是出于训练目的。否则，既然已经有现成的实现，为什么要等？Ojeda 说，支持不想使用 LLM 的开发者也是很好的理由。

Assisted-by

Documentation/process/coding-assistants.rst 已在 7.0 内核中加入，为使用这些工具的开发者提供指引；其中要求在借助 LLM 开发的补丁的变更日志中加入 Assisted-by 标签。截至 -rc7，7.3 内核已纳入 18,533 个非合并变更集（创纪录），其中 1,884 个（约 10%）含有 Assisted-by 标签。实际由 LLM 辅助的补丁数量肯定要高得多。

在峰会上，我指出大量贡献者虽然在使用 LLM 却没有加这些标签；有时是因为不了解规则，有时则是提交者想刻意隐藏自己对 LLM 的使用。但几乎没有维护者去询问贡献者的 LLM 使用情况并确保标签存在。其结果是，Assisted-by 提供不了任何有用的信号。我建议，要么找到办法强制执行这一要求，要么干脆彻底放弃它。

Airlie 说，如今大概 90% 的贡献者都在使用 LLM。他说，其中许多人害怕被卷入反 LLM 的猎巫行动。他建议增加一项要求，让模型读取内核的全部文档，并写入 AGENTS.md 文件。Torvalds 认为，许多提交者只是羞于承认自己在使用这些工具。Gleixner 半开玩笑地建议，不如改加一个 Not-assisted-by 标签；Arnd Bergmann 说，他会觉得这是“值得投入时间去帮助的开发者”的有用指标。

Torvalds 说，标签要求可能会吓退使用 LLM 的人，他很乐意取消这个要求；Brauner 补充说，它现在已毫无意义。Khan 说她仍觉得 Assisted-by 有用，但现场有强烈的共识：这个标签已经完成了它可能有过的一切使命，这一要求可以取消。

尽管如此，大家普遍仍有兴趣了解补丁是如何产生的。有人希望看到使用了哪些模型，或者模型是在开发流程的哪个环节被引入的。维护者仍然想知道开发过程中是否有人类参与。不过大家一致认为，这些信息不必记录在变更日志中；讨论中提出的建议是把这些信息放到 cover letter 里。

安全问题与紧急修复

LLM 的出现导致大量与安全相关的缺陷被发现，随之而来的是大量修复。在这些缺陷的响应工作中扮演核心角色的 Kroah-Hartman 说，还有更多正在路上。他说，目前的工具能找到很多漏洞，但其中大约一半也是错的；他有学生在致力于改进这一表现。他也有人力和资金来帮助处理由此产生的修复。他说，这一大堆问题我们可以处理完，但需要一些时间。这正是未来一年的工作重点。

Levin 补充说，LLM 做到了两件前所未有的事。一是它们擅长从补丁开发出漏洞利用；二是它们可以被用来监控邮件列表并判断哪些修复涉及安全问题。其结果就是自动批量生产漏洞利用的机器。他说，问题一旦被发现，任何 embargo 实际上都已终结。目前外界已有数千个已知的漏洞利用。

Kroah-Hartman 说，唯一能做的就是让修复尽快进入主线。Brauner 指出，这会导致 -rc1 之后出现大量 pull request，而 Torvalds 曾对此抱怨过。不过 Torvalds 说，满是修复的 pull request 没有问题，只要它们来自他信得过、确实验证过这些是针对真实问题的修复的人。对他来说，做一次 pull 的成本几乎为零；这本就是他的工作。

Pinchart 说，修缺陷固然好，但真正需要的是防止新缺陷被引入的办法。Kroah-Hartman 说，更多使用 Rust 会有所帮助；许多缺陷出在错误处理路径上，而 Rust 有更好的处理方式。另外，也有一项工作在推进，即扩大对 C 代码加固（hardening）的投入。

其中一些工作已落地于最新版本的编译器中，但开发者往往不容易用上它们，linux-next 同样如此。Ojeda 说，目前有工作在推进，以提高预构建工具链的可用性，供开发者测试自己的代码。

Kroah-Hartman 说，安全缺陷现在会被立即抄送给维护者，而不是保密；这是跟上这股洪流的唯一办法。但他提醒，维护者不应在缺陷公开之前把消息告诉自己的雇主；否则整个项目将面临与全球各地政府机构产生麻烦的风险。不过，一旦修复被推送，embargo 即告结束。

Starovoitov 说，如今存在由 LLM 发现的漏洞清单，其中许多附有复现程序。他想知道把这些修复送入主线的最佳方式是什么。Torvalds 说，如果有真正的内核开发者参与，最紧急的补丁可以直接发给他，绕过维护者，避免增加他们的工作负担。Hildenbrand 担心维护者会因此失去审查其子系统内修复的机会并失去控制权，但 Torvalds 回答说，审查所有这些修复只会给每个相关的人增添压力。

痛点

峰会之前，Torvalds 请每位与会者准备一段一分钟的陈述，向大家介绍自己最大的痛点。这些陈述在半小时内完成，在所有人讲完之前不进行讨论。“不讨论”的规则在大部分（但不是全部）时间里得到了遵守。按发言顺序：

  • Kroah-Hartman：有些子系统不给补丁加上 CC: stable@vger.kernel.org 标签，却仍然期望 stable 团队去捡起那些重要修复。stable 维护者已经不堪重负，不会那样做。
  • Pinchart 听开发者说，他们提交了代码，却不知道补丁何时被合入、合入了哪个树。他说，更多维护者应在合入补丁时发一封邮件。
  • Eric Biggers：难以直接应用的补丁，而且没有注明可应用的基础提交。他说，很多补丁不先应用就无法得到恰当的审查。
  • Rafael Wysocki：总体上补丁得到的反馈不足。人们往往有意见，却不总是说出来。
  • Airlie 问了他的子维护者；其中大多数人指出他本人就是最大的痛点。认真地说，痛点在于 DRM 子系统的回归仍然太多。子系统内部有一股推动力，想把开发迁到 GitLab 以使用其 CI 功能；他没有阻拦，因为想看看结果如何。
  • Ts'o：优先级安排，以及要看的东西太多。他很想在 patchwork 中加一个优先级标签，供维护者设置，帮助识别哪些需要优先关注。
  • Ryhl：发出一个版本的补丁后，不知道要等多久才能断定不必再为它的问题操心。
  • 我（本人）：大量补丁触及文档目录，很难判断哪些该由我来合入、哪些该留给别人。大量时间被花在翻查 linux-next，看补丁是否已被别人捡走。Torvalds 说他也经常有同样的问题。
  • Khan 抱怨同样的问题；往往不清楚谁会捡走测试补丁。
  • Hildenbrand：审查负担沉重。审查不能简单交给机器人；大多数改动需要开发者的意见。不知怎么地，子系统需要培养出更多专家，但很难识别出能够这样成长的人。
  • Bergmann 说，审查流程正在崩溃。他回复补丁时，尽力教导贡献者如何改进，但他已经灰心，因为使用 LLM 的人不学习。于是现在那些可能学得会的人得不到他们需要的反馈。相反的问题也存在：一位提交者（确实）发送了 50 个版本的补丁并回应了每条意见，但 Bergmann 认为那个补丁根本就不该存在。
  • Starovoitov：维护者不应再去寻找缺陷或编码风格问题；机器人现在会做这些。相反，审查应严格聚焦于补丁的“为什么”、修复是否做在了正确的位置，以及是否有品位。
  • Ryabitsev：MAINTAINERS 文件中最后一项，名为 “THE REST”，把每个补丁都定向到 linux-kernel 邮件列表。这每天产生数百万封外发邮件，导致持续的投递问题。他询问能否移除或修改这一条目，把补丁重定向到 patches@vger.kernel.org 列表。他随后提交了一个针对 get_maintainer.pl 的补丁，使其只在没有其他列表被确定为收件人时才添加 linux-kernel。
  • Levin：各子系统的实践正在分化，许多子系统现在都有一份关于如何与之交互的手册。这让跨子系统工作的开发者日子艰难；他希望社区重新团结起来。
  • Hellwig：Sashiko 审查工作流已经坏掉，导致人们不断重发补丁。这个问题没有显而易见的答案，但必须有所改善。
  • Brown 请有测试的子系统真正去构建并运行它们，以免它们在 linux-next 中损坏。
  • Kosina：需要更好的方式来确定处理提交的优先级。他喜欢 Ts'o 的想法，但不想借助 patchwork。
  • Will Deacon：这个过程已经不像从前那样有趣了；维护者尽力向贡献者解释他们可以如何改进，却被无视。
  • Danilo Krummrich 不介意在短时间内看到同一个系列的多个版本，但提交者只是把 Sashiko 的审查喂给 LLM 来生成这些新版本。需要找到办法鼓励提交者真正参与并与维护者交流。
  • Abeni：基础设施跟不上子系统的需要。网络子系统运行着自己的 Sashiko 版本，效果更好，但不可能为每个网络子系统都运行一套。这给维护者带来额外的摩擦。
  • Eric Dumazet 宣布他刚刚退休，他所有的痛点都烟消云散了。
  • Gushchin：Sashiko 已从一个实验成长为社区广泛使用的工具。除了开发机器人本身，还有大量工作要做：他得获取运行所需的 token、向管理层解释它的价值等等。他非常需要更多的人手和更多的反馈。他只熟悉少数几个内核子系统；如果别人不告诉他其他子系统的问题，他永远不会知道。
  • Julia Lawall 不知道她的工作——其中大部分涉及在内核中查找和修复缺陷——将来是否还有意义。五年前她还会向开发者索要更多反馈，如今她不确定这是否还重要。
  • Ojeda：横跨整棵树（tree-wide）的重构工作可能很棘手，而更多 Rust 代码的出现似乎将使其更难。
  • Gleixner 把大量时间花在研究设计模式并用长篇邮件加以解释上。开发者曾经珍视这种工作，但近来它大多被无视，他怀疑这样做是否还值得。在 LLM 的世界里，人们说他们没时间搞设计，再说代码能跑。他做了 25 年的清理工作，不想再合入将来还得清理的东西。
  • Brauner：删除代码。是时候少修一些代码、多删一些代码了。

原意是这些痛点会在陈述结束后进行讨论，但实际上并没有发生。相反，对话走向了一个相当不同的方向。

接班

Torvalds 表示，他即将休假两周，考虑到合并窗口即将开启，这有些尴尬。因此他在考虑把合并窗口延长到第三周作为应对。现场对这一想法没有太多反对意见。

他接着谈到接班计划。2025 年峰会曾就这一话题进行过讨论，主要聚焦于如果 Torvalds 突然无法继续领导项目该怎么办。今年他说，虽然他短期内不会离开，但思考如何优雅地过渡到一个没有 Torvalds 的未来并不为时过早。为推动这一进程，他已开始主动忽略更多邮件，并在开发问题上略微退后一步。他很好奇社区会如何反应。

随后是一场宽泛而无定论的讨论，主题是 Torvalds 在社区中扮演的角色，以及当他最终决定转向别处时事情将如何运转。这一角色的两个主要方面可以概括为“补丁猴”（patch monkey，执行 pull request）和开发者之间冲突的仲裁——他自称不擅长后者。未来这些角色也许可以分开。项目可以任命一位新的“仁慈独裁者”，或者转向某种委员会模式。

没有做出任何决定——现在不需要做决定，也没有人期待做出决定。但 Torvalds 显然认为，最好远在压力到来之前就思考这些问题。将建立一个邮件列表，初始成员为峰会与会者，让相关讨论慢慢酝酿。最后，Gushchin 指出，如今的世界与一年前已大不相同；以目前的变化速度，要为预计在多年之后发生的事情做出有意义的规划，将会很困难。

元讨论

最后一个话题是 Maintainers Summit 本身，以及它将来可以如何改进。话题始于今年 8 月的一个讨论串，其中 James Bottomley 质疑这一活动是否还应该继续存在。似乎没有多少人认为应当取消它，但人们对与会者的遴选流程表达了担忧，有人称其为封闭的小圈子。

也许不出所料，在场的维护者——他们都收到了邀请——并不觉得那个流程有什么大问题。高层次的流程讨论往往需要高层次维护者到场。正如 Brauner 指出的，这个群体总难免显得有点精英化。但他说，让这个群体每年相聚一次，对整个项目的管理是有益的。

Torvalds 说，Kernel Summit 旧有的形式——参与者上限约 150 人——根本无法管理。他说，较小的群体至少能够进行有建设性的讨论。Hildenbrand 说，问题之一是人们普遍有一种印象：为峰会提议一个话题就必然会换来一封邀请；他建议明年重新措辞征题公告。

Ts'o 说，把峰会与 Linux Plumbers Conference（LPC）放在同一地点举办效果很好，而且峰会安排在其后举办最佳。这样与会者可以从其他人那里收集信息，再带到这个更聚焦的群体中。

Hellwig 提出希望有另一种形式的聚会，让来自同一子系统的开发者可以与其他人进行“办公时间”（office hours）式的交流。如今在大会上某种程度上已有这种形式，但他说，大会的时间安排太紧、其他干扰也太多。Bergmann 指出，LPC 的 kernel-summit 分会场（track）多年来相关性逐渐下降，建议可以把其中一部分时间挪作他用；这一想法获得了相当不错的反响。也有人谈到在其他时间使用视频会议服务器来举办面向子系统的办公时间。

会议在普遍的共识中落幕：现有形式运转得相当不错，办公时间的想法或许能使其更进一步。最大的变化可能出现在征题公告上，它可能会被重写，以提供更多关于遴选流程如何运作的信息，并明确人们可以提名他人参加。最后，还有人建议可以更多地使用 ksummit 邮件列表。通常在会议临近时那里会有有趣的讨论，但其余时间便归于沉寂；没有理由不能在其他时间也在那里开展这类讨论。

Rust 项目目标进展更新

作者：Daroc Alden 2026年10月8日 英文原文

Tomáš Šedovič 是 Rust 基金会的项目经理。他共同领导目标团队（goals team），该团队协助组织 Rust 项目的整体目标，包括确保同意参与某项目标工作的人获得所需的支持。在 Kangrejos 2026 大会上，他概述了 Rust 项目的目标流程，目的是让 Rust for Linux 的开发者了解该项目如何组织、跟踪和修订目标。Rust for Linux 项目催生了当前的若干项目目标，因此他认为让大家从内部视角了解这套流程或许会有所帮助。

Šedovič 说，目标是向 Rust 做出更改的若干入口之一。如果有人想做出某项更改并且知道怎么做，可以直接与相关团队沟通并着手实施。如果有人想做出更改，但不知道从何入手、该找谁谈，这就是目标团队发挥作用的地方。他们会接收提案，与提交者协作完善它，把它交给合适的人来实施更改，并持续跟进以确保一切按计划推进。

最初的提案可以是任何内容：一项特性、编译器的重构、测试覆盖、性能工作等等。大多数目标针对特定特性，但并非必须如此。提案写好之后，需要有人承诺承担实际的实现工作。通常这就是提案作者本人，但有时是项目的其他贡献者。偶尔，要找到愿意做实现的人还需要为其投入的时间提供资金。目标团队最近开始把需要资金的提案与希望看到相关工作完成的资助方对接起来。

提案、资金和进行中的目标都在 Rust 目标网站上跟踪。部分目标还会被打包成"路线图"（roadmap），即一组相关目标的集合。目标应当是自包含的，耗时不超过大约一年。

路线图是更长期的计划，例如让 Linux 内核仅用稳定语言特性即可构建。2024 年，Rust for Linux 项目提出了唯一一项 Rust 项目目标。自那时起，目标不断扩展，如今 Rust for Linux 路线图下已列出了十三项目标。

Šedovič 简单演示了目标网站的布局，展示了正在寻找贡献者的目标列表、正在寻找资金的目标列表，以及所有目标的完整列表。Miguel Ojeda 将最后这个列表比作 C++ 委员会的论文列表，方便更熟悉 C/C++ 开发模式的人理解。

目标！

接下来，Šedovič 简要汇报了当前所有 Rust for Linux 目标的进展。他从字段投影（field projections）目标讲起，并称其为一个写得很好的目标的范例。每项目标都应指定一个具体的联系人，在这里是 Benno Lossin，由他负责持续更新。目标还可以拥有专门的 Zulip 频道用于讨论，并在每个相关团队中指派一名"倡导者"（champion）。字段投影目标需要更改语言的定义、类型检查器、编译器本身、各类库以及语言的运算语义；因此每个相关团队都有一名指派的倡导者。

该目标本身的实际工作主要是梳理可能的设计空间。Lossin 承诺会在他稍后的演讲中讨论这一点，因此 Šedovič 跳过了大部分技术细节。Tyler Mandry 也在一周前的 RustConf 上介绍了部分已敲定的设计。

下一个讨论的目标——任意 self 类型（arbitrary self types）——的涉及面要小一些。目前，Rust 类型上的方法接收对被调用值的引用时，只能使用内建的引用类型或内建的智能指针类型，例如 Box 或 Rc。由 Ding Xiang Fei 领导的任意 self 类型工作，旨在将这一能力扩展到任意的用户自定义智能指针。在内核中，这可以让定义便捷 API 变得更容易——这类 API 在获取锁或使用读-复制-更新（RCU）保护的同时访问资源。

另一个小改动是更好的就地初始化（in-place initialization）。目前，Rust 中所有结构体都先在栈上分配，即使它们随后会立即被移入堆。这并不理想，因为分配大型结构体时可能导致栈溢出，在使用较小栈的内核中尤其如此。虽然在大多数情况下可以通过将一段内存填零并将指向它的指针做类型转换来绕过，但最好能有内建的语言支持，就像 C++ 那样。Alice Ryhl 正在推进这一目标。

不可移动类型（immovable type）的概念也可能是 Rust 可以从 C++ 借鉴的东西。所有 Rust 类型都可以通过直接移动其字节来移动，唯一例外是用 Pin 包装的类型。这种包装一直带有几分权宜之计的色彩，并且让许多处理被固定（pinned）结构的接口比本应的样子更复杂。不可移动类型与有保证的析构器目标涵盖了实现新的 Move 自动 trait（auto-trait）所需的工作——该 trait 可以被选择退出，从而将类型标记为不可移动。

const trait、完整的 const 泛型和 supertrait 自动实现目标都旨在提升 Rust 类型系统的灵活性。它们分别可以实现：在编译期使用 trait 实现、一种受限形式的依赖类型，以及更容易的、向后兼容的 trait 层级修改。Ojeda 表示内核会充分利用这三者，因为在编译期安全地生成特化代码的能力在内核语境中普遍有用。

Šedovič 提到的最后一个目标，就是催生整组 Rust for Linux 目标的那个：稳定内核构建所依赖的那些不稳定的编译器特性。随后 Ojeda 引导大家去看他在内核一侧用于跟踪这些共同目标的跟踪文档，并询问 Šedovič 是否知道处理完现有的 Rust for Linux 目标大概需要多久。

Šedovič 认为无法给出确切答案，但表示自他开始在目标团队工作以来，他"看到了大量的进展"：

"字段投影、就地初始化——这些都是非常难的问题，但人们真的投入进去了。"

不过他说，令人欣慰的是，这些最初由 Rust for Linux 项目请求的语言变更，如今也有正在将 Rust 引入 CPython 的 Python 贡献者提出请求。Šedovič 说，能够说出"哦，这些事情我们已经在做了"是一件令人愉快的事。他总结道，两个大型 C 项目请求相同的特性并汇集资源共同推进，表明一旦当前目标实现，Rust 将能很好地融入现有的 C 项目。

工具链

用大语言模型进行 GCC 开发

作者：Jonathan Corbet 2026年10月14日 英文原文

经过反复讨论，GCC 项目最近制定了一项关于在编译器套件开发中使用大语言模型（LLM）的政策。这项政策有些限制性，但仍然为 LLM 在开发过程中的使用留出了空间。在 2026 年的 GNU Tools Cauldron 上，Jeff Law 和 Kyrill Tkachov 讨论了这些工具是如何对他们有所帮助的。

Law 首先回顾了项目的政策，即"拒绝任何包含 LLM 生成内容或源自 LLM 生成内容且具有法律意义的贡献"。不过，这项政策并非普遍适用；对于向测试套件添加内容的情况，政策明显更为宽松。LLM 可用于帮助理解代码、查找 bug、审查补丁等等。但项目希望避免其版权被 LLM 生成的代码所污染；这一领域的法律尚未定型，因此项目采取了保守的立场。他说，这项政策将定期评估，并可能在不久的将来予以修订。

说完这些，Law 表示在本次环节接下来的时间里，政策问题明确属于离题内容；随后他把话筒交给了 Tkachov。Tkachov 一开始便说，最好把基于 LLM 的工具当作虚拟助手来对待。它们蕴含大量知识，接受过多种类型材料的训练，并且能够查阅资料。

他说，这些工具也能编写代码，尽管写出来的代码好不好尚有争议。它们可以写出合理的测试。LLM 擅长处理含糊不清的请求，并具备一种"能干的态度"。他说，有一个助手愿意去尝试各种想法而不是跟你争论，这令人耳目一新。LLM 不会感到厌倦，因此把重复性任务交给它们也不会让人觉得过意不去。

他花了一些时间探索用 LLM 来查找 bug。若将它们指向特定的代码区域，并告知需要查找哪类 bug，它们的效果最好。他说，LLM 在发现错误或缺失的测试方面表现出色。这些工具可以为 bug 构建最小重现程序，并撰写清晰的 bug 报告。当然，它们的输出仍然始终需要人工审查。

一个相关的任务是查找 bug 的根本原因。LLM 可以按需构建编译器版本，并将结果与 LLVM 的行为进行比较。它可以检查 GIMPLE 和 RTL 中间表示，从而准确找出是哪个编译器 pass 出了问题。结果中还可以包含一个建议的修复方案；该修复不一定正确，但通常是很好的起点。他提到这个 bug，作为一个 LLM 帮助快速找到根本原因的例子。

LLM 适合用于快速原型设计和可行性研究。例如，某些优化既可以在 GIMPLE 层完成，也可以在 RTL 层完成，而通常其中一个的效果会更好。如果他不想把时间浪费在错误的方向上，可以让 LLM 把两种方案都试一遍，并给出该更改实际影响的数据。一旦找到了正确的方向，这些代码就可以丢弃，然后再正式地重写。

LLM 适合的其他任务还包括寻找被错过的优化机会以及改进构建系统。总的来说，他说，即使受到项目政策的约束，LLM 也已被证明对 GCC 开发有用。它们可以协助数据收集、运行"如果……会怎样"的演练，以及追查 bug。但即便项目政策允许，用它们来编写代码也是有风险的。

Jeremy Bennett 问道，在这么多任务上对 LLM 的依赖日益增加，是否会让项目面临失去那些真正理解代码的人员的风险。Tkachov 回答说，这确实是一种风险，但他也将这一情形比作汽车工业。曾经，人们必须了解发动机的工作原理才能开车，但如今已不再如此；也许未来许多开发者将不需要如此深层次的理解。他说，当需要更深入的理解时，开发者可以利用 LLM 永不厌倦向人解释这一特点。它们可以详尽地解释代码，只要愿意投入时间学习，就能帮助提升理解。Bennett 表示这没问题，但他担心的是那些职业生涯刚起步的开发者，他们可能永远无法获得对代码的深层理解。

Mathieu Desnoyers 建议先在自己能够理解的项目上试用 LLM；这是了解其局限性的好方法。之后再扩展到新的领域。他说，应当多向工具提问；有时这会把 LLM 逼到能够纠正自己所犯错误的地步。

Law 回来谈了几个他发现这些工具特别有用的具体领域。其中之一是挖掘编译器生成的汇编代码，寻找可以改进代码生成的地方。他有一个 QEMU 插件，可以识别热点代码块，然后将其交给 LLM 评估是否存在次优的代码生成。这项工作已经带来了针对热门基准测试所生成代码的改进——其中包括一些他已经凝视了多年的代码块。

事实上，他说，他查看过的每一个基准测试都找到了改进之处。这项工作最难的部分是为模型编写好的提示词。这令人沮丧到他曾尝试雇用第二个 LLM 为第一个 LLM 编写提示词，但结果是"一场彻底的失败"。

关于审查现有代码，他说，在所需上下文量相对较小的领域，LLM 表现良好。例如，评估 match.pd 文件中的模式就是 LLM 的一项很好的任务。这些模型往往会产生大量的错误报告，而他真正想要的只是对其所发现错误类型的描述。不过，这些报告指出的确实都是真实的 bug。他再次表示，更好的提示词工程肯定会有所帮助。

至于补丁审查，他编写了一个 Thunderbird 插件，可以直接在邮件客户端中完成这项工作，但他对结果一直不太满意，其中充斥着 slop。有效报告的比例大约是 20%。在提示词中加入更具体的指导显然有帮助；他在这上面做得越多，就越是在重新造 Sashiko 的轮子。事实证明，Sashiko 所做的许多工作更具通用性，可以为 GCC 带来良好的结果。

本次演讲以对 LLM 有用之处的总结作结，并建议开发者应当使用它们来审查自己的补丁。Law 说，社区将受益于一种在开发者之间共享提示词的方式。最后有人问到将专有 LLM 用于自由软件开发（或用于任何事情）的伦理问题；Law 承认这些担忧确实存在且合理，但表示他无法对此提供任何答案。

内核

为 GCC 添加内核控制流完整性检查

作者：Jonathan Corbet 2026年10月9日 英文原文

当许多开发者还在疲于应付如潮水般涌来的漏洞报告时，另一些人仍在专注于从源头上防止这些报告的出现。控制流完整性（control-flow integrity，CFI）指的是防止（或至少检测）那些使控制流偏离其既定路径的攻击手法。在 2026 年 GNU Tools Cauldron 大会上，Kees Cook 介绍了他为 GCC 编译器套件所做的修改，以支持内核的前向 CFI（forward-edge CFI）。

他开场说，这项工作的根本目标，是防止一个允许向内存任意写入的漏洞被升级为完整的代码执行漏洞。曾几何时，内核可以写全部内存，因此攻击者可以轻易地直接改写内核的代码。随着时间推移，可执行内存已被写保护并隔离起来，如今已能完全免受此类攻击。于是，攻击者转而专注于以意料之外的方式复用现有代码——使用伪造的参数调用函数，尤其是劫持间接函数调用和函数返回，迫使它们跳转到意料之外的位置。

间接函数调用本质上是一次跳转，目标是存储在（可写的）内存位置或寄存器中的地址；如果这个地址能被更改，内核的控制流就可以被重定向到攻击者选定的位置。防止这类调用被劫持被称为"前向"CFI，这正是 Cook 工作的主题。防止返回被重定向则是"后向"CFI，他说这项工作最好交由硬件处理，超出了本次演讲的范围。

前向 CFI 的关键在于提供（并检查）关于间接调用的预期去向的信息。这样就可以在调用发生时验证函数指针。具体而言，目标是确保任何间接调用最终落在以调用方所期望的原型定义的函数上。这与大多数借助硬件的前向 CFI 不同——后者只是标记函数的入口点。硬件方案可以防止调用到函数的中间位置，但无法检测到重定向到了一个完全不同的函数。

检查原型匹配并不能阻止所有被误导的函数调用；一个函数可能拥有兼容的原型，但并不打算在特定场景下被调用。即便如此，原型检查仍能大幅缩小间接调用的可能目标范围。Cook 说，内核中的间接调用里，55% 的可能目标少于五个，只有 7% 的可能目标超过 100 个。少数调用的目标则多得多。

前向 CFI 的实现方式是为每个函数计算一个类型 ID（type ID）；它是由函数原型生成的哈希值。每个可达的函数都在其前导代码（preamble）中包含这个哈希，而每个间接调用都会在允许调用继续之前检查该哈希。这种 CFI 于 2022 年在 Clang 中实现；内核在 6.1 版本中获得了使用该特性的能力。Cook 说，他曾长期呼吁在 GCC 中实现等价功能，但找不到愿意实现的人，于是决定自己动手。他补充说，在此过程中，他明白了为什么没人愿意接手那个项目。

该实现将类型 ID 哈希加入每个函数的代码中，紧邻入口点之前。每个调用点都存储了该哈希的二补数相反数。编译器为间接调用生成的代码会从目标函数取出哈希并与本地存储的哈希相加；如果结果为零，则允许调用继续，否则会产生一个陷阱（trap）。有一种宽松模式只发出警告但允许调用继续；另一种不那么宽松的模式则会让系统 panic。

Cook 起步时对 GCC 代码库并不熟悉，但他逐渐学会了；要把这个特性映射到 GCC 的内部结构中，需要在编译器的多个层次上工作。C 前端负责属性和类型，中间层必须把这些类型转换为哈希并用检查代码包裹间接调用，各目标架构相关的后端则必须把这些被包裹的调用转换成所需的具体指令。后端还要把类型 ID 注入函数前导代码。

在前端，新的 -fsanitize=kcfi 命令行选项用于启用该特性。此外还新增了几个属性，用于对特定的函数调用禁用 CFI 检查。例如，如果一个调用进入 BIOS，它会缺少必要的类型 ID，因此无法执行检查。还有一些逻辑用来处理内联函数。

类型修饰（type mangling）被用来生成类型 ID；他最终使用了 Clang 的 Itanium C++ 修饰器，以与 Clang 的行为保持一致。他发现 Clang 的实现使用了一种编译器开发者想要摒弃的哈希实现，于是提交了一个补丁来更换它。他说，实际使用的算法并不重要，也不必具备密码学安全性。现在使用的是 FNV-1a 哈希。

中间层需要一个针对函数调用的新 RTL 包装，其中包含目标函数的类型 ID。他说，确保尾调用（tail call）被正确处理也带来了一些复杂度。他已为四种架构添加了后端支持：32 位和 64 位 x86、64 位 Arm，以及 RISC-V。

最终补丁系列大约有一半是回归测试；在开发这个特性的过程中，他"以各种方式把东西弄坏过"，并为每一种方式都写了一个测试。他一直很难为成果找到审查者；大多数 GCC 补丁不会横跨整个技术栈，因此没有多少人能审查全部内容。GCC 项目的全局审查者之一 Andrea Pinski 表示，完整的审查正在进行中，应该会在近期完成。

Cook 最后谈到了大语言模型（LLM）在这段代码开发中的使用。GCC 的 AI 政策总体上禁止 LLM 生成的代码；这一限制曾让他感到紧张，直到他注意到测试被明确排除在外。他说，他的补丁系列中只有测试是在 LLM 协助下生成的。事实证明，Sashiko 审查系统对审查这项工作很有帮助。

系统

systemd 现状：2026 年版

作者：Joe Brockmeier 2026年10月9日 英文原文

在 2026 年的 All Systems Go! 大会上，systemd 维护者 Luca Boccassi 和 Zbigniew Jędrzejewski-Szmek 主持了传统的“项目现状”环节，概述了 systemd 项目过去一年的成果。随后是一场维护者圆桌讨论，Boccassi、Jędrzejewski-Szmek、Daan De Meyer 以及项目负责人 Lennart Poettering 回答了关于 systemd 的规模、健康状况，以及它是否会取代 Kubernetes 的问题。（不会。）

我今年没有亲临 All Systems Go! 大会，但在会议视频发布后观看了录像。“systemd: state of the project”和“systemd: round table”两场录像可以通过 Chaos Computer Club 的媒体存档以多种视频和纯音频格式获取。“systemd: state of the project”演讲的幻灯片也可以在线获取。

Boccassi 首先感谢 Software in the Public Interest（SPI）为 systemd 处理“财务和法律事务”，并提到他每年会向 SPI 提交一份年度报告，内容包括项目的主要发布、贡献者数量等。2025 年，这体现为两个主要的 systemd 版本（v258 和 v259）以及 40 个次版本。2025 年，项目合并了来自 379 位贡献者的 6,160 个提交，低于 2024 年的 7,372 个。他说，到 9 月底，项目已经收到了来自 480 人的贡献。他表示，贡献者数量的增加在很大程度上是人们使用 LLM 编程工具的结果。

systemd v258 版本的开发历时约九个月。Boccassi 说，对于如此漫长的发布周期，“大家都不满意”，因此项目决定尝试每个季度发布一次。“我们用两个月合并特性，然后用一个月进行稳定化并发布候选版本。”他说，项目并不总能精确命中计划中的发布日期，但每次都在一周左右之内。2026 年到目前为止已经有了三个主要的 systemd 版本（v260、v261 和 v262）。“这更像是在放牧一群猫，而不是发布工程，但到目前为止运转良好，大家似乎都对此感到满意。所以我们尽量保持这个固定的节奏。这对开发者、维护者、发行版以及用户都更好。”

蓝精灵村庄

他指出，systemd 最近将其治理方式成文化：这份文档相当简短，只有六条简短的规则，以及项目当前维护者的名单和项目负责人（当然是 Poettering）。Boccassi 将项目的治理概括为：“它基本上就像蓝精灵村庄那样运作。我们有一位蓝爸爸负责，然后（维护者们）或多或少是一个集体，做决策、合并 PR 等等”。

Jędrzejewski-Szmek 展示了项目自 2016 年以来 GitHub issue 和 pull request 的统计图表。他解释说，issue 新开的速度正在加快，如果持续下去，项目将面临大量未解决的开放 issue。“我们目前有 3,000 个（开放 issue）。这已经多到难以掌控了。所以我不知道该怎么办。这不太妙。”

pull request 也呈现出同样的趋势。他说，项目在 2025 年年中之前一直能很好地跟上这些请求的节奏，如今却由于他所说的 AI 革命而开始不堪重负。“现在我们看到的是指数级增长，如果这样继续下去，我们就只能停止审查和处理 pull request，我认为这种状况无法持续”。不过，向代码库合并提交的速度基本保持恒定。“似乎没有什么能对 systemd 仓库的提交节奏产生太大影响。我的假设是，实际参与审查的人数没有太大变化，所以合并速度才保持恒定”。如果项目想要提升处理能力，就需要改变流程，或者增加参与审查的人数。

Boccassi 快速翻过了一张关于 systemd 过去一年左右持续集成变更的幻灯片。他指出，项目为 ARMv7 架构增加了更多测试覆盖，并为 RISC-V 增加了构建测试。“不是单元测试，只是构建测试，因为模拟运行仍然太慢。希望将来会有所改善。”

项目还增加了一项能力，允许维护者使用 Open Build Service（OBS）基于某个 pull request 构建 systemd 软件包。“这很有用，比如有人提交了 issue 但并非技术人员，那么其他人可以开一个 PR，然后告诉他们：‘嘿，去安装这个 PR 专属仓库里的这些软件包’，然后他们就可以进行测试。”项目还继续通过 OBS 提供来自其主分支或最新稳定版本的最新软件包，覆盖 Arch Linux、Debian、Fedora、openSUSE 和 Ubuntu。

安全

德国的 Sovereign Tech Agency（STA）在 2025 年向 systemd 项目授予了一笔近 40 万欧元的委托，用于改进其安全性和基础设施。Boccassi 说，这项委托的部分重点是帮助改进 GNOME 与 systemd 管理的家目录之间的集成，改进 systemd OS 安装器，以及 systemd 的 system-update 服务。他没有详细介绍这些特性，但 Julian Sparber 确实就 systemd OS 安装器做了一场演讲，Dhanuka Warusadura 则介绍了由 STA 资助的扩展 systemd-homed 的工作。

STA 还通过 YesWeHack 平台资助了一个安全漏洞赏金计划。Boccassi 说，项目不得不对该计划关闭新提交，“因为提交实在太多，分类处理人员根本没有时间处理它们”。他希望很快能重新开放提交。同样，报告的涌入也是 LLM 辅助漏洞挖掘所致；他说结果“不太理想”。共收到 183 份报告，其中只有 13 份被接受。总计 168 份因无效、与其他漏洞重复或超出范围而被关闭。演讲进行时还有两份在审查中。项目通过该赏金计划共发放了 21,250 欧元。

他说，systemd 项目最近更新了其安全策略，更倾向于通过 GitHub 上的一项流程接收安全报告。他说，systemd 已经通过 GitHub 收到 62 份报告，并发布了 15 份安全公告。“这里的信噪比更好。我猜是因为这样做拿不到钱。”

此外，systemd 于 6 月正式成为 CVE 编号权威机构（CNA）；他说，从那时起它已发布了两个 CVE，并拒绝了一个。Boccassi 解释说，systemd 只会为“真正高优先级的问题”发布 CVE。一旦发布 CVE，“所有下游都得手忙脚乱地做大量工作”，因此项目只会在漏洞被认为属于高危且确有必要时才会发布 CVE。

发布亮点

Boccassi 说，他会快速介绍过去一年 systemd 版本中的一些有趣特性，不过他建议关注 Poettering 的 Mastodon 账号上关于 systemd 版本的帖子。在 systemd v259 中，项目将其大部分运行时依赖改为使用 dlopen() 而非显式共享库链接，并在 v260 中完成了依赖转换工作。Boccassi 说，systemd 现在只直接依赖 GNU C 库。“我们不再有固定的、链接进来的依赖。我们仍有 20 多个可选依赖，它们都只在运行时当某个特性真正需要时才会（被打开）。”这意味着发行版可以编译所有带外部依赖的可选特性，而默认不会得到一个庞大的 systemd 二进制文件。“所以你可以拥有一个全功能的单一构建，然后在你的镜像中决定要不要包含那些库。”他说，这对安全也很重要，他指的是库链接在 XZ 后门事件中所起的作用。

Boccassi 指出，De Meyer 在 systemd v259 中为 run0 命令（sudo 的替代品）添加了 --empower 选项。他解释说，该选项允许用户将权限提升为“接近 root，几乎是 root，但不是 UID 0”。这意味着用户可以以 root 的权限运行进程，但文件会以用户自己的 UID 和 GID 创建。他还把另一项特性归功于 De Meyer：该特性允许运行 systemd-machined 的每用户实例，使非特权用户能够使用 systemd 运行虚拟机和容器。

Varlink 是一种进程间通信（IPC）协议，作为 D-Bus 的替代方案。LWN 曾在 2018 年（即它公布后不久）报道过 varlink。在 v260 中，systemd 添加了 varlink 注册表，用于发现系统上有哪些支持 varlink 的服务可用。Poettering 在 v260 发布前曾在 Mastodon 上更详细地描述过这个注册表。Boccassi 还提到了 v260 中新增的 metrics 和 reports 子系统，用于从系统中提取带签名的报告。

systemd 在 v261 中添加了 systemd-imds，用于支持从云服务商的实例元数据服务（IMDS）获取数据。Boccassi 说，这基本上是 systemd 对 cloud-init 的替代，后者一直是云端实例初始配置的标准工具。“似乎没有人喜欢 cloud-init，所以我们现在有了它的替代品。”

在 v262 中，Boccassi 添加了一个他渴望已久的功能：一次入队多个作业的能力。在此版本之前，如果用户用如下命令启动多个作业：

# systemctl start a.service b.service

将会产生两次 EnqueueUnitJob() D-Bus IPC 调用，从而可能导致“一组竞态条件和各种糟糕的问题”。在 v262 中，systemd 为 D-Bus 和 varlink 提供了 EnqueueUnitJobMany() API。“这让你可以在单次 IPC 调用中入队任意数量的作业，从而可以启动、停止或重启任意数量的单元，并保证它们在管理器中属于同一个事务。”

问答环节

Boccassi 没有在 systemd 现状演讲中接受提问，而是建议听众利用紧随其后的维护者圆桌环节。该环节的第一个问题是：维护者是否考虑过将 systemd 扩展为 Kubernetes 的替代品，让它不仅管理本地系统上的作业，还管理远程系统。

Poettering 说，他认为 systemd 并不适合做这件事。“我认为 systemd 从本质上说是管理节点的东西。它不是编排节点的东西。”他补充说，systemd-report 是编排器充分了解系统状态并据此做出决策的一种途径，但他认为编排不属于 systemd。“让这一切成为可能并提供合适的工具，这是 systemd 的职责。但编排器——调度之类的事情——我认为那不是 systemd 的事。”

另一位听众不想谈 systemd 扩展职责取代 Kubernetes 的话题，而是想谈谈规模限制：“我来自嵌入式领域，在那里每一字节的闪存都贵如黄金。我们看到每个 systemd 版本的闪存占用都在增加。你们在开发新（特性）时会考虑这一点吗？”

Jędrzejewski-Szmek 认为 systemd 在这方面做得相当不错：“诚然 systemd 的代码在增长，但我们在让依赖变为可选项方面做得好得多，而那些依赖实际上比 systemd 本身还要大。”Poettering 说，保持 systemd 的占用空间很小很重要，这也是为什么用 Rust 编写 systemd 会很复杂，因为 Rust 生态缺乏一种“尝试让依赖是动态的、可选的、能优雅降级的，而不是把所有东西都塞进一个庞大的二进制文件里、要求所有人编译所有东西”的理念。他和 Boccassi 举了一些近期特性的例子，比如 systemd-report 和 systemd-imds，它们都是完全可选的。如果不启用，就不会在占用空间上付出任何代价。

另一位听众延续了占用空间不断增长的话题，并指出随着 systemd 不断增加各种工具，“它真的正在变成一个生态系统”。他想知道何时才算够。“我们不断地加、加、加，以至于现在 systemd 能做——我都不知道——Kubernetes 和各种各样的事情”。Boccassi 回应道：“我认为只要没人拿走 Lennart 的 GitHub 账号，我们就会继续加下去。”

Poettering 说，这是一个绝对合理的问题，而且从第一天起就是如此。“我们在哪里画线？坦率地说，这条线已经移动过了。但如果你现在问我，那就是让一个节点保持运行的最基本的东西。但生活中一个简单的事实是，这些基本的东西本身在变化，对吧？”他提到了平台完整性；他说，十年前这还不是个事。而现在，它“对操作系统设计来说是绝对根本性的”，而且他想不出还能在哪里实现它。

经过一番讨论和相互插话之后，他补充说，同样的问题也适用于 Linux 内核和其他项目。“如今的内核仓库里也有用户空间工具之类的东西，对吧？到哪里是个头？又从哪里开始？我们有一个大致的概念，但这个大致的概念会随时间改变，对吧？”

围绕 systemd 职责范围这一主题继续下去，有人提出了关于项目维护 systemd 各个组件能力的问题。“你们是否看到某些组件特别缺乏维护者，而另一些组件在审查等方面维护和支持得好得多？”Poettering 说，项目倾向于给 systemd 添加特性的原因之一是维护会因此变得更容易。“如果我们修复某个跨多个模块的损坏问题，我们往往会一路修补那些模块来更新它们”。他补充说，systemd 治理文档为项目的少数几个组件指定了维护者，其余的一切“基本上人人都是维护者”。

他承认，有些领域受到的关注多些或少些，因为优先级会随时间变化。Poettering 是 Amutable 的联合创始人，该公司于今年 1 月宣布成立，所以他的重心是这家公司需要的东西。“而那些也许我们不需要的东西就不那么（受关注）”。他提到 SELinux 支持是 systemd 中“非常缺乏支持”的领域，不过 Boccassi 指出，最近有 Red Hat 的人发送了与 SELinux 相关的 pull request。此时环节时间已到。Boccassi 说，他感到失望的是没有人明确问到 AI 或 Rust，环节就此结束。

在 Rust 代码中接管 C 类型

作者：Daroc Alden 2026年10月13日 英文原文

当 Rust 的所有权与借用引用体系能够正确建模程序的需求时，它会非常方便。Rust for Linux 项目一直致力于在 Rust 的语义与内核中现有的 C 代码之间提供适配器。在 Kangrejos 2026 上，Andreas Hindborg 谈论了一个实现下一个此类适配器的补丁系列：一个用于表示由 C 代码分配、但由 Rust 代码负责在使用完毕后清理（不一定是释放）的对象的 Ownable trait。他希望在邮件列表上讨论数月之后，最终能就这一补丁系列达成共识。

在 Hindborg 主要工作的 block 子系统中，有一个专门用于处理并发请求的内存池。每个 I/O 请求由一个 bio 结构表示。要发起新的请求，block 层会在池中找到一个未使用的结构，填入请求的细节，然后将其传递给相应的驱动。驱动处理请求，清空请求结构，再传回 block 层以便复用。这一设计避免了为每个请求不断进行分配和释放的开销，但它也与内核 Rust 代码中现有的抽象并不完全契合。

最接近的两种抽象是 KBox 和 ARef 类型。前者不适合这种情况，因为它假定分配是在 Rust 代码内部进行的。后者也不合适，因为它假定对象总是被引用计数的，而对 I/O 请求而言情况并非总是如此。因此，Hindborg 想要添加一个名为 Owned 的新智能指针，它在概念上表现得像 KBox，即提供对所指向值的独占访问，但不会在生命周期结束时尝试释放内存。相反，Owned 指针会调用一个特殊的 release() 函数，该函数可以执行诸如将底层内存归还给特定子系统内存池之类的操作。Owned 指针只能指向实现了 Ownable trait 的 C 类型，以确保它们只用于拥有有意义的 release() 函数的类型。

复杂性来自于让 Owned 与内核中现有的 Rust 抽象集成。例如，如果一个引用计数类型的引用计数为一，那么理论上持有 ARef 的 Rust 代码可以知道不存在其他引用，因此转换为 Owned 指针应当是安全的。当一个类型既可被独占拥有又可被引用计数时，反过来把 Owned 指针转换为 ARef 也说得通。如果该操作消耗掉 Owned 指针，那将是健全（sound）的。

问题在于，目前已经允许用 Owned 指针产生内建引用。此外，把内建引用转换为 ARef 指针也是允许的，因为如果 Rust 代码设法获得了一个对引用计数类型的引用，那么引用计数必定至少为一。综合来看，这些特性会导致不健全性。如果用 Owned 指针产生了一个内建引用，再用该引用创建一个 ARef，然后继续用 Owned 指针修改底层条目，就可能造成并发修改。

Hindborg 说，内核中的一些用户对保留将内建引用升级为 ARef 指针的现有行为态度坚决。他认为他们本可以修改自己的 API 使其直接接受 ARef，那样会更简单，但他们一直不愿采取这种做法。作为折中，他建议将现有的 AlwaysRefCounted trait（它告诉编译器 C 类型可以放在 ARef 之下）拆分为两个更小的 trait。其中一个使类型能够与 ARef 一起使用，另一个则允许把内建引用转换为 ARef 指针。对同时实现了 Ownable 的类型实现后者将被禁止。

在 Hindborg 为 block 层提出的 Rust 绑定中，一个 I/O 请求可能处于四种状态：由 block 层拥有、由驱动拥有、在驱动的多个部分之间共享，以及被驱动停放（parked）。当 block 层向 Rust 编写的驱动发送请求时，绑定会传递一个指向该请求的 Owned 指针；将请求标记为结束则需要传回一个。这样，block 层的 Rust 代码就可以确信驱动没有在内部保留任何引用。

他展示了一幅完整状态机的示意图，由于可能存在多个共享指针，或者依赖于驱动内部的硬件标签，这个状态机变得更加复杂。归根结底，他的目标是产出一个驱动程序只能正确使用的接口。

他认为，其他子系统也可以利用 Owned 抽象。IOMMU 页表和 Rust binder 驱动都可以使用它。他曾讨论过将其用于 GPUVM，但随后认定它并不合适。随后，Alice Ryhl 和 Hindborg 就能否使其适合 GPUVM 展开了反复讨论，最终得出的结论是，所需的更改可以在 Hindborg 的补丁系列合并之后再行添加。Boqun Feng 不同意将其扩展以支持 GPUVM 是可取之举。Greg Kroah-Hartman 则认为 USB 驱动也可能用得上 Owned。

Hindborg 的一个疑问是，围绕 page 结构的 Rust 包装类型实现 Ownable 是否合理。这无法简单地做到，因为 Rust binder 代码依赖于能够把指向 page 的内建引用升级为 ARef 指针。之所以需要这样做，是因为 Rust binder 代码会把引用传递给 vm_insert_page()，而后者会增加 page 上的引用计数。Hindborg 问 Ryhl，能否修改 vm_insert_page() 的 Rust 绑定，以消除传递内建引用的必要。Ryhl 认为不行，她指出，一般而言，代码增加 page 的引用计数是可以接受的做法，因此解决这一个案例并不能使 page 实现 Ownable 变得安全。

Kent Overstreet 补充说，page 的引用计数是一个微妙的话题，原因在于它与 splice() 系统调用的交互。在受邀详述时，他解释说，是否可以更改引用计数可能因 page 而异。此外，向 folio 的过渡使这部分代码复杂化，因为现在必须区分 head page 和 tail page。

Gary Guo 想知道 Hindborg 究竟为什么想要使用拥有型（owned）的 page 结构；他认为，能够编辑 page 结构与能够直接编辑 page 中的内存之间存在区别，而且遗憾的是，代码的不同部分对什么是允许的有各自的假设。Hindborg 表示，他感兴趣的是修改 page 的数据内容，但他认为这是能够修改 page 结构本身这一问题的一个子问题。Feng 指出，内存管理维护者希望推动开发者使用 folio，并避免把 page 暴露给任何新用户。因此，是否以这种方式把 page 暴露给 Rust 代码，更多是一场应当让内存管理维护者参与的 API 讨论，而非一个可以在 Rust 侧单独解决的正确性问题。

Hindborg 说，这个补丁系列自 2025 年初以来一直在推进，如今已是第二十二个版本。由于人们要求做出不同的修改，实现工作一直在原地打转。到了这一步，Hindborg 只想看到达成某种共识。"所以拜托了。让我们齐心协力。我们能做到的。"

Miguel Ojeda 提到，在内核中，审查互换（review swaps）常常是可行的，即两个人互相交换对彼此工作的审查。Hindborg 立即表示同意，说："I am absolutely for sale."（我完全可以被"收买"。）希望这意味着 Hindborg 的补丁集很快就会被审查，并有可能被合并。

与树外追踪器协作：LTTng 的上游化困境

作者：Jake Edge 2026年10月14日 英文原文

与树外追踪器协作

LTTng 的创造者 Mathieu Desnoyers 似乎多少陷入了一种两难困境（catch-22）。在 2026 年 Linux Plumbers Conference（LPC）上，他主持了一场讨论，谈的是他在尝试与内核中的其他追踪项目（例如 ftrace、perf）协作时遇到的问题。无论是这些年来还是最近，他得到的反馈都没有显示出一条能让他把已有 21 年历史、采用 GPLv2 许可证的 LTTng 追踪框架——或者以渐进方式将其中的特性——贡献进主线内核的路径。

ftrace 的创造者（也是本次追踪议题的组织者）Steven Rostedt 在听众的笑声中将这场讨论介绍为"今天争议性最小的话题"。Desnoyers 说，他从 2005 年起就一直在维护 LTTng，想探讨"我们如何能改善树外追踪器项目的开发者与上游内核之间的协作"。他表示希望这场讨论是一次讨论而非报告，所以只准备了两张幻灯片。

他指出，如果转述核心内核开发者对追踪器的看法，那就是：追踪器应该属于内核本身，而不是作为模块加载进内核；这些年来他一再被告知这一点。他说，ftrace 和 perf 都位于核心内核中，并且无法构建为模块。

随后他引用了 Linus Torvalds 2025 年 7 月一封回复 Desnoyers 关于将 LTTng 上游化的 RFC 的邮件："如果人们需要两种追踪模型，那么另一种就留在树外。就这么简单。"Torvalds 在同一封邮件中还说道：

就我而言，这场讨论根本算不上讨论。要么存在借助共享（SHARED）基础设施渐进合并的道路，要么就不存在。

Desnoyers 说，这些约束叠加在一起，让 LTTng 项目陷入了棘手的境地。如果不能使用它贡献给主线的任何特性，那么项目继续留在树外反而更有效率。按照当前的内核准则，新特性不能被导出给内核模块使用，除非主线中已有模块在用它们。LTTng 有一套用户喜欢并希望其延续下去的特性集；理想情况下，LTTng 的特性会被逐步加入内核，直到全部上游化。

Desnoyers 指出，正如 Torvalds 所说，实现这一目标的路径是渐进式的。"这意味着把 LTTng 模块的一部分一块一块地推进上游追踪器中，直到我们达到特性完备。"这可以先说服上游追踪维护者相信这些特性对他们的用例有用来实现，但如果项目成功地做到了这一点，它得到的回报却是要同时维护树内和树外的代码。

这份额外的维护负担会一直持续到 LTTng 用户需要的所有特性都上游化为止，而这可能需要相当长的时间。另一种选择是放宽"所有追踪器都必须内置于内核"的要求。如果内核开发社区愿意承认存在开发者想要协作的树外追踪器，并允许添加那些被导出（通过 EXPORT_SYMBOL_GPL()）以便那些可能构建为内核模块的追踪器能够使用的特性："那么我们就可以拥有共享的基础设施，然后我们就可以把 LTTng 模块的部件移除出来并渐进地上游化。"

目前，存在一条禁令：不允许导出没有内核内使用者的符号。即使 LTTng 开发者成功说服了其他追踪维护者相信其某些特性的价值，LTTng 继续使用它们所需的钩子也不会可用。把 LTTng 作为全有或全无的补丁集整体上游化或许也行得通，但 Torvalds 对此的立场非常明确。两难困境。

协作

"我对此也有点恼火"，Rostedt 说。他多年来一直在主线内核中与 Desnoyers 就各种追踪功能展开合作；他们在这方面有过相当多的协作。LTTng 中有一些他希望 ftrace 也拥有的特性，但存在一种"严格的——我称之为'苛酷的'——态度"，即除非符号在内核树中有使用者，否则不应导出。Christoph Hellwig 是反对任何导出（即使是面向 GPL 覆盖的代码）的"最大推手"，除非有内核内的使用者。

Rostedt 说，他在 5 月的 LSFMM+BPF 上与 Hellwig 讨论过这个问题，但 Hellwig 坚持认为，除非树内内核模块中的某些代码使用这些符号，否则不应导出。Rostedt 说，这意味着内核项目并不寻求协作。"不如干脆说'Linux 不支持开源，Linux 不支持协作'"。如果内核项目要对一个背后有资深内核开发者的 GPL 覆盖项目抱有敌意，那么项目就应该明确其意图。他指出，Desnoyers 是 tracepoints（跟踪点）的开发者，而 tracepoints 遍布整个内核追踪生态系统；如果内核开发者找不到纳入像 LTTng 这类项目的方法，内核项目就应该直截了当、明确无误地说出来。

他不理解禁止为像 LTTng 这样的模块导出符号背后的理由。他曾希望 Hellwig 会来参加这场讨论，也邀请了他，但 Hellwig 没有到场。"他应该来的"，Rostedt 说。

一位与会者说，他总体上同意扩大导出范围，但担心这会创建出需要永远维护的新接口。Rostedt 立刻指出，内核模块接口不是用户空间接口，即使其他人开始使用它，也不需要维护它。Desnoyers 说，作为一个树外追踪项目，LTTng 多年来已经变得擅长适应这种接口的变化。"我们只需要一个基本的保证：人们不会主动破坏我们正在努力做的事情，并且当我们贡献某部分基础设施时，我们能够使用它。"

另一位与会者想知道 LTTng 可能为内核基础设施贡献些什么。Desnoyers 指出，过去两年他一直在为内核开发 SFrame 支持；Rostedt 说，即使它进入内核，也不会有符号被导出，因此 LTTng 将无法用它来展开（unwind）栈。

Rostedt 说，曾有一度，有人准备了一个提议把 LTTng 加入内核的补丁，但因为 Torvalds 反对功能重复而不了了之。LTTng 无法访问内核内部，只能使用导出的符号，因此它不得不自行实现 ftrace 和其他内核内组件可以直接使用的大部分基础设施。所以，实际上，导出的缺乏导致 LTTng 重复实现了功能，而且往往以自己的方式实现。Torvalds 认为，既然 LTTng 与内核内追踪器之间的统一在过去的 20 年里从未发生，那么它永远也不会发生。Rostedt 反驳说，未能统一的部分原因恰恰是 LTTng 与内核之间从来无法共享代码。

模块

Desnoyers 说，他对问题的表述稍有不同。LTTng 所需的符号可以被导出供内核自测（self tests）使用，LTTng 随后也能使用它们。他说，真正的约束在于内核追踪器不能构建为内核模块，因为那会妨碍为自测导出符号；那些测试实际上就相当于内核追踪模块。

Rostedt 说，问题的另一部分在于 LTTng 关注的用例与内核内追踪工具完全不同。多年来，追踪器之间发生过"环形缓冲区战争"，试图找到"一个能解决一切的环形缓冲区"，但追踪社区发现存在"许多不同的用例"，它们有着"略微不同的需求"，这就导致了多个环形缓冲区实现的存在。人们很容易认为内核只需要一个环形缓冲区实现，"但一旦你真正深入到那些棘手的细节中，就会发现并非如此"。

Brendan Gregg 说，他没有研究过 LTTng，唯一的原因就是没有时间，但这种情况可能会改变。他越来越发现，要获得行为异常系统的 SSH 访问权限变得越来越困难，因此他正在关注 LTTng 中那些无需这种访问权限就能帮助诊断问题的特性。我在讨论结束后与 Desnoyers 通了邮件询问这些特性；他说他的用户常常把追踪器设置为一直运行，并配备触发器来捕捉（并导出）追踪数据的快照。对 SSH 加以限制通常针对存有敏感数据（比如用户的个人身份信息 PII）的服务器，而这正是 Gregg 如今越来越常遇到的情况。

在 LPC 的讨论中，Desnoyers 说 LTTng 的重点一直是内核与用户空间相关联的追踪，以及在检测到错误时对追踪数据进行快照和导出的能力。例如，电信公司就在光纤网络的路由器上以这种方式使用它。Rostedt 说，Torvalds 曾告诉他没有人真正想要这些追踪特性，但 Rostedt 反驳了这一点。他指出，Torvalds 基本不参加大会，但如果他参加，就会发现很多人想要追踪和新的追踪特性，而不只是 Torvalds 所说的"你和你的小团体"。用户群体相当庞大，Rostedt 说，"基本上就是 Open Source Summit 上的所有人"。

在某种程度上，Torvalds"活在自己的小茧房里"，Rostedt 说；他需要与 LPC 或其他大会上的与会者交流，以更好地理解人们如何使用他的内核。Rostedt 说，Hellwig 确实参加一些大会，"但他不在这个房间里，而我请过他来"。他问道："当他们连讨论都不想进行时，你怎么让对话进行下去？"他说，如果找不到解决这些问题的办法，那么内核应该宣布自己"对外部项目怀有敌意"——这是很重的措辞，但准确地反映了他的感受。

内核 / 内存管理

[vx]swap 对决

作者：Jonathan Corbet 2026年10月8日 英文原文

过去一年里，内核的交换（swap）层经历了多项重大变革，许多长期存在的问题得到了解决。但主线中尚未解决的一个问题，是 swap 缓存中的槽位与持久 swap 文件中的空间之间的直接绑定，这会导致资源利用率极为低下。目前有两种相互竞争的解决方案，但都尚未达到可合并的成熟度；一场关于前进道路的漫长讨论表明，人们对最佳路径仍存在分歧。

内核的 zswap 层凸显了 swap 子系统当前设计中的困难之处。Zswap 会拦截即将被换出到 swap 文件的 folio，并不将其写入该文件，而是压缩其内容并把结果存储在 RAM 中。它本质上是一种用一些 CPU 时间换取更多空闲内存的方式，同时让数据保持就近可用，并将磁盘 I/O 降到最低。随着当前工作负载的演变，zswap 的使用越来越流行。

问题在于，存储在 zswap 中的每个 folio 仍然必须在某个持久 swap 设备上分配一个槽位。如果 zswap 区域溢出，folio 可能会被刷出到它们被分配的（持久）槽位，但通常的意图是不让这种情况发生。所以，大多数时候，那些存储空间完全被浪费了。然而，若要使用 zswap，这些空间又必须存在。这个问题在大型数据中心似乎尤为棘手：在那里，海量的闪存存储必须专门用于存放“空无一物”。

Nhat Pham 提出的解决方案之一是 vswap，LWN 此前曾撰文介绍过。Vswap 在现有 swap 设备之上增加了一个新的虚拟化层；当 folio 被加入 swap 缓存时，它会被分配到这个虚拟层中的一个槽位。该槽位随后可以映射到多个不同的位置，包括任意物理 swap 文件中的槽位、zswap 中的槽位，或者对于只包含零的页，干脆不映射任何槽位。Folio 可以在保留其虚拟槽位的情况下在不同后备设备之间移动，这使得把 folio 从 zswap 刷出，或在移除 swap 文件之前将其撤离变得容易。这项工作使用 xarray 数据结构来跟踪槽位。随着 swap 底层在其之下不断变化，这项工作经历了大量修订；vswap 最后一次发布是在 9 月中旬。

另一个方案是 Baoquan He 和 Chris Li 的 xswap。在其 9 月中旬的形态中（此后已更新），xswap 可以被看作是一个实际上没有任何后备存储的虚拟 swap 设备。向 xswap 设备写入 folio 的尝试不会成功，因此该设备实际上无法存储任何数据。它能做的，是为存储在 zswap 中的 folio 提供“物理”swap 槽位。在一个把 xswap 配置为唯一 swap 设备的系统上，folio 可以存储在 zswap 中而无需任何物理存储。Xswap 使用稀疏映射的地址范围来存放其管理数据，在 swap 使用率较低时将其内存占用降到最低。

9 月初，已经为 vswap 工作了一年多的 Pham 发表了一个长篇询问，询问虚拟化 swap 层的工作应当如何推进。他总结了 vswap 和 xswap 两项工作，并指出两个项目各有优势。例如他说，xswap 使用的稀疏映射管理数据结构也许比他为 vswap 使用的 xarray 更有吸引力。

Pham 建议，两个项目的部分内容最终都可以合并，由此引出了哪个应该先合入的问题。也许并不令人意外，他建议 vswap 应先于 xswap 合入；他表示，后者基本上可以看作是一种优化，可以在 vswap 的主要设计元素就位之后再采用。

同样不令人意外的是，xswap 的开发者们认为先合并 xswap 更为合理。“VM_SPARSE 数组不是日后可以加装上去的优化；它是一种结构性选择，代码也体现了这一点”。He 说，如果先合入 vswap，其基于 xarray 的数据结构最终将不得不被 xswap 的实现所取代。与其添加 vswap 带来的额外复杂性随后又将其移除，不如先添加 xswap 这个相对简单的“地基”。Kairui Song 至今完成了大量 swap 现代化工作，他附和了其中一些论点。

虽然在随后的大规模讨论中没有做出任何决定，但很快就可以明显看出，支持 xswap 的呼声并不高涨。xswap 缺少一种将 folio 从 zswap 写回到物理 swap 设备的方法，这被视为一个严重的缺陷，而 vswap 并不存在这个问题。不过，最具争议的问题源于作为 xswap 底层核心“结构性选择”的稀疏映射管理区域。

具体来说，该区域要求在一开始就预留完整的地址空间；这进而为 xswap 设备设定了最大尺寸，从而也限定了可存储在 zswap 中的 folio 数量上限。而 vswap 呈现的 swap 区域大小则可以随工作负载的需要动态增长或收缩。Johannes Weiner 认为，要求管理员来设定 swap 区域的大小从根本上是错误的；zswap 中能存下多少内存，很大程度上取决于其压缩效果，而这又取决于工作负载。他说，管理员无法知道合适的大小是多少，内核也没有理由在已经存在的内存使用控制之外再施加额外限制。

讨论的这一部分持续了一段时间，并逐渐变得清晰：应用于 swap 空间的限制（无论在设备尺寸上还是在控制组中）正被以不同且有些互相矛盾的方式使用。一些站点用这些限制来约束进程的最大虚拟尺寸，而另一些站点则专门关心物理 swap 空间的使用控制。在前一种情况下，将 zswap 页计入限制是合理的；在后一种情况下则不然。一旦 zswap 与物理 swap 槽位分离，开发者将不得不决定支持哪种用例，而似乎注定会有人因此不高兴。Gregory Price 的这封邮件较为详细地描述了这种脱节（以及一种可能的解决方案）。

讨论最终逐渐平息，没有得出明确结论。为讨论该问题组织一次电话会议的持续努力尚未取得成功。与此同时，He 发布了一个分为三部分的新 xswap 实现。第 1 部分是如上所述的核心 swap 设备实现，第 2 部分实现了此前版本所缺失的物理回写，第 3 部分实现了对物理 swap 空间使用的统计。到目前为止，唯一的评论来自 Pham 的这封邮件，他对自己的想法被采用却未注明出处感到不满。

在经历多年相对停滞之后，内核 swap 子系统的演进在过去一年里十分迅速。swap 空间的虚拟化是合乎逻辑的下一步，它将解决许多长期存在的问题。但内存管理开发者们会希望确保把这件事做对；他们在未来多年里都要与自己决策的后果共处。即使在没有根本性细节分歧的情况下，内核这一部分的改动往往也需要很长时间才能落地；这一次可能会比往常更久。

KDE Linux 两岁了

作者：Joe Brockmeier 2026年10月13日 英文原文

KDE Linux 两岁了

KDE Linux 是 KDE 项目第二次尝试创建自己的发行版，2024 年由 Harald Sitter 在 Akademy 大会上以"Project Banana"之名首次亮相。Nate Graham 在 Akademy 2025 期间宣布了第一个 alpha 质量的版本。Graham 和 Sitter 在 Akademy 2026 上联手介绍了项目的进展，阐述了根据用户反馈完善该发行版的计划，并讨论了一些仍需解决的问题。KDE Linux 还没有完全做好大范围应用的准备，但 Graham 希望它能很快适合广泛使用——至于"很快"是多久，尚未定义。

我今年确实参加了 Akademy，但没能旁听 Graham 和 Sitter 的演讲，因为它与我计划参加的另一场演示安排在同一时间；于是我在回家后观看了这场演讲的视频，并对照幻灯片阅读。我还得以审看几周后举行的 2026 All Systems Go! 大会上 Sitter 的"KDE Linux Under the Hood"演讲的视频和幻灯片。本文也收入了那场演讲中的一些细节。

生机勃勃

Graham 在 Akademy 演讲开始时开玩笑说项目已经被取消。"我们现在都去看 AI 演讲吧。"他随即向听众保证，项目生机勃勃、运转良好。Sitter 解释说，KDE Linux 是一个基于镜像的发行版，目前基于 Arch Linux 软件包，KDE 软件通过 kde-builder 工具提供。Sitter 说，Arch Linux 底层并不重要，"将来可能会改变"。

基于 Ubuntu 的 KDE neon 发行版是 KDE 首次尝试用发行版来展示 KDE 软件。它的状态有些不明朗；恰好有足够多的存活迹象，令人困惑。构建版本仍在继续发布，但不那么频繁了。KDE neon 开发者博客自 2025 年 10 月以来没有更新；其论坛上也有关于更新的未获回应的问题，比如它何时（或是否）会针对 Ubuntu 26.04 LTS 版本进行更新。不过，除了 Graham 顺带提到过一次 neon 之外，关于 KDE Linux 的演讲并没有谈及 neon 的状态。

Graham 指出，在已有如此多发行版的情况下再造一个 Linux 发行版，看起来可能有点傻；然而，KDE 希望与用户建立"少一些中间人"的直接关系。他说，这从 neon 开始，"而我们现在用 KDE Linux 把它延续下去"。KDE Linux 的另一个理由是展示"一个真正出色的原生 Plasma 体验是什么样子，不需要大量补丁和五花八门的壁纸之类的东西"。

KDE 的开发工作也是创建该发行版的动机之一。Graham 说，它被设计成一个开发 KDE 软件的绝佳平台，而这个发行版作为"对所有东西的一次巨大的全栈集成测试"也很有用。这惠及"栈的上下各处"的 KDE 应用和其他项目。例如，该发行版大量使用 Flatpak；对 Flatpak 的任何改进也会使其他使用 Flatpak 的发行版和项目受益。

"从策略角度讲，我们可以推荐 KDE Linux，而不必在潜在赞助方中挑肥拣瘦，那会很尴尬。"最后他说，如果 KDE Linux 足够好，"它有望抬高其他操作系统的水准，让它们能从我们所做的东西中学习，就像我们从它们所做的东西中学习一样"。

Graham 认为是时候回答某些人心中可能存在的问题了：KDE Linux 是否意在取代或消灭其他发行版？不，不是的。"我们可以构建一个操作系统，同时也支持其他人构建他们的操作系统，而且我们真的可以相处融洽，我觉得这非常酷，因为我们不是在竞争，而是在互相学习"。KDE Linux 继承其他发行版已完成的工作，也正在分享它自己的工作供他人借鉴。

反馈

自去年发布以来，KDE Linux 项目收到了用户关于他们喜欢什么——以及不喜欢什么的反馈。Graham 从正面说起。例如，用户喜欢该发行版带有回滚功能这一事实。他说这对用户来说是"一张不可思议的安全网"，让他们确信如果更新出了问题，可以把系统恢复到可用状态。他觉得奇怪的是，到了 2026 年，回滚竟然还没有成为操作系统的普遍功能，尤其考虑到实现这一功能的方法有很多。"显然，我们有这个技术。如果要我向所有其他发行商推销一件事，那就是：请以某种方式集成操作系统回滚。"

同样，他大力称赞了使用基于镜像的更新系统的好处。"你不会遇到基于软件包的发行版上那些奇怪的问题：装了某个东西就会出现软件包冲突，更新拖太久就会出现过期的软件仓库。这些问题在这里不存在。"用户还喜欢 8 月集成进该发行版的针对家目录的 Btrfs 快照功能。这让用户即使没有外部备份，也能轻松把文件回滚到旧版本。Graham 说这是防止误删除和误修改的一张安全网，但也承认该系统仍有"一些怪癖"（不过他没有细说）。KDE Linux 还内置了 Kup，一个面向用户文件的备份系统。

Graham 还谈到了用 Flatpak 发布应用的优势，比如管理 Flatpak 的便利性。"最重要的一点是，你可以放心大胆地安装和卸载它们。绝不存在这样的危险：装个 Steam 或卸载它的时候，不小心把整个操作系统给删了——纯属假设的例子。"KDE 的软件管理应用 Discover"以合理而连贯的方式呈现软件"。它提供了一个统一的应用来安装 Flatpak、KDE Plasma 的附加组件以及操作系统更新。"一切都是连贯的。一切都很好。应用以应用的形式展示。操作系统更新以操作系统更新的形式展示。东西很容易找到。一切运行得非常好。"

抱怨

当然，用户也有抱怨。Graham 说，最大的抱怨是 KDE Linux 没有软件包管理器。虽然他称赞了 Flatpak 的好处，但他承认，缺少软件包管理器对更技术型的用户来说是个问题。如果开发者想要一个命令行工具或"随便某个构建依赖"，事情就变复杂了。这导致失去了一些可能帮助改进 KDE Linux 的用户，因为他们发现绕过软件包管理器的缺失实在令人沮丧。

Sitter 补充说，还有一些与"内核关系紧密"的 GUI 应用，比如 VirtualBox，不容易打包成 Flatpak。他说，目前没有官方支持来创建需要树外内核模块的 Flatpak，不过他暗示自己正在为这种场景做一个原型。

事实上，许多抱怨似乎都集中在 Flatpak 的局限上。Graham 一口气数出了好几个问题，比如限制性的沙盒权限、缺少"与宿主系统的深度集成"、Flatpak 应用的主题化问题，以及其他痛点。"我们必须现在就修复这些问题，而不是提供一个让这些问题永远蛰伏下去的逃生舱口（比如原生软件包管理器）。"他希望 KDE Linux 用户遇到的某些问题能由正在开发中的 Flatpak 下一个大版本解决。

无关紧要的东西

Graham 说，他和 Sitter 曾预期 KDE Linux 的某些方面或局限会对用户很重要，但实际上并非如此——或者至少没有他们预期的那么重要。例如，关于打印和打印机驱动程序的反馈很少，而这对基于镜像的系统来说可能是个棘手的问题。Sitter 观察说，"人们并没有那么频繁地打印"，并说自己已记不清上一次在家里打印东西是什么时候。

Sitter 原以为较旧 NVIDIA GPU 的驱动程序会是更重要的议题，那些驱动需要他称之为"有点可疑"的专有内核模块。然而，他推断关于缺少旧驱动程序的反馈之所以很少，是因为开源的 Nouveau 驱动程序大概已经足够好，除了那些在意高性能图形的人。"如果你在意任何形式或方式的性能，那你很可能反正都在用最新的（硬件）。"老旧硬件最终也会消失："所以我希望能拖得足够久，久到不必解决这个问题，尽管我手上已经有一个原型。"

KDE Linux 目前使用 zram 作为交换空间。Graham 说这"主要是出于懒惰"，因为 systemd 的 zram-generator 让设置基于 zram 的交换空间变得很容易。Zram"就像一个内存翻倍器"，它压缩物理 RAM 上的内存并将其用作交换空间。问题在于，他说，"一旦（内存）用光了，就是用光了"，然后内核就开始杀掉应用。"我们原以为这会是个大问题，但坦率说，它没那么糟。"计划是最终迁移到 zswap，但"需求基本上没有我们预想的那么迫切。事实证明 zram 其实挺好"。作为 GNOME 生态系统的类似展示性发行版，GNOME OS 已于 9 月迁移到了 zswap。

Graham 说，总的趋势是，有几个"我们预期会存在的痛点，但它们并不存在……结果它们对少数人来说只是中等或小程度的问题"。由于 KDE Linux 项目的资源有限，大家决定"暂时不去追求这些微优化"。目前，重点是让 KDE Linux 对用户和开发者可用。

架构

Sitter 精神一振，宣布"哦，轮到我的部分了——技术黑话"，然后开始谈论 KDE Linux 的架构。他说，基础操作系统可以是任何发行版；现在是 Arch Linux，但也可以是 Fedora，或者项目可以用 Apache BuildStream 来组装发行版。KDE Linux 使用 Btrfs，并且默认开启快照。Sitter 说，选择 Btrfs 的原因显而易见："它是写时复制的，有快照，有配额，有压缩，它有你在现代文件系统中想要的一切，对吧？"此时一位听众大声嚷了些什么关于性能的事。Sitter 回答说，Btrfs 的性能"对普通用户来说完全没问题"。

KDE Linux 上的 /usr 目录是一个只读的 EROFS 文件系统。Sitter 说，选择 EROFS 是因为它在速度与压缩率和体积之间取得了平衡。"所以它在一定程度上既快又小。"他补充说，他认为将来它可能会被用于 Flatpak 镜像和统一内核镜像（UKI）。KDE Linux 会存储多个 EROFS /usr 镜像以便于回滚；目前它被设置为存储四个镜像，为用户提供多个可回滚的选项。在 All Systems Go! 大会上，他澄清说，等发行版成熟之后，数量可能会比这更少。毫无疑问，对存储空间紧张的人来说这将是一个受欢迎的改变（磁盘空间显然短期内不会变便宜）。在我的 KDE Linux 测试系统上，最新的 EROFS 镜像每个约 7.2GB，这意味着一个存有四个镜像的系统将为当前镜像和恢复镜像总共分配近 30GB 的空间。

EROFS 镜像使用 mkosi 创建，这是一个从 Arch Linux、Debian、Fedora 或 openSUSE 构建定制操作系统镜像的工具。Sitter 说，mkosi 也被用来创建 UKI 中的 initrd。Sitter 说，KDE Linux 使用了"一大堆 systemd 服务"。例如，它使用 systemd-repart 创建 EROFS 镜像，使用 systemd-sysupdate 执行系统更新。KDE Linux 还在其系统更新守护进程中使用了 casync（内容可寻址同步）的一个替代实现，叫做 desync。"它是 systemd 与我们的 desync 存储技术之间的一个垫片，用于增量更新"，Sitter 说，它提供了更智能的下载系统。

未来之路？

Sitter 在演讲早期就暗示过用 BuildStream 取代 Arch Linux 作为发行版的基础。他把 BuildStream 描述为与 Yocto Project 类似，后者被用来创建定制的基于 Linux 的系统。他说，切换到 BuildStream"目前正在探索中"，并指出 GNOME OS 已经在使用该项目。切换的理由是"对基础操作系统的完全控制权"。

他说，还有一个由此产生的预期：因为 KDE Linux 目前以 Arch Linux 为基础，"你必须有点像 Arch"，这对 KDE Linux 来说并不成立。"这两者在你如何使用它们上再怎么分离、再怎么不同也不过了。"不制造这种预期将是一个优势。Sitter 说，项目正在考虑 Arm 和 RISC-V 构建，而使用 BuildStream 会更容易做到这一点。

有一件事没有被提及：如果 KDE Linux 切换到使用 BuildStream，项目计划如何处理安全更新之类的事情。通过让 KDE Linux 基于 Arch Linux（或其他发行版），项目同时也继承了该发行版对构成基础系统的软件包所做的安全工作。一旦切换，项目打算如何处理安全报告、更新等，将会是一件值得关注的事。

KDE Linux 仍被视为 alpha 质量，不过 Graham 说他对它有足够的信心，已经在全职使用它："这就是我现在正在用来做演讲的系统，这个 alpha 操作系统，我对它有信心，因为它有操作系统回滚。"但他不愿意给出达到 beta 的预计日期。"我已经学会了不给预估时间。"

对于该发行版距离达到 beta 里程碑还有多远，他确实给出了一个更具体的回答。Graham 说，根据 GitLab 上的里程碑追踪器（Milestone tracker），项目大约完成了到 beta 质量的 85%。"85% 相当不错。众所周知，80-20 法则是真实存在的。所以最后的 20% 要花十年的功夫。"不过，他希望到 beta 不需要十年，并请求大家帮忙推动它达成。

提问

第一个问题关乎 KDE Plasma 桌面（它是基础镜像的一部分）与以 Flatpak 形式发布的 KDE PIM 应用之间的集成。提问的听众说，他喜欢 KDE Linux，但不得不放弃使用它，因为 Flatpak 版本的 KDE PIM 应用与 Plasma 集成得不好。Sitter 开始建议构建自定义镜像，但提问者打断了他："我不想构建它，因为那要花四年。"

Graham 说，正确的答案应该是让 PIM 栈对 Flatpak 更友好，"这也许是一件我们可以寻求外部资金的事情"。Kevin Ottens 前一天与 Graham 一起做过一场关于为 KDE 筹资以实现企业级特性的演讲，他表示让以 Flatpak 形式打包的 KDE PIM 应用工作得更好的工作已经在进行中。

另一位听众想知道，既然有那么多关于聚焦企业的谈论，KDE Linux 是否会有"某种扫描过期软件的东西"，包括依赖在内。Sitter 回答说，迁移到 BuildStream 将为这个问题提供解决方案，因为它可以轻松生成关于软件中 CVE 的报告以及软件物料清单（SBOM）。

最后一个问题是关于移动设备的，因为讨论时间快用完了。"你们有没有计划也支持移动 Linux？比如在手机上运行，那种通常运行 Android 的设备？"Sitter 说目前没有计划，但这是他们心中一个愿景式的目标。

Eisentraut：revert 将持续到士气改善为止

PostgreSQL 核心团队成员 Peter Eisentraut 发表博文，反思自 beta 期开始以来即将发布的 PostgreSQL 19 中被移除的"异常之多的特性"：

"部分被 revert 的特性存在重大架构缺陷，在 beta 期间很难快速修复。但也有一长串相对无害的边界情形问题。在过去，这些问题很多要到很久之后才会浮现，我们会在随后五年里一点一点修掉。但在 LLM 辅助代码评审之下，这类问题能被更快发现，然后你面对的是一份多达四十项的缺陷报告清单。即使每项平均只需要三行修复，处理每一项都有固定开销，然后时间就不够了。几乎所有受影响的特性都是很久以前写的，那时 LLM 辅助代码评审还没有现在这么有用——也就是说，有效的质量门槛是在特性编写并提交之后才被抬高的。除非 LLM 辅助代码评审的能力不再以当前的速度提升，否则这种情况在未来的开发周期里应当会自行好转。"

"由此推论，至少就我所知，这一局面大部分并非源于『凭感觉编码』（vibe coding）——这些代码早在那种做法出现之前就已写就。"
