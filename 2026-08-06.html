进程构建 API 的雏形

作者：Jonathan Corbet 发布日期：2026年8月4日 英文原文

近期关于 "spawn templates"（生成模板）的讨论提出了一个疑问：是否时机已到，应该提供一种替代经典 Unix fork()/exec() 进程创建模式的接口。其中浮现的一个想法是将模板模式转向一种接口，可用于从零开始高效地组装新进程，而不必复制父进程。理想情况下，该接口还应能实现 posix_spawn()。Li Chen（spawn-template 工作的作者）现已以一个补丁系列（在大量 LLM 辅助下编写）作为回应，展示了 Linux 的 process-builder API 可能是什么样子。

在 Unix 模型中，调用 fork()（在 Linux 上最终是 clone() 的某种变体）会创建调用进程的副本，这涉及相当多的工作。子进程随后通常会以所需方式修改其环境——例如打开或关闭文件——然后调用 execve() 运行新程序。后一个调用最终丢弃了为复制父进程所做的大部分工作，这并不完全高效。如果意图是立即运行不同的程序，更好的模型或许是：从一开始就拼装新进程，而不卷入（大部分）父进程状态。

进程创建

在 Chen 的补丁系列中，实现方式是首先通过现有的 pidfd_open() 系统调用创建一个空进程：

new_process_fd = pidfd_open(0, PIDFD_EMPTY);

新的 PIDFD_EMPTY 标志请求创建一个进程壳（process shell），其细节将在以后填充。返回的是真正的 pidfd，但大多数与进程相关的资源尚不存在：没有进程 ID、内核中没有 task 结构、也不计入父进程的进程数资源限制。在此阶段，大多数作用于 pidfd 的内核操作都会拒绝对此 pidfd 执行任何动作。

下一步是整理驱动新进程构建的信息；这项工作围绕如下结构展开：

struct pidfd_spawn_run_args {
    __u32 flags;
    __u32 nr_actions;
    __aligned_u64 path;
    __aligned_u64 argv;
    __aligned_u64 envp;
    __aligned_u64 actions;
    __u32 action_size;
    __u32 reserved0;
    __u64 reserved[2];
};

path 字段是指向字符串的指针，包含新进程应运行的可执行文件路径；如下所述，在某些情况下它可为 NULL。argv 和 envp 指向常规的 argument 与 environment 数组。flags 字段必须为零，reserved 字段也必须为零。填写这些字段（其余稍后介绍）就提供了通过两个新系统调用中的第一个来构建并运行进程的充分信息：

int pidfd_spawn_run(int pidfd, struct pidfd_spawn_run_args *args, int arg_size);

此处 pidfd 是正在构建中的进程的 pidfd，args 是指向上述结构的指针，arg_size 是该结构的大小。若一切顺利，此调用将创建完整进程并以其指示的程序运行；返回值是现在已完全填充的进程的 ID。原始 pidfd 保持有效并附加到该进程。如果发生某种错误，进程壳将留在某种死亡状态，任何进一步操作它的尝试都将失败。

配置

提供可执行映像、参数和环境通常只是配置新进程的开始；典型应用还会希望设置进程的文件描述符，并可能调整许多其他内容。这正是 pidfd_spawn_run_args 结构的 actions 字段的用途。它指向此结构类型的数组：

struct pidfd_spawn_action {
    __u32 type;
    __u32 flags;
    __u32 fd;
    __u32 newfd;
    __u64 reserved[2];
};

type 字段描述在进程被实例化并启动前应执行的操作。此补丁集中目前定义（最终所需操作的很小子集）的操作有：

  • PIDFD_SPAWN_ACTION_DUP2：使用 dup2() 复制现有文件描述符。现有文件描述符应在 fd 字段传递，预期的新描述符在 newfd。
  • PIDFD_SPAWN_ACTION_CLOSE_RANGE：关闭 fd 和 newfd 之间（含）的文件描述符范围。
  • PIDFD_SPAWN_ACTION_FCHDIR：将新进程的工作目录更改为 fd 标识的目录。

PIDFD_SPAWN_ACTION_CLOSE_RANGE 允许 close_range() 系统调用支持的 CLOSE_RANGE_CLOEXEC 与 CLOSE_RANGE_UNSHARE 标志；其他两个操作的 flags 必须为零。pidfd_spawn_run_args 结构中的 nr_actions 字段指示存在多少操作，而 action_size 是 pidfd_spawn_action 结构的大小。这些操作将在定位可执行映像之前执行，意味着更改工作目录会影响相对路径如何被解析。

如果任何操作在 pidfd_spawn_run() 时失败，整个系统调用将失败，新进程不会启动。

第二个新系统调用是新进程某些方面的替代配置接口：

int pidfd_config(int pidfd, unsigned int cmd, char *ukey, char *value, int aux);

此系统调用旨在超越 spawn 功能而有用；但在本补丁集中，它只能做一件事。使用 cmd 为 PIDFD_CONFIG_SET_STRING，可将基于字符串的参数设置给给定 value。此集中唯一的此类参数是 PIDFD_CONFIG_KEY_PATH，它设置要运行的可执行文件路径。如果传递给 pidfd_spawn_run() 的 path 指针将为 NULL，则必须调用此调用。如果向该系统调用传递了非 NULL 路径，它将覆盖用 pidfd_config() 配置的 path。

缺失的部分

此系列旨在作为概念验证，帮助社区决定整体方向是否合理，因此它没有实现最终所需的大部分内容。如上所述，可用操作集比最终需要的要小得多。为实现 posix_spawn()，内核必须支持定义信号处理、控制调度器参数、打开文件等操作。在很大程度上，一旦所需接口形式确立，这些只是编程问题。

另一个大缺口是 pidfd_spawn_run() 实际上并不是从零创建新进程；相反，内部实现基于 vfork()。理论上，一旦 API 达成一致，可以透明地替换实现，用户空间唯一可见的变化是更好的性能。实践中，这可能不是个小工作。内核只从零创建两个特殊用途进程（init 和 kthreadd）；用于一般情况的相关机制并不存在。这也只是编程问题——或许相当多。

不过首先，API 必须达成一致。该系列于 7 月 16 日发布，但截至本文撰写仅获得一条 review 评论。在考虑更完整的实现之前，它需要吸引更多目光。多年来许多人一直在要求这类进程创建接口；现在正是他们查看该提案是否接近其想法的时候。

Fedora 考虑引入利益冲突（COI）政策

作者：Joe Brockmeier 发布日期：2026年8月4日 英文原文

Fedora Council 正在考虑为其决策机构制定利益冲突（COI）政策，例如 Fedora Engineering Steering Committee（FESCo）、特殊兴趣组（SIGs），以及向委员会报告并负责对影响 Fedora 项目的决策的任何其他组或个人。不过，当前草案不适用于委员会本身。COI 政策的公开讨论于 7 月 23 日开始，似乎接近完成，委员会将在 8 月 13 日的会议上再次讨论该主题。

缘起

开源项目拥有 COI 政策并不罕见。事实上，对于像 Fedora 这样拥有许多其他明确定义政策的项目却缺乏此类政策，可能看起来有些不寻常。在宣布讨论时，Aoife Moloney 表示，委员会追求 COI 政策的想法源于约 18 个月前"Fedora 中一个治理组做出撤销某人以某种方式贡献项目能力"的决定的余波。

Moloney 含糊提及的决定，是 FESCo 对撤销 Peter Robinson 的 provenpackager 状态的颇有争议的处置，该状态授予提交 Fedora 中所有包（而不仅是其拥有的包）的能力。FESCo 曾在私人会议中投票剥夺 Robinson 的状态，并采取罕见步骤公开宣布撤销，指控他"继续使用其 provenpackager 特权以未批准方式，频繁给其他维护者造成额外工作"。Fedora Council 后来推翻了该决定并向 Robinson 道歉。

Emmanuel Seyman 于 4 月询问委员会提供 FESCo 行动背后的公开说明，以及每位成员如何投票。他指出 FESCo 曾承诺在 2024 年 12 月发布带有私人讨论摘要的公开 ticket：

自那以后，我们等待被告知将创建的公开 ticket，并且不得不在多次 FESCo 选举中投票，却无当时投票者的完整投票记录，以便我们判断是否需要他们继续留在 FESCo。

委员会成员 Justin Wheeler 表示委员会已开会讨论该请求，摘要将在"今天结束前"于 5 月 7 日发布，但直到 6 月 5 日才有更新，当时 Moloney 说委员会决定不提供额外信息。"对做出这些决定时所依据的隐私初始期望翻悔会显得不真诚，而且我们缺乏必要的背景来形成回顾性意见。"

Wheeler 于 7 月 6 日跟进，再次报告委员会不会提供关于撤销事件的进一步信息，但"承诺改进我们的利益冲突政策，作为防止此类治理问题再次发生的机制"。这正是 Robinson 曾建议的：他在 2024 年 12 月向委员会提出请求表示 Fedora 需要 COI 政策。Fedora 项目领导人（FPL）Jef Spaleta 于 2025 年 7 月向委员会提供草案政策，但直到现在才分享以进行公开讨论。

由于针对 Robinson 的投诉细节从未公开，目前不清楚 COI 政策本可在改善情况中发挥什么作用。可能是 FESCo 的一名或多名成员启动了程序然后投票反对 Robinson 而不是回避（recuse）——但就目前而言，观察者只能猜测。

草案政策

该政策开头免责声明其"使用 NotebookLM 生成，然后经人工编辑控制修订"。政策的主要目标是确保项目做出的所有影响个人参与 Fedora 的决定"被视为公平、公正，并符合 Fedora 项目及其社区的最佳利益"。

政策范围包括"在 Fedora Council 下运作的任何 Fedora 项目组或团队内参与决策过程的所有个人和团体"，列举了非详尽的组、团队等列表，但似乎广泛适用于项目中发生的任何决策，除了 委员会自身的决策。它将利益冲突定义为：个人的利益或其所属组织的利益"可能合理被视为影响或看似影响其代表 Fedora 项目做出客观决策的能力"的任何时候。冲突利益可能是"财务收益、职业晋升、个人关系或对另一组织的忠诚"。

政策提案规定，利益冲突并不自动取消参与讨论或对事项投票的资格。它承认，例如许多 Fedora 贡献者受雇于 Red Hat，可能经常面临可能是利益冲突的情况。

草案要求，如果个人"认为其可能与特定讨论、投票或任务有利益冲突"，则应尽早声明该冲突。草案有点模糊，不幸的是。它规定如果存在 COI，个人应从决策过程中回避（recuse），但也建议可讨论可能的 COI，以便如果决策组认为不取消资格，仍允许参与决策。

委员会将调解或裁决任何关于利益冲突的分歧或争议。政策对如果个人有利益冲突、或决定似乎受利益冲突影响会发生什么持开放态度。补救步骤，它说，"应逐案处理（case-by-case basis）"。

讨论

Christopher Boni 指出草案关于回避的语言与其注明冲突不自动取消资格的明显矛盾。FESCo 成员 Fabio Valentini 回复说，如果假设回避仅适用于"关于先前声明的利益冲突是否取消此人资格或应采取任何补救行动的决定过程"（草案第 6 点），明显矛盾就解决了。不过，他说如果这是意图，应在政策中明确。

FESCo 成员 "Maxwell G" 说他理解委员会无法将决策上报给自己，"但我认为其余部分也应适用于委员会内部的决策"。Valentini 同意并建议或许委员会可以"向下上报（escalate 'down'）"到像 FESCo 这样的机构。

讨论中出现的一个担忧是 FESCo 成员可能必须回避投票自己的 change proposals。Miro Hrončok 说已反复同意 FESCo 成员被允许投票支持自己的提案。"为了自身利益而竞选机构也应完全 OK。只要披露，我不认为我们应自动要求弃权（abstentions）。"

大多数人似乎同意 COI 政策是好事，即使草案需要润色。然而，FESCo 成员 Zbigniew Jędrzejewski-Szmek 主张它不必要。他说 FESCo 移除 Robinson provenpackager 状态的决定并未"以任何强烈方式"受利益冲突影响，COI 政策不会带来不同。

我看到 Fedora 中各种决策缓慢或出错（事后看来），但那些问题与利益冲突关系不大。我会列举如下原因：缺乏时间调查细节、对范围的误解、对某些技术或方法的偏好、过于宏大的计划、疲倦、缺乏同步等。在某些情况下存在人际好恶或人际间的信任/不信任，但那些[是]不属于拟议政策所要求披露类型的明显关系。

似乎不太可能合理要求 FESCo 或其他机构成员基于例如对另一贡献者的厌恶而回避决策。

Aleksandra Fedorova 似乎同意政策无必要。"我们不需要更多政策来声明和管辖显而易见的事。它只是给企业风格官僚作风带入以人为本的项目。"她后来说对于"无法公开进行的决策"如行为准则投诉或其他敏感主题，拥有 COI 政策可能有意义。"如果决策无法在公开中充分讨论和证明，没有简单默认方式获得信任，一些明确的利益冲突考虑会有帮助。"她建议一个更小的政策：

涉及行为准则问题、以及关乎 Fedora 项目中特定个人访问权限的其他问题之决策，不应由直接参与此类行为的人做出。

Moloney 说她赞成将政策范围缩减至需私下做出的决策。Jędrzejewski-Szmek 说他认为 Fedorova 建议的文本很棒。"我们能采纳那一句话并将其加入顶层治理文档然后就此结束吗？"

委员会在 7 月 29 日会议的开放楼层部分讨论了该政策。Moloney 说委员会决定重拟文档并允许两周更多反馈。它将在 8 月 13 日安排的委员会会议上再次讨论。

FUSE io_uring 的缓冲区大小

作者：Jake Edge 发布日期：2026年8月3日（LSFMM+BPF 峰会） 英文原文

Filesystem in Userspace（FUSE）子系统提供了一种从用户空间服务器服务文件系统请求的方式，将格式处理代码移出内核。FUSE 服务器可以使用 io_uring 设施获得更好性能，但 Bernd Schubert 担心内存被浪费，因为当前实现具有单一、大型 buffer 大小，对于小 I/O 操作过于庞大。他在 2026 年 Linux 存储、文件系统、内存管理与 BPF 峰会于克罗地亚萨格勒布的文件系统轨道主持了关于该主题的 discussion。

目前，libfuse 每个 ring 设置 8 个条目，每个条目默认最大负载大小（8MB），不过也可切换为 4MB，他开始说。通常每个 ring 需要一到两个条目来达到至磁盘（本地或通过网络）的最大吞吐量，但也需处理元数据请求，用于 stat() 或目录列表等操作。"你不想在作这些元数据请求时干扰你的流 I/O"。

那些较小请求可能是 16KB 或 128KB。然而，要用该大小请求饱和 I/O 带宽，需要更大量 buffer。"问题是我们如何做。"现有实现使用带有独立 header 和 payload 结构的条目，但每个具有相同的 payload 大小。

Schubert 指出 Joanne Koong 一直在研究更改 FUSE io_uring 的 buffer 处理的补丁，将 header 与 payload 分离。每个条目仍有一个 header，但 payload buffer 将共享。条目与 payload 之间不再有一对一映射，且 payload 将以多种大小可用。

Schubert 设想了不同方法，例如四种不同 payload 大小。将有使用 4KB、64KB、128KB 和 1MB payload 大小的条目；4KB 条目有 128 个 buffer 可用，而较大大小只有两个 buffer 可用。他尚未编写实现其想法的代码，但认为可行：基于 I/O 操作大小从单一 ring 选择适当大小条目。

在前一天与 Koong 的讨论中，她说问题可用多个 ring 而非单一 ring 上多种大小解决。每个 ring 有不同 buffer 大小，并有代码基于 I/O 大小选择正确 ring，类似于 Schubert 设想的代码。他的担忧是多个 ring 意味着更多系统调用，因此他偏好单一 ring。用户空间 FUSE 服务器需监控多个 ring 并从每个服务 I/O 操作。

他对多个 ring 的另一个担忧是针对被分区为仅运行 Linux 于少数核心的系统上的应用，这意味着单一核心可能负责轮询多个 ring。"那变得痛苦。"

FUSE 维护者 Miklos Szeredi 问 Schubert 的计划是否需要管理大内存池中的 buffer 分配，但 Schubert 说不需要。那样处理分配会导致碎片，因此他的方法只是静态设置每种大小的多个 buffer；例如当没有更多 4KB buffer 时，请求者将必须等待。有人疑问或许在那种情况下使用更大大小，但他认为那些太宝贵而不能那样用。

Koong 说她担心等待正确大小的可用 buffer 会增加不必要延迟。用她的多 ring 方案，其他 ring 可为请求提供 buffer 而不是等待正确大小的那个。她问："如果你有小请求且有更大 buffer 可用，为何让小请求等待直到有小 buffer 可用？"Schubert 说那种情况下，已有 128 个请求在飞，因此再加一个无实际益处。

他们之间有些来回，Schubert 想避免处理多个 io_uring ring 的用户空间复杂性，而 Koong 寻求最佳利用所有可用 buffer。她说她认为不需要超过两种不同 buffer 大小，一种小用于元数据，一种大用于数据。Schubert 说那没问题，但仍意味着如果不同大小在 Koong 提议的不同 ring 上，需轮询多个 ring。

一名与会者问所见的 io_uring 性能问题，但 Schubert 说不是他要改善性能。他想减少内存使用，因为需要许多元数据请求，但如果它们都必须与 I/O 请求同大小，会浪费大量内存。

Koong 提出 head-of-line blocking 问题，她说这是多 ring 的优势：一个线程可处理数据 I/O 而另一个处理元数据请求。Schubert 说当前 libfuse 可能仍以同步方式处理请求，可能导致较小 I/O 操作阻塞在较大之后，但将 libfuse 切换为异步处理 io_uring 操作应解决该问题。Koong 不确信那种 libfuse 更改能很好与有自己 I/O 处理想法的自定义库配合。Schubert 同意那可能是问题，但认为罕见，Koong 不同意。

Schubert 说他计划向 libfuse 添加 coroutine 支持，应能使服务器仅用 libfuse 线程避免 head-of-line blocking 问题。他指出已经可写避免该问题的 FUSE 服务器，但必须用处理异步 io_uring 操作的额外线程。

此时，会议时间已到，且不完全清楚之后会怎样。

内核 / BPF · 网络

用 BPF 检视其他网络命名空间

作者：Daroc Alden 发布日期：2026年8月5日（LSFMM+BPF 峰会） 英文原文

Jordan Rife 的工作涉及为 Cilium 编写与 Kubernetes 网络接口的 BPF 程序。作为该工作的一部分，他想允许具有适当权限的 BPF 程序遍历不同 network namespace 的 socket。他在 2026 年 Linux 存储、文件系统、内存管理与 BPF 峰会主持了关于该想法的会议，出席的 BPF 开发者迅速提出了若干相关替代方案。

Socket-lb 是 Cilium 的一个特性，使用与给定 control group 关联的 socket 钩子将连接跨远程服务器负载均衡，同时避免网络地址转换（NAT）的每包开销。在不用 socket-lb 的设置中，客户端可能向前端服务器请求，然后前端用 NAT 透明路由连接到所选后端服务器。Socket-lb 通过让路由直接发生在客户端设备上来改进，对用户空间仍透明，但避免 NAT 暗示的额外网络跳。实践中，socket-lb 有一些限制，Rife 说。例如，如果所选后端消失，流量将继续指向那不存在的后端，直到 Cilium 清理。今天，该软件通过使用 BPF iterators 遍历可用 socket 并在需要时销毁它们来做到。

那可行，但仅在特定 network namespace 内，因为 namespace 彼此隔离且不能看到彼此的 socket。实践中，这意味着 Cilium 的用户空间组件必须进入主机上每个 Kubernetes pod 的 namespace，扫描其 socket，然后退出 namespace 并进入下一个。这给整个过程增加了显著开销，其实不需要，因为 Cilium 本来有所有 network namespace 的管理访问权。

更糟的是，socket 在内核中不按 network namespace 排序，因此每次 Cilium 的 BPF 程序扫描时，必须遍历整个 socket 哈希表；内核在 BPF 程序看到前过滤掉其他 namespace 的 socket。因此，Cilium 为每个 network namespace 遍历系统上每个 socket 的列表一次，这低效。在他的工作中，Rife 说曾见每台计算机多达 256 个 namespace。

他提议的解决方案简单：创建新 iterator，供具有适当特权的 BPF 程序使用，一次遍历系统上所有 socket，即使是来自外部 namespace 的。那样，Cilium 不需更改 network namespace；它可简单用 BPF 程序定期扫描整个系统以查找陈旧 socket-lb socket。

Jakub Sitnicki 问 Rife 为何不直接保留哪些 socket 对应哪些后端的列表，然后用那些。BPF 程序可将指向 socket 对象的指针存储在 socket maps 中，可用于存储弱引用（不增加 socket 引用计数、因此不阻止其关闭的指针）。所以，这样的方案不会在 socket 自然死亡后保持它们存活，他指出。Rife 在 2025 年确实试过，但使其工作比应有更复杂。在当前内核，BPF 程序不能从 socket map iterator 的上下文销毁 socket，因为它们需获取 socket 的锁。修复那需要重写围绕 socket 访问的许多锁逻辑。

一种变通是添加 bpf_sock_destroy() 的可睡眠变体，将自行获取 socket 锁，Martin Lau 曾向他建议，他说。最终，Rife 放弃了该想法，但如果他提议的整机 iterator 不被接受，他可能回来。Sitnicki 想知道为何 socket map iterator 起初不可睡眠。Rife 不知道，尽管他推测 RCU 与 socket 锁交互可能有些挑战。Lau 澄清许多 BPF iterator 可睡眠，只是 socket map 特别有此问题。

Rife 的一位同事正致力于在单独 map 中跟踪所有 socket 的元数据，那也可能是变通。另一种方法是让 bpf_sock_destroy() 本身从 socket map iterator 上下文工作，Rife 说。那难做而不增加引用计数（从而一些内存开销）或更改 iterator 语义。但允许足够特权的 BPF 程序遍历所有 network namespace 是整体简单得多的解决方案，他认为。

Daniel Borkmann 提到 BPF 维护者曾讨论添加遍历 network namespace 的 iterator；或许该 iterator 的引用可作为受信任输入传给 socket map iterator，他建议，这将让现有 socket map iterator 工作而不需 Cilium 用户空间组件更改 namespace。Rife 指出那仍会多次遍历机器上所有 socket，只是完全在内核内做。

Sitnicki 和 Lau 关于当前代码如何找 network namespace 引用及潜在改进进行了简短旁谈。Rife 同意研究它，并咨询网络维护者，但观察到那仍不解决他的效率问题。

John Fastabend 指出 Cilium 在多处缓存原始 socket 指针，因为 BPF socket map 不可扩展，"这很讨厌"。存储在 BPF socket map 中的指向 socket 的指针在 socket 销毁时自动清理；作为不透明值存储在 BPF arena 中的 socket 指针便于跟踪存储，但不自动清理且不可解引用。Sitnicki 指出在 BPF arena 存 socket 指针不能很好用于 Rife 的用例。Fastabend 回复说他也不好用，但有许多理由想将 socket 搁在更灵活处。他建议更改 BPF socket map 为可调整大小（resizeable）。

能挂载 sockfs（允许用户用文件系统 API 管理 socket 包括权限的虚拟文件系统）并以那样 pin socket 会不错，Sitnicki 说。那将完全避免需 BPF map。Lau 评论有人有补丁在进行与之相关，但仍认为能如 Rife 提议遍历一切会有用。

Sitnicki 问 Rife 是否考虑获取可能消失的 UDP socket 后端进程的重复文件描述符，在 daemon 中持有，并在需要时用以清理。Rife 解释他愿从 BPF 做整个事。Fastabend 想知道这是否也是 TCP socket 问题。Borkmann 解释正常 TCP reset 机制会处理，但仅在足够长超时后，一些客户偏好 socket-lb 提供的更快故障转移，因此它用于 UDP 和 TCP。

此时会议陷入关于其他应用可能用可调整 socket map 的讨论，然后时间耗尽。尽管与会开发者对 Rife 想法提出许多替代，无一人显敌意，只是有兴趣将棚子漆不同颜色。截至 8 月初，Rife 问题尚无接受方案。

内核 / 文件系统 · FUSE

FUSE 现状与计划

作者：Jake Edge 发布日期：2026年8月5日（LSFMM+BPF 峰会） 英文原文

Filesystem in Userspace（FUSE）维护者 Miklos Szeredi 在 2026 年 Linux 存储、文件系统、内存管理与 BPF 峰会主持了关于该子系统的 birds-of-a-feather（BoF）讨论。其中他谈了维护挑战、提议特性及其状态，以及他的新 FUSE API 计划。FUSE 社区目前似乎有很多兴趣和活动。

他开始注意到他感觉"不是个好维护者"。做维护者有两方面，他认为，"一是挡住 bug，二是放特性进来"。他擅长第一，但不擅长第二。解决方式之一是 FUSE 有共同维护者（co-maintainer）。"如果有人自愿，我会非常高兴。"与会者有些或许开玩笑的建议，但无人站出来帮共同维护 FUSE 本身。

特性与清理

Szeredi 转到待定特性列表，从 Darrick Wong 的基于 iomap 的用户空间 API for FUSE 开始。那补丁集很大，Szeredi 说，使内核中 FUSE 大小至少增 30%。来自 John Groves 的基于 FUSE 的 famfs 补丁小得多，他希望那些在当早些时候的 famfs session 有些进展。他也提及 Joanne Koong 的 FUSE 中 io_uring 的零拷贝支持、来自 Horst Birthelmer 的 compound commands、Luis Henriques 的 file handle 用户空间 API for FUSE、Bernd Schubert 在上一场主持的 io_uring buffer size 讨论，以及 Koong 的 FUSE 大 folio 支持。同时，Szeredi 一直在重构和清理 FUSE API。

他详述清理，从 传输和文件系统层分离 开始，已进入即将到来的 7.2 内核。他计划对 字符设备用户空间（CUSE）和 virtiofs 做同样事。此外，他想提供多种层类型，引用现有网络与 io_uring 传输为例需更好分离。他也想将 superblock 操作从 inode.c 拉到自有 C 文件，并将"非常大"的 file.c 按所用 I/O 类型拆成更小文件。他鼓励他人提出清理想法。

FUSE 的用户空间 API 已有 20 多年，像 FUSE 内核代码一样积累相当多糟粕。他已开始干净 slate API，"目前非常瘦"约 2,000 行代码，即当前 FUSE API 大小的 10%。它叫 "fusex"，用于 FUSE extended 或 experimental，并可在他的 FUSE 树中获取。它有很多限制，因仅支持本地文件系统，正好与原 FUSE 网络文件系统焦点相反，他说。它也仅同步，无异步操作支持。虽然 fusex 当前用作添加可能最终迁入主 FUSE 代码库各种特性的实验树，他愿见它变成"协议的新主版本"。

Ted Ts'o 提出了 FUSE 文件系统在非 Linux 平台使用的"有点相关"问题。特别是，有 fuse2fs FUSE 客户端在 macOS 和 Windows 的用户；Wong 一直在扩展它以用更新 FUSE 特性，Ts'o 说，并遇到 macFUSE 问题。Ts'o 愿见更简单用户空间 API 因为他看了现有者并注意到其中体现的 20 年历史。他愿其 FUSE 驱动在 macOS 和 Windows 工作，但意识到可能需其他操作系统开发者与 Linux FUSE 项目大量协调，这可能没发生。Szeredi 指出他上次从 macFUSE 开发者听说已是 15 年前，因此无真正协调。

Schubert 说他一直在处理 libfuse 在 BSD 上的一些 问题 且认为 macFUSE 基于 libfuse。在 BSD 上跑 libfuse 测试难，且他无也不想要 BSD 系统；一些 BSD 开发者正搞运行 OS 的虚拟机以便跑测试，但他认为 macFUSE 无类似努力。因 Apple 内核代码限制，他说当前方法是将文件系统挂载为 NFS 并用 FUSE-to-NFS 转换层。由于那些限制，他认为原生 macFUSE 开发已停止。

Ts'o 说他正用 macFUSE 跑原生 macOS FUSE 在笔记本。问题是 Apple 需签名内核扩展，因此仅单一开发者能从 GitHub 上 macFUSE 源码 构建二进制。任何想用 macFUSE 者必须从 Apple store 获取二进制，他说；可能有方式让其他想搞代码者向 Apple 注册以便本地跑在笔记本，然而。Schubert 说 FUSE-T 是他谈的项目，Ts'o 不熟悉。Ts'o 确有兴趣使 fuse2fs 在 macOS 工作且也有 BSD 虚拟机访问，因此他可能帮些测试。

子维护者

Szeredi 指出他认为一些待定 FUSE 特性，如 iomap、file handle、compound command 支持，应进 fusex 而非现有 FUSE 实现。他也认为 FUSE 对某些片如 io_uring 路径有子维护者（sub-maintainers）有意义；他大笑着说 Schubert 已揽太多活但自愿子维护 FUSE io_uring。Schubert 说他总看影响那路径的补丁且想直接在变更时通知，但 Christian Brauner 警告作为子维护者也不太可能抄送像近期 kmalloc() 转换 的变更。

Brauner 也建议 Koong 应考虑做 io_uring 子维护者。她有些犹豫同意，但有更一般担忧想提。她愿 FUSE 开发社区从 Szeredi 获更多关于什么是可维护的指导，尤其用户空间 API，难更改。他有数十年经验许多新 FUSE 开发者缺，她说。另一与会者指出子维护者仅当 Szeredi defer 其判断才有效；Szeredi 同意，指出他不能再将所有 FUSE 装进脑袋，因此已 defer 如 FUSE io_uring 给他人。

用户空间 API 是需做对的重要事，Szeredi 说。Brauner 同意并指出内核开发者"对此烂"，但指出他认为虚拟文件系统（VFS）层开发者近期变好"因为我们与实际用户紧密同步"。那帮更好 API 也帮 API 采用；"常你能设计被用户空间忽略因不实用的 API"。

Brauner 指出 VFS API 近期对扩展性的关注有益。一旦实现新特性，有趣扩展想法出现；能轻松容纳"在我经验中是无价的"。他指出 io_uring 是另一从开始烘焙扩展性的例子。

Amir Goldstein 已自愿做 FUSE passthrough 子维护者但似乎怀疑加更多 FUSE 子系统条目到内核 MAINTAINERS 文件有用。他人不同意，Brauner 指出可能对职业生涯有帮助；工具，特别是 b4，好用那些条目。Szeredi 加了两个新 FUSE 子系统，io_uring 和 passthrough，及新维护者；那变更 合入 7.2。

Schubert 曾建议 FUSE 月度或双周电话会议，因此 Szeredi 请他描述想法。需对特性方法达成一致，Schubert 说；当前开发可进行数月直到 patch review 脱轨特性。那留开发者试图向管理解释需更多时间开发新补丁集。他建议设计在开发前提交邮件列表；那些设计可在电话讨论。Brauner 说他愿 VFS 开发者那样做。

Fusex

通过远程链接，Wong 问 fusex 及是否意为与现有 libfuse 工作。Szeredi 说，或许有点犹豫，是；Wong 希望将其 iomap 工作切到 fusex 不需改任何用户空间代码，但 Szeredi 不能承诺。他认为不需多代码，但 fusex 仍缺一些所需特性。

Fusex 仅用于本地文件系统，他重申，意味着文件系统除通过 FUSE（和 fusex）外不能更改。那样做不应导致崩溃，但文件系统不正常工作因 fusex 无处理那情况的基础设施，那简化它极大。它仅是原型，但这点若继续，应加远程更改文件系统能力"但以比当前上游 FUSE 更 sane 方式"。

Brauner 问 Szeredi 是否视 fusex 为现有 FUSE 替代；Szeredi 说是，但认为现有 FUSE 永不能消失因 fusex 不能完全向后兼容。两者将共享多相同代码，因此维护负担不大；事实上，"摆脱边角情况和奇怪行为"应使整体维护更易。

Goldstein 指出维护负担需包括 libfuse，Szeredi 同意。Schubert 说他计划开始标记一些 libfuse 函数为弃用（deprecated）；希望文件系统开发者随时间远离它们。远离用弃用函数的转换甚至可由 LLM 处理，他说。

Schubert 也问特性，如 compound commands，正被推到 fusex；开发那些特性的公司可能想用更少限制的上游 FUSE。Szeredi 说不反对加特性到主 FUSE 代码库，但愿合入 fusex 作为实验场所然后加其中的特性可合回常规 FUSE。此时会议时间到。Szeredi 在峰会后不久向邮件列表发了会议摘要。

内核 / BPF · 生态

BPF 中库的未来

作者：Daroc Alden 发布日期：2026年7月31日（LSFMM+BPF 峰会） 英文原文

Song Liu 相信程序员组装复杂 BPF 程序的方式未来将快速变化。在 2026 年 Linux 存储、文件系统、内存管理与 BPF 峰会会议中，他分享了关于那变化可能样子的想法，尽管他对 BPF 维护者该做或不做什么无具体提议。他预期 Rust BPF 包生态系统将发展，这重要因为 BPF 目前无真正包管理器。

Liu 说，现有流行 BPF 库不多。那些存在的通常是小 header-only 库，或处理加载和管理 BPF 程序的用户空间侧。有 BPF 库非不可能；bpftrace 有标准库。Bpftrace 也能导入非标准库 BPF C 代码，类似正常 C 中内联汇编。"但我不确定人们真这样做，"他加。

给定其余编程世界用库，为何不 BPF？有几个原因。其一，无标准包管理器或分发方式。而且，BPF 程序是否过验证器可取决于整个程序共同属性，不仅隔离函数。这使用库更难，许多人发现复制现有例子并改用于其用途比建可重用库易。该趋势明显例外是 libarena，它曾在 峰会早些时候讨论。

Emil Tsalapatis 指出缺库的另一个原因可能是许多人将 BPF 程序写为单一 C 文件，不通过链接多个 BPF 对象所需步骤。他在处理 sched_ext 调度器时观察那模式。

随 Alexei Starovoitov 计划使 BPF 更易用 Rust 写，可能 BPF 库出现在 crates.io（Rust 包仓库），Liu 说。但那有其自身问题：多库时难找好、可靠者。而且 libarena 若用 Rust 重写可能大变。Starovoitov 澄清 libarena 目前用 C 写，"但时机到我们会转 Rust"。

Liu 然后推测大型语言模型（LLM）使用可能如何改变 BPF 库使用景象。他认为它们可能比人类作者更易复制修改现有方案，但难确定。Liu 预测更多 BPF 库将出现在 crates.io；伟大库留为库，仅好的库被复制、粘贴、修改。坏库导致问题并花时间转有用代码。那预测多取决于 LLM 适应 BPF 打包文化变化的好坏。

Starovoitov 说他预期 LLM 快速适应特别 libarena 使用。库副本应留 GitHub，他说。然后 sched_ext 可将其作为 Git submodule 包含，一旦 LLM"第百万次刮 repo"将拾取已移入 libarena 代码并开始用。截至 2026 年 7 月，sched_ext 尚未加 libarena 为 submodule。总体，将库放入 LLM 知去寻处如 GitHub、crates.io 等将帮采用，Starovoitov 说。

Liam Wiseheart 问人们期望 BPF 库放什么，除基本数据结构。"Whatever you want，" Starovoitov 答。其他与会者冒险一些候选答案，包括路径打印与遍历、字符串操作、基本文件 globbing、正则表达式。

内核 / 系统调用

重新审视 O_CREAT|O_DIRECTORY

作者：Jonathan Corbet 发布日期：2026年7月30日 英文原文

Linux 提供系统调用（mkdir()）创建目录，和 几个 open() 变体 可打开目录。但，Linux 中无系统调用能在单一、无竞态调用中创建并打开目录。Jori Koolstra 一直在补救该情况，最近通过改造当前返回错误的 open() 标志集。然而，有担忧显示创建不给应用开发者设陷阱的用户空间接口有多难。

在单一系统调用创建并打开目录比用两个更简单高效，当然。它也防其他进程在创建和打开步骤间将目录替换为他物可能。检测那情况目前 Linux 可能，但需某些防御性编程，应用开发者不总擅长。因此渴望更直接方式完成那对操作。

3 月，Koolstra 试图用 补丁系列 加新系统调用 mkdirat_fd() 解决，返回新创建目录的文件描述符。那系统调用在 后续补丁 改为 mkdirat2()。有许多对实现担忧，也关于首先创建新系统调用。Christian Brauner 特别 认为这问题更好用修改 open() 处理一对现有标志解决。

具体，所有 open() 变体支持 O_DIRECTORY 标志，如果应用试打开目录而非正常文件则必需。也支持 O_CREAT，指示 open() 如果命名文件不存在则创建。解释那两标志组合为请求创建并同时打开目录会有意义。加此能力到 open()，Brauner 说，也将使系统调用许多其他特性免费可用，如限制名如何解析的能力。因此他总结："I think here it is pretty clear that O_DIRECTORY|O_CREAT is the right thing to do"。

Koolstra 遂将新 API 实现为 RFC 补丁集，随后三个更多 RFC 和三个非 RFC 版本；仅在 最后那个 发布后其他开发者开始认真看提议 API，且不都信服是正确方法。Pedro Falcato 特别 主张此 API 几乎不可能让应用可移植使用，给定 O_CREAT|O_DIRECTORY 过去解释方式数量。

那故事确实有点复杂；LWN 在 2023 年 报道过。Linux 处理带那标志组合的 open() 方式包括：

  • older kernels 如果命名文件存在会失败，如果是常规文件返回 ENOTDIR，如果是目录返回 EISDIR。如果给定名无物，open() 会创建常规文件，似乎不可能调用者所要。
  • 自 2020 年 5.7 发布，内核开始最后情况返回错误，仍创建文件，似乎更不可能开发者希望。
  • Brauner 加 补丁 到 6.4 使内核所有情况以 EINVAL 失败该标志组合。

加上其他支持 POSIX 系统调用系统有自己对那标志组合解释，Falcato 说，结果将难正确使用：

如果你想写可移植、或打算标准化的东西，你有大约 5 种不同行为横跨整个 FOSS UNIX 版图，还没考虑其他一切。它也可能永远不会进 POSIX，因为没人能就此处语义达成一致。

TL;DR 鉴于上述原因，我不明白用户要如何使用它而不陷入彻底雷区。

他建议将变更限 openat2() 可能更好方法。

Brauner 虽 不理担忧，说："I don't think any of this is really an argument worth considering"。那标志组合行为在 Linux 一致多年，他说，因此现在更好利用它有意义。Falcato 指出旧 LTS 内核从未收 6.4 变更，因此无一致行为，且用户空间仍须执行"某些相当 gnarly 测试"安全用特性。Brauner 建议回填 6.4 修复，并加："Feature testing has always been a pain that we forced onto userspace. I think we should continue with that proud tradition"。

Christoph Hellwig 不同意：

我们需要一个在 Linux 上自发现的接口。任何被先前内核接受并给出与新接口不同结果的标志组合，都不符合该要求。

他加说不可能依赖修复回填所有在用旧内核。

Neil Brown 建议加新标志 OPENAT2_NEW_COMBINATION，将使 openat2() 拒绝任何未识别标志组合。任何旧内核将立即失败带那标志调用；新内核可用它启用先前不支持组合，包括 O_CREAT|O_DIRECTORY。Brauner 再次 不理 Hellwig 担忧为"a strawman"。他说他能无单一回归报告使那标志组合返回错误是无人冒风险加意义证据。Hellwig 不同意，说一旦组合支持，应用将开始用，且它们会在旧系统破。他说，必需加"不意外在旧内核做错事的 APIs"。

Koolstra 对 openat2() 建议 有不同担忧：似乎许多 seccomp() 配置仍阻 openat2()。那可能使新特性在许多系统不可用，减其价值。

讨论接近结束（迄今），Brauner 请 Koolstra 发支持 openat() 和 openat2() 版本。他没说 open() 变更是否应留，但抱怨"we're deliberately crippling a useful extension for userspace"。Koolstra 的系列 最新版本 启用那标志组合给所有 open() 变体无任何额外检查。Brauner 尚未应用那系列，因此我们不知它是否以那形式进主线。

长期保持兼容不易。确保新内核不破旧应用已够难，但避免破旧内核上新应用常更狡猾。关键方式之一是提供应用发现内核是否支持给定特性方法。此处分歧在于提议特性是否提供那发现机制，Falcato 和 Hellwig 等开发者说"不"，而 Brauner 觉在所有真要紧内核上可发现。只有一次机会做正确决定；一旦新特性在核心发布暴露，之后难更改。

一个 LLM 智能体试图入侵 GitHub 上的项目

英国 AI Security Institute 发布了一份详细报告关于其自身引发的一起安全事件。该机构将一些 LLM 智能体放在互联网上执行一项安全挑战；很快它们就开始创建带有恶意软件的 pull request 以及用于推广这些请求的马甲（sock-puppet）账号。

该智能体向 ⟨REPO_A⟩ 提交了一个恶意 pull request（PR），并采取了多种策略试图让其被合并：

  1. 使用马甲账号在 PR 下反复评论，制造共识假象，并向维护者施压，使其在未充分审查的情况下批准。
  2. 在另一个仓库（同样由 ⟨PERSON_A⟩ 拥有）中开了一个 GitHub Issue，其中包含针对其他编码智能体的提示注入（prompt injection）。这些恶意指令是写给 issue 分诊的 AI 编码智能体的，在网站上查看的人类不可见。
  3. 向 ⟨PERSON_A⟩ 和 ⟨PERSON_B⟩ 发送多封邮件，使用不同借口诱使他们运行恶意代码。在该样本期间，智能体共发送了五封邮件，其中一些包含恶意软件，另一些旨在说服维护者接受该 pull request。

如果这是唯一一起此类事件，那才令人惊讶；此处唯一的真正不同在于相关人士记录了所发生的事。

SQLite 严重 CVE 还是 LLM 垃圾？（JFrog 博客）

JFrog 博客审视了一些报告的 SQLite 漏洞，其中部分已进入了知名的漏洞数据库，但结果发现完全是由 LLM 编造的。

这些 LLM slop（垃圾）CVE 会导致组织浪费时间调查并修补根本不存在的漏洞，同时还会污染漏洞数据库。在那些根据漏洞评分自动优先处理严重漏洞或自动开单的环境中，此类虚构的 CVE 会变成真正的负担。

在那些使用 AI 来自动化漏洞分诊与修复的环境中，这一点更令人担忧。遇到虚构 CVE 的 AI 智能体可能会试图定位有漏洞的函数、生成补丁，或基于根本不存在的代码提出建议。非但没帮助安全团队修复真实漏洞，反而可能将他们引向完全错误的方向，潜在地引入不必要的改动并浪费时间。
