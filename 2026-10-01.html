从 PostgreSQL 的视角看内核

作者：Jonathan Corbet 2026年9月29日 英文原文

Andres Freund 有几项令他成名的成就，但其中最突出的是他多年来为提升 PostgreSQL 关系型数据库管理系统（RDBMS）性能所做的工作。这项工作需要与 Linux 内核的众多特性与行为打交道——有时还得想方设法绕过它们。他出席了 2026 年的 Kernel Recipes，分享了自己与内核项目协作的经验、内核如何能更好地支持 PostgreSQL 这类应用，以及 PostgreSQL 领域里一些有趣的进展。

他先快速列举了自己在使用 Linux 过程中遇到的若干「有趣」经历，首先是 2018 年那件事的余波——当时人们发现内核在遇到 I/O 错误时可能会静默地丢失数据；他把这段经历称为「fsyncgate」。更近一些时候，io_uring 出现了一些会破坏多进程应用的问题；他特意说明，自己与 io_uring 维护者 Jens Axboe 保持着富有成效的协作关系，双方已共同解决了其中许多问题。他说，内核的改动不断带来层出不穷的 bug 和崩溃，必须逐一处理，还有各种随机出现的性能变化需要去排查定位。

他说，不知为何，处理这些问题最后总会落到他头上，也许是因为他喜欢操作系统相关的话题，而且负责 PostgreSQL 偏底层的部分。曾经有段时间，他以为阅读 linux-kernel 邮件列表能让自己变得更聪明；他补充说，眼下似乎也有「某种更新的技术」得出了同样的结论，引来了观众的一片笑声。他很幸运，遇到问题时认识一些可以请教的对的人，但他一个人分身乏术，无法总是跟上这些问题的节奏。

为什么没有更多 PostgreSQL 的人与内核开发者交流互动呢？他说，他们中许多人并不太了解 Linux，觉得自己不够格去提问。内核的沟通风格被认为带有威慑感；随着时间推移已有所改善，但人们依然不喜欢那种动辄挨骂的氛围。雪上加霜的是，当有人提出某个问题时，内核开发者常常会给出互相矛盾的说法；因此知道哪些人的意见可以忽略不计很重要。而且跟进内核的进展也很困难；他提到自己在本次会议早些时候才第一次听说 b4 这个工具。

PostgreSQL 正在发生什么

PostgreSQL 社区中有许多进展，可能会引起内核开发者的兴趣。该项目正缓慢地从以进程为中心的模型转向基于线程的模型（2023 年本刊曾报道过这一话题）。共享地址空间让许多事情变得更简单，而更好的转换检测缓冲区（translation lookaside buffer，TLB）利用率和更快的上下文切换所带来的性能收益也很有吸引力。从长远来看，该项目还希望把数据库连接与处理这些连接的进程或线程分离开来。

PostgreSQL 以使用缓冲 I/O 而闻名，而大多数高性能数据库系统则使用直接 I/O。但即便是 PostgreSQL，也在缓慢地转向异步 I/O 模型，而不再「仅仅靠页缓存来掩盖 I/O 延迟」。他一直在研究为此使用 io_uring，但 io_uring 很复杂，而令他惊讶的是，仅仅使用大量工作线程的模型也能有相当出色的表现。未来会有对直接 I/O 的支持（直接 I/O 需要异步 I/O 才能发挥良好性能），但它很可能永远不会成为默认选项。因为有很多系统都是 PostgreSQL 与其他应用一同运行，在这种情况下很难把直接 I/O 的使用调优到位。

他一直在试验原子写（atomic writes）——即保证整体成功或整体失败的多块写操作。但 Linux 目前只支持原子直接 I/O，而 PostgreSQL（尚）未使用它；他希望对缓冲原子写的支持能尽快就绪。他说，恰当的原子写支持将帮助 PostgreSQL 保持更小的日志（journal）。

他还试验了时间片延长（time-slice extension），但到目前为止效果并不算特别明显。在请求延长时间片时，线程能做的事情所受的限制对 PostgreSQL 而言过于严格，因此该特性无法在所有场景中使用。

好的与坏的

他说，Linux 内核中有很多「很棒的事情」正在发生。回写（writeback）与回收（reclaim）已经好了很多——提升了 2 到 4 倍。RWF_ATOMIC（用于请求原子写）的加入是一项巨大的改进，而 io_uring 在很多方面都很出色。但当然，也存在一些问题。

例如，可扩展性仍然常常是个问题。他展示了一张幻灯片（完整幻灯片可在此查看），说明了某个特定系统在客户端数量增长时（所处理的查询数量）的表现；可在右侧看到。这张图显示，性能会随客户端数量线性增长——但只到某个点为止。之后性能会下降并趋于平稳，直到客户端数量增长到远高于此，才大致回到原来的那条线上。

这里发生了什么？这个问题可以通过禁用 cpuidle 子系统来「解决」，这一事实是一条重要线索；负载不足以让 CPU 保持在高功耗状态，于是它们进入空闲状态，系统性能便遭到破坏。只有当负载增长到让 CPU 维持在高功耗状态时，性能才会重新回升。话虽如此，真正的问题很可能是若干独立因素相互作用的结果；他希望不久后能好好地把它写出来。

他说，无法对程序代码段（program text）使用透明大页（transparent huge pages，THP）这一点很让人头疼。READ_ONLY_THP_FOR_FS 这一变通做法有所帮助，但大多数发行版并未启用该选项，而且无论如何，内核开发者正在移除它。没有这项支持，性能会受损，而且很难得到一致的结果（这对基准测试而言很痛苦）。

PostgreSQL 使用 futex 在进程之间进行同步，但这里同样存在问题。futex 为应用信息提供 32 位空间，但对 PostgreSQL 来说不够用，因为它需要在那里存储更多状态。而且 futex 本身也不算快，内核内部的哈希查找在某些情况下会占用 25% 的 CPU。普通 futex 没有优先级继承（priority inheritance），会导致较大的尾延迟（tail latency），但支持优先级继承的 futex 又完全无法使用。它们提供的可用状态更少，而且虽然确实改善了尾延迟，但其内置的公平性机制会拖垮整体性能。由用户空间控制的有向唤醒（directed wakeups）若能实现，将带来相当大的帮助。

控制组（control group）中的内存耗尽（OOM）处理是另一个痛点。PostgreSQL 开发者喜欢在生产系统上设置 vm.overcommit_memory=2（这会禁用内存过量分配（overcommit），详情见该页面）。但除非整个系统都面临内存耗尽，否则该模式在控制组内并不奏效。这使得控制组对于那些希望以禁用过量分配方式运行 PostgreSQL 的管理员来说形同无用。

PostgreSQL 依赖于知晓检查点（checkpoint）数据的写入一定会成功，因此它会使用 fallocate() 提前在存储设备上预留空间。但这往往会造成碎片化，损害性能。在日志型文件系统（journaling filesystem）上，向以这种方式分配的磁盘区域进行的每一次写入，还可能引发日志写入，这同样会造成损害。还有一个问题：以这种方式分配空间在写时复制（copy-on-write，CoW）文件系统上并不奏效，因为后者会在被写入时重新分配空间。

他说，有些用户一直使用 1GB 大页来运行 PostgreSQL，但效果往往不尽如人意。如此大的页会在 folio 头部制造争用——主要是引用计数方面的争用——这可能让性能减半。

最后他说，io_uring 中的预留缓冲区（reserved-buffers）机制有助于性能，但它们对 I/O 操作施加了 1GB 的上限。这可能迫使 PostgreSQL 采用更小的写操作，从而造成损害。显然 Axboe 对于如何改善这种状况有一些想法。一个相关的 io_uring 问题是，ring 本身会计入进程的锁定内存（locked-memory）资源限制，而所需的量在不同内核版本之间可能不同，导致有时无法使用该特性。

结语

Freund 在结语中指出，有不少公司同时雇佣 PostgreSQL 开发者和内核开发者；人们自然会想，为什么其中的一些内核开发者不多帮帮 PostgreSQL 的问题。在他的雇主那里，PostgreSQL 团队自成一体，与公司其他部门互动不多；这意味着在争取其他资源来帮忙时，它缺乏影响力。他怀疑其他公司的情况可能也类似。

他说，PostgreSQL 或许有多种方式可以帮助内核项目。数据库遇到的许多问题并非 PostgreSQL 所独有；解决它们将惠及众多用户。PostgreSQL 开发者所做的测试（以及可以做得更多的测试）有助于在回归问题进入正式发布的内核之前将其识别出来。他还说，或许 PostgreSQL 开发者可以帮助内核社区找到一些更好的基准测试，用以识别更多真实世界中的性能问题。归根结底，PostgreSQL 和内核都是历史悠久的开源项目；它们有很多共同点，通过更紧密的合作可以获益良多。

Rust 在 GPU 上的原生支持

作者：Daroc Alden 2026年9月29日 英文原文

Christian Legnitto 是 rust-gpu 和 Rust CUDA 两个库的维护者，这两个库让人们可以用 Rust 为计算机的图形处理器（GPU）编写程序。不过，他对 Rust 目前 GPU 支持的现状并不满意。在 RustConf 2026 的一场演讲中，他阐述了自己的构想：如何让 GPU 成为普通 Rust 代码的一个寻常编译目标，无需任何特殊的库或新的生态系统支持。这一构想尚未完全实现，但他确实有一个正在准备发布的原型。

现状

现有的可以用 Rust 编写 GPU 程序的库有很多，包括 Legnitto 本人维护的那些。在他看来，它们的问题在于，它们从观察 GPU 的特性出发，试图在 Rust 中把那些特性表达出来。这确实行得通——这些项目能产出在生产环境中运行的优质代码——但当 GPU 与 Rust 的预期不一致时，就会产生摩擦。更糟的是，它把 Rust 生态割裂开来：为使用某个库而写的项目，通常与为使用另一个库而写的项目互不兼容。

目前面向 Rust 的 GPU 库似乎默认假定「GPU 很奇特」，需要特殊对待。Legnitto 不这么认为。他说：「问题在于，CPU 其实也很奇特，只是我们已经习惯了。」最近，他一直在探索一种不同的方法：从 Rust 优先（Rust-first）的设计出发，而非 GPU 优先（GPU-first）的设计。他的目标是尽一切代价保留 Rust 的原生语义，即便这会带来一些低效。其成果虽然仍处于实验阶段，却是一个能直接在 GPU 的并行硬件上运行普通 Rust 应用——包括那些并非为 GPU 使用而设计的库——的系统。

Rust 已经支持多种 CPU 架构，而每种架构都有自己的问题和怪癖。该语言的处理方式是：尽可能使用零成本抽象（zero-cost abstraction），在不可行之处则采用需显式启用的「逃生舱口」、针对特定目标的编译以及内联汇编。从很多方面看，标准库是对同一批基础概念的不同不兼容实现之上的一层门面。

他这项实验的计划是：凡是 GPU 能够合理支持的操作，都在 GPU 本身上完成；其余操作（例如文件系统交互等）则派发给宿主 CPU。标准库在 CPU 上已经是这么做的，只不过操作是派发给内核，而不是派发给另一块硬件。关键在于，Rust 应用代码无需知道、也无需关心它的请求是如何被处理的。

未来

需要更多斟酌的一个部分，是并发原语（concurrency primitive）的整合。GPU 比 CPU 更擅长的一点——也是人们使用它们的根本原因——在于硬件支持更高程度的并行。不过，Legnitto 认为 GPU 提供的并行性与典型 Rust 代码中进程、线程以及单指令多数据（SIMD）指令的运用能够很好地对应起来。

他说，要在 GPU 上运行代码，CPU 首先完成必要的配置，然后在 GPU 上「启动一个 kernel（内核）」。这可以看作一种进程，它在 GPU 上被分配了若干「block（块）」和「warp（线程束）」（后者是提供并发的更小硬件单元）。只要有不同的 warp 集合可供分配，多个 kernel 就可以同时运行。GPU kernel 与 CPU 进程的区别在于，kernel 会同时在其被分配的所有 warp 上运行；它并不是从一个特定的 CPU 核心上启动的。不过，有一个显而易见的补救办法：让除一个之外的所有正在运行的 GPU kernel 实例都「休眠」（进入忙等循环，因为它们无法像进程那样真正睡眠），然后再把执行权交给用户代码。Legnitto 承认这种方案效率不高，但认为问题不算太大。

Legnitto 说，warp 这样的硬件组成部分并不强制要求使用并发。它们只描述可达到多大的并发程度，而代码本身仍掌控着并发的实际使用方式。凡是通常用进程来做的事情，都可以通过启动一个 kernel 来实现：「它有生命周期，多个可以并行运行，还有堆，等等。」kernel 甚至可以通过请求 CPU 代为启动，来创建新的 kernel。因此，Rust 代码期望能用进程完成的一切，都可以用 kernel 启动的方式来实现。

类似地，GPU warp 基本可以承担线程的角色。它们拥有共享内存、程序计数器、栈、线程局部存储（thread-local storage）等。唯一的区别是，warp 无法创建新的 warp，因为 warp 是一块物理硬件，其数量是固定的。解决办法是利用在 kernel 开始执行时进入休眠的那些其他 kernel 实例。想要派生（spawn）一个新线程的 warp 会把一个函数指针推入一个共享列表，然后设置一个标志，由那些忙等中的 kernel 实例来检查。其中一个实例会取出该函数指针并调用它。这样一来，尽管 warp 的实际数量是固定的，也可以让数量动态变化的 Rust 线程在它们之上被调度执行。

最后，CPU 的 SIMD 指令与 GPU 的「lane（通道）」完美对应——lane 是 GPU 中最小的并行硬件单元，能同时对多个输入应用同一个简单操作。在 CPU 和 GPU 上，它们都代表最低层次的并发，其硬件宽度固定，所支持的操作也有限（大多是数学运算）。唯一真正的区别是 GPU 往往更宽，但 CPU 的 SIMD 指令宽度也各不相同，因此 Rust 编译器本来就需要处理这种情况。

随后，Legnitto 展示了一个示例，说明采用这种方法为 GPU 编写的 Rust 代码会是什么样子。截至本文撰写时，他尚未公开自己的幻灯片，但一个派生线程并使用 SIMD 内建函数（intrinsic）一次性完成四对数字相加的简单示例如下：

fn example() {
    let handle = thread::spawn(|| {
        let a = i32x4::from_array([10, 20, 30, 40]);
        let b = i32x4::from_array([1, 2, 3, 4]);
        let result = a + b;
        println!("SIMD Result: {:?}", result.to_array());
    });

    handle.join().unwrap();
}

同样的代码不改动就能在 CPU 上运行。真实的代码通常会派生更多线程并用它们做些更有意思的事情，但基本操作是相同的。

他说，从理论上讲，这种方法并不比现有方法慢。一个派生出多个、且都开始使用 SIMD 的线程的 Rust 程序，其性能应当与手写的 CUDA 代码相当。真正的好处在于，「普通的 Rust 东西」可以直接奏效。现有的库和语言特性都可以照原样使用，并能在合理之处通过逐步采用线程与 SIMD 来提升性能，这同样也会让在 CPU 上运行的用户受益。对于真正关键的性能段落，仍然可以下探到内联汇编，直接为 GPU 编写代码。

Legnitto 说，这也意味着所有 Rust 程序员一夜之间都成了 GPU 程序员，无需学习任何新东西。他接着说，如果像他这样的提案能够落地，Rust 将成为全世界最大的 GPU 生态。

这并不是说这种方法没有缺点。对某些硬件而言，可能存在与 Rust 模型不兼容、但更好的 GPU 程序组织方式。此外，如果原本为 CPU 编写的库也能用，这可能会打消人们编写更好的 GPU 专用库的积极性。编译后二进制文件的大小也可能是个问题；与整个 Rust 应用相比，大多数 GPU 代码都短小简单。他说，这些年 GPU 代码已经变得更加复杂，所以他确实认为所有 GPU 都将不得不处理更大的程序——而 Rust 应用只会立刻撞上这个问题。

改进语言

在 GPU 上采用 Rust，也有可能推动一些在别处同样有用的语言特性的设计与采纳。例如，一种「disjoint slice（不相交切片）」类型，允许引用数组的多个互不重叠的部分，这在 GPU 和 CPU 上都会很有用。Legnitto 声称，标准库对张量（tensor）和矩阵乘法的支持，是 Rust 无论如何都可能迟早需要纳入的另一个领域。「某样东西在 GPU 上有用，并不意味着它就只针对 GPU。」

归根结底，Legnitto 认为，在 Rust 中一等公民地支持 GPU，对这门语言的未来至关重要。越来越多的软件在使用 GPU，而更新的 CPU 设计也在不断融入类 GPU 的元素。他说，竞争性的软件生态永远都会存在，而那些在 GPU 或类似 GPU 的 CPU 核心上运行不佳的软件将处于劣势。

之后有短暂的提问时间。一位观众问道，那些针对 CPU 优化过的编译器，是否真能生成运行良好的 GPU 代码。Legnitto 承认，面向 GPU 代码的自动向量化（auto-vectorization）仍然「相当粗糙」。不过，考虑到这是 LLVM 首次以这种方式被应用，这也是意料之中的。他说，未来还会有更多优化，把性能提升到与现有 GPU 工具包相当的水平。

桌面 / KDE

Plasma 的这一年与未来展望

作者：Joe Brockmeier 2026年9月30日 英文原文

过去一年里，KDE Plasma 桌面环境发生了很多事情。大部分时间都投入在 Plasma 上的 KDE 贡献者 Marco Martin 在奥地利格拉茨举行的 Akademy 2026 大会上登台演讲，介绍了 Plasma 的主要新特性、一些虽小但有趣的改进，并预告了即将到来的变化。最受关注的一项即将到来的变更——从 Plasma 中移除 X11 支持——早已广为宣传；但此外还有进一步改进远程桌面支持等计划。

数字

Martin 被介绍为在 Plasma 开发中长期活跃的贡献者之一。根据这篇访谈，他从 2007 年开始贡献。不过他来到 Akademy 并不是为了谈论自己过去在 Plasma Netbook 等项目上的工作；他想聚焦于 Plasma 过去一年的开发，以及自 Akademy 2025 大会以来发生了多大变化。

他说，在这段时间里，他打算谈论的版本大约有「四个小数点版本」：从 2025 年 6 月发布的 Plasma 6.4，一直到 Plasma 6.8。6.8 计划于 10 月中旬发布，以配合 KDE 30 周年纪念。6.8 的第一个 beta 版已于 9 月 10 日发布。

他先用「一些无聊的数字」来量化概述自去年以来完成了多少工作。Martin 首先给出了已处理 bug 的数量：共有 5286 个 bug 报告被关闭为「RESOLVED」，但这其中包含重复项、无效 bug 等。总共有 1681 个 bug 以「FIXED」状态关闭。当然，这些是贡献者确认存在问题并成功解决的 bug 报告。

Martin 说，他使用 GitLab API 统计了过去一年 Plasma 组下五个项目仓库创建的合并请求（merge request）数量：KWin、Plasma Workspace、Plasma Desktop、Discover 和 Union。Plasma 组下还有许多其他仓库，但这些是 Martin 认为最能代表 Plasma 整体开发的仓库。合并请求总数达 7903 个。Plasma 桌面的 KWin 窗口管理器获得的关注最多，有 1847 个合并请求，「因为它是一个非常核心的部分 [...] 如果它不工作，你的屏幕就什么也显示不出来」。

KDE 应用的 Union 样式引擎排在列表最末，有 261 个合并请求——但这个数字可能具有迷惑性。Union 是 KDE 相对较新的成员；Arjen Hiemstra 于 2025 年初引入它，该样式引擎首次随 KDE 6.7 发布。Martin 说，Union 在解决为所有 Qt 和 QML 应用提供一致可视化界面这一问题上很重要。他指出，过去一年它获得了大量关注，包括许多用户界面和可用性方面的改进，以及性能提升。Hiemstra 在 5 月的更新很好地概述了 Union 在被纳入 Plasma 6.7 之前所做的工作。

在打开的 7903 个合并请求中，共有 6556 个被接受，约占 82%。不过 Martin 警告说，他开始看到「纯 LLM 生成的合并请求有所增加」，其中描述和代码明显完全由 LLM 生成，「而提交它的人并不真正知道这个补丁做什么」。他说目前「还不算多」，但他认为有必要制定一份明确的 AI 政策，让维护者有可依赖的准则，并能引导潜在贡献者参考。Nate Graham 已开始制定这样一份政策，但在该政策成为网上批评的众矢之的后，似乎已被放弃。他或其他 KDE 贡献者是否会重新拾起，尚不清楚。

有什么变化？

「这些只是数字」，Martin 说；他想看看 Plasma 和 KWin 中引入的一些新特性，并「完全随意地」挑选了一组变更来谈，从 Plasma 6.5 开始。Plasma 长期以来就有浅色和深色主题；6.5 版本引入了自动切换主题的能力，白天使用浅色主题、夜间使用深色主题。用户可以将其配置为根据设备位置在日出和日落时自动切换，或选择在一天中的某个时刻从深色切换到浅色，再切回来。

6.5 中另一项改进是在使用远程桌面协议（RDP）时，本地与远程桌面之间可共享剪贴板。例如，用户可以在本地桌面会话中复制文本，然后粘贴到远程会话的应用程序中。Martin 提到还有许多「细小的体验修复（paper-cut fixes）」，比如 Sticky Notes 小组件的视觉改进、Folder View 小组件的若干更新等。

KDE 剪贴板新增了一项功能，允许用户创建二维码将文本分享到移动设备；将文本复制到剪贴板后，用户可以选择「显示二维码」，然后用手机或其他移动设备扫描该二维码，即可将文本复制到移动设备的剪贴板。

新的键盘

Martin 在 Plasma 6.6 中讨论的第一项变化是 Plasma Keyboard 的正式发布，这是一款面向触摸屏的虚拟键盘。它取代了 KDE 一直使用的「老旧且维护不佳」的 Maliit Keyboard。「所以现在我们有了一个自主研发的虚拟键盘，想怎么改进就怎么改进。」

Plasma 有许多时钟小组件供用户选择。过去每个时钟小组件各自独立实现类似功能，而 6.6 引入了一个新的 libclock 库，帮助减少了代码重复，Martin 对此很满意。「我真的很喜欢合并请求里红线比绿线多。那才是最好的合并请求。」用户很可能也会欣赏另一项移除：Plasma 的系统设置将不再为不存在的硬件显示 KDE 配置模块（KCM）页面。以前版本的 Plasma 例如会在系统没有相应硬件时仍显示 Thunderbolt 设置页面——这可能会让用户困惑。

6.7 中加入 Union 样式引擎，将使开发者在处理样式时轻松许多，无需再使用 Qt 的 QStyle 来实现主题。「编写它简直是一种可怕的体验。成千上万行 C++，谢谢，不用了。」相反，开发者可以用 CSS 来为 Plasma 应用等设置样式。Martin 特别感谢了 Akseli Lahtinen，他「忍受了实现一个能理解 Union 主题的 QStyle 的痛苦，这样其他人就再也不必碰 QStyle 了」。

Martin 还再次强调了 6.7 中许多细节修复，例如在使用多屏幕时更好地自动隐藏面板。他说，新虚拟键盘获得了更精细的控制，用户可以配置它仅在设备处于平板模式时出现，或在使用触摸屏或鼠标时出现。

6.8 即将到来

他说，6.8 有大量工作，这个即将发布的版本的第一大亮点是「不是我们新增的东西，而是我们移除的东西：X11 支持即将消失」。在 Martin 说完后，观众报以长时间掌声。这并不令人意外，因为 Plasma 团队已于 2025 年 11 月宣布了这一消息。Martin 说，移除 X11 相关代码将简化 Plasma 面板、任务栏等特性的维护，「这也有望意味着[它们将]少很多 bug、稍微快一点，诸如此类」。

「我们还在加载壁纸时省下了一些微秒」，他说，「这实际上很重要，因为你可能有三块屏幕，各用一张 4K 壁纸」。更快的壁纸加载意味着 Plasma 启动更快。Union 样式引擎在 6.8 中继续推广，增加了对 Qt widgets 的支持。「它还不完美」，Martin 说，但正在逐步完善。他认为 Plasma 的默认主题 Breeze 可能在一两个版本内完全基于 Union。

有一项工作不会在 6.8 版本中显现，但日后会带来回报，那就是将 Plasma 的许多 KCM 移植到 Kirigami 用户界面库（用 KDE 的术语来说是 Framework）。他说，当所有 KCM 都移植到 Kirigami 组件后，就可以「一次性大规模重新设计样式」，为 KDE 系统设置应用及其他地方使用的配置模块提供更现代的外观。

Martin 还快速介绍过去一年多里 KWin 出现的一些新特性。他指出其屏幕镜像功能有了「很大改进」，但未详细说明。在 6.6 版本中，KWin 获得了仅通过远程桌面共享虚拟屏幕的能力，这允许仅通过 RDP 会话出现的虚拟屏幕使用不同的色深、刷新率等。

他说，Wayland 上 Plasma 一直缺失的一件大事是会话恢复（session-restore）协议；这是许多 X11 用户特别看重的东西，终于在 6.7 版本中出现。「现在，当你从 Plasma 登出时，可以选择『保存我所有的窗口』。在 Wayland 上我们之前做不到，现在可以了。」

KWin 6.7 还新增了从一块屏幕独立于另一块屏幕切换虚拟桌面的能力；在该版本之前，虚拟桌面的切换总是在所有显示器之间同步。「这是我见过的让最多人开心的一项功能。」他说，「各种 Linux YouTuber」都在谈论它，「所以这很好，因为显然它让许多用户开心」。他还补充说，KWin 在多 GPU 支持方面也有「一些改进」，这对同时拥有 Intel 和 NVIDIA GPU 的笔记本电脑很有用。

提问环节

Martin 留出了充裕的时间用于提问。一位参会者问他，认为 Plasma 用户最头疼的问题是什么。Martin 说，其中之一是某些领域「仍有一点复杂感」。他说 Plasma 和 Dolphin 等主要应用的默认设置都很好，但如果用户进入设置去修改默认值，「所有复杂性又会一下子全砸到你身上」。他希望能让用户在「稍微偏离默认」时更轻松。他还补充说，多屏幕设置仍然不是「完美、完美、完美」。

另一位观众想要一个具体例子，说明移除 X11 如何让 Martin 的工作更轻松。Martin 说，例如 Plasma 面板中有大量复杂性。「我们在 X11 和 Wayland 上有两条完全不同的代码路径来管理定位、自动隐藏等等」，这相当于同一批功能有两套完全不同的实现，意味着代码「非常不优雅」。他还提到多显示器设置和管理屏幕配置变更的复杂性，涉及不同的代码路径。「只有在 Wayland 那一套上，我们才能做一个漂亮且高度可复现的自动化测试。X11 那套有点『凭感觉』。所以现在这些代码都死掉了，我非常高兴。」

C 语言 / 内存安全

减少 C 语言中的未定义行为

作者：Jonathan Corbet 2026年9月28日 英文原文

作为一名生物医学工程教授，Martin Uecker 或许并不符合 Kernel Recipes 演讲者的典型形象。但他是一位长期的 Linux 用户，从事用于控制磁共振成像（MRI）扫描仪的自由软件工作。他来到这次会议，是为了谈论 C 编程语言、C 中未定义行为（undefined behavior）这一具体问题，以及它最终能否被改造成一门内存安全的语言。

为什么在 2026 年还要费心用 C？他说，它仍然是一门很棒的语言。C 可移植、长期稳定、编译速度快，生成的二进制代码也快。「所见即所得」；很容易看着 C 代码就对计算机实际会做什么有所了解。有大量处理这门语言的工具，而且在必要时 C 不会挡路。

他说，C 有着悠久的历史，这影响了我们今天所看到的这门语言。C89 标准必须应对种类繁多的硬件，包括采用符号-数值（signed-magnitude）或反码（one's-complement）整数表示的机器、分段内存、奇特的指针表示，以及出人意料的各种类型大小。例如，某些 Honeywell 机器的字节有 9 位。这极大地增加了编写一份能支持可移植代码的标准的难度。

所采取的方法是用抽象机（abstract machine）来定义语言的语义。所有操作都要按照在抽象机上运行的方式来执行，而抽象机可能并不与真实硬件完全一致。程序的可观察行为必须与抽象机会做出的行为一致。「可观察」这一点很重要：对 volatile 变量的访问被定义为可观察的，必须严格按抽象机的方式发生；其余一切只需产生相同的最终结果即可。

标准给了编译器实现者很大的自由；只有可观察行为必须被保留。该行为中有许多方面要么是未定义的，要么是实现定义的。这些不是可观察行为，因此不约束编译器实现者能做什么。当然，在 C 标准未约束之处，还有其他规范可以约束编译器开发者；这些包括 ABI 要求、POSIX 之类的标准，或向后兼容的需要。

未定义行为出现在程序做了要么不可移植、要么标准根本未定义的事情时。在这种情况下，C89 标准规定它对实现「不施加任何要求」。未定义行为的存在有多种原因。它允许实现支持扩展、管理与基于硬件的安全机制的交互，并执行激进的优化，同时允许忽略难以检测的错误。它明确赋予编译器忽略整类难以检测错误的权利。

鼻魔（Nasal demons）

Uecker 说，问题在于标准允许编译器对未定义行为做出任何反应，直至召唤「鼻魔（nasal demons）」。按照编译器作者的说法，如果程序包含任何未定义行为，它就没有预期的语义。C++23 标准更进一步，明确规定标准对这些程序不施加任何要求。这导致开发者之间就这门语言能期望什么产生了广泛的分歧。

例如，如果你把整个结构体清零（也许通过调用 memset()），然后写入特定字段，那么读取该结构体中任何填充字节时会发生什么？它们可能包含与安全相关的数据吗？一项 2015 年的调查显示，对于这种情况应该发生什么，并没有共识。或者考虑这段简单的代码：

extern int x;

int f(int a, int b)
{
    x = b ? 42 : 43;
    return a/b;
}

如果 b 为零，那么 return 语句就是除以零，属于未定义行为。在这种情况下，编译器是否有权完全省略这个测试，直接执行 x = 42？毕竟，b = 0 的情形没有预期语义，因此可以被忽略。确实有编译器会这么做。在未定义行为的情形下，对 x 的写入不是可观察行为。但现在考虑这种情况：

extern void g(int x);

int f(int a, int b)
{
    g(b ? 42 : 43);
    return a/b;
}

这看起来可能是同样的情况，编译器有权移除测试并直接向 g() 传入 42，有些编译器也确实这么处理过——但这种编译器行为是一个 bug。想象一下 g() 的定义在 b 为零时调用 exit()。那样的话除法永远不会发生，程序的行为也不是未定义的。因此，忽略测试并直接向 g() 传 42 是不正确的。

再来看一个有趣的例子：

volatile int x;

int foo(int a, int b, bool store_to_x)
{
    if (! store_to_x)
        return a/b;
    x = b;
    return a/b;
}

这里的问题是：编译器能否把最后的除法操作提升到对 x 的赋值之上？如果 b = 0 的情形没有关联语义，那么可观察行为就没有变化。这也是编译器曾做过的事，但 C23 标准增加了「禁止时间旅行（no time travel）」的规定来禁止它。而在 C++ 中，则必须通过插入对 std::observable_checkpoint() 的调用来显式阻止这种提升。

时间旅行 bug 最终应该会消失，但还有许多其他情形，即使标准是明确的，编译器作者也常常意见不一。这些包括读取未初始化变量（这几乎总是有定义的），以及指针的相等比较，这总是有定义的，但 Clang 和 GCC 都会错误地编译它。

对抗未定义行为

为了解决所有这些问题及其他问题，C 委员会设有三个专门研究内存对象模型、内存安全和未定义行为的研究组。目前 C 标准中约有 100 处未定义行为，但进行中的 C2y 草案已移除了其中 45 处。情况确实在好转。

旨在发现问题的工具日益丰富：编译器警告、静态分析器、sanitizer、基于 LLM 的工具、形式化验证等。在检测到可能的未定义行为时，编译器发出警告的情形越来越多；近期的例子包括对整数溢出和潜在 use-after-free 情形更好的警告。静态分析器可作为独立工具使用，但也越来越多地被内置到编译器中；例如 GCC 现在能对许多潜在的缓冲区溢出情形发出警告。Sanitizer 通过插入运行时检查来工作；它们能捕获大量未定义行为，并且在 trapping 模式下还可用于加固。

内存安全从来不是 C 的强项，但 Uecker 想说明它是可以改进的。这个问题可分解为三个子问题：类型安全、空间内存安全和时间内存安全。

他说，C 有强类型系统，剩余问题是可以修复的。例如，无标签联合体（tagless union）可能造成类型混淆，但编译器可以通过一些额外的注解来强制类型。新的诊断信息可以捕获来自 void 的不安全强制转换。在 C 中，跨翻译单元的类型检查传统上不是大问题，因为头文件被用来确保类型一致，但借助链接时检查器可以改善这种情况。

空间内存安全——边界检查——是一个已部分解决的问题；编译器现在能在许多情况下执行数组边界检查。在某些情况下，需要修改一些代码才能充分受益于这种检查。例如，使用 counted_by 属性可以为柔性数组成员启用检查。

Uecker 说，时间内存安全——避免 use-after-free 之类的 bug——更难，Rust 在这方面确实有优势。尽管如此，更好强制执行时间内存安全仍是可能的。CHERI 之类的架构在这方面也有帮助。Fil-C 能发现大量时间安全 bug。

所有这些工具和语言改动能让我们实现完全的内存安全吗？他说，要彻底解决这个问题，要么需要昂贵的运行时检查，要么需要形式化验证。在不久的将来，最完整的结果将来自受限语言与形式化验证工具的结合。

总的来说，他总结道，C 仍然是一门有生命力的语言，仍在不断改进。C23 标准移除了许多有问题的特性，包括旧式（K&R）函数定义、对符号-数值和反码机器的支持，以及三字符组（trigraph）。它增加了位精确（bit-precise）整数类型、带检查的整数运算等。C2y 会更进一步，新增 case 范围、具名 for 循环、用于确定数组长度的 _Countof() 宏，以及大量「恶魔清除」。它不会为 C 实现完全的内存安全，但这是最终可能实现的事，并会随时间推移变得越来越实用。他最后鼓励感兴趣的人参与这些工作组。

软件无线电 / Rust

用 Rust 收听无线电

作者：Daroc Alden 2026年9月24日 英文原文

无线电频谱中传输的许多信号，都可以用一款相对廉价的硬件 dongle（接收棒）来解码。Thomas Eckert 在蒙特利尔举行的 RustConf 2026 上介绍了他的业余爱好：用 Rust 解码无线电传输。在演讲中，他讲解了上手软件无线电（software-defined radio）所需的全部数学知识，并演示了收听 AM 和 FM 广播，以及解码飞机应答机（transponder）发出的信号。他的幻灯片和示例代码已发布在 GitHub 上。

Eckert 表示，他所有的演示都依赖同一条基本流水线。随后他运行了一个程序，开始接收来自蒙特利尔皇家山（Mt. Royal）的一座 FM 电台。那个信号最初是施加在发射天线上的电流，它推动金属中的电子来回运动。变化的电场意味着变化的磁场，反之亦然；这个不断变化的场穿过空气传播出去，直到抵达他的天线。在 FM 和 AM 广播演示中，天线夹在讲台侧面；而在飞机演示中，由于使用的是不同的波长，天线被架在屋顶上，数据通过一台 Raspberry Pi 转发——会议主办方允许他把这台设备放在那里。

Eckert 解释说，天线会一次性接收整个无线电频谱，但不同天线对频谱的不同部分更为敏感。一般来说，对于简单的线状天线，理想长度是无线电信号波长的四分之一。他刚才短暂调谐到的那座 FM 广播电台，波长约为三米，因此理想天线长度为 77 厘米——正是他把讲台上那根银色可伸缩天线拉到的长度。而对于飞机应答机，理想长度则降到大约五厘米。

无论长度多少，接收天线中的电子都会随入射无线电波同步振荡，从而产生电流。Eckert 使用的软件无线电 dongle 是 RTL-SDR Blog V3，一款 30 美元的小设备，一侧是 USB 线，另一侧是同轴天线电缆。它对这股电流采样，把模拟波形转成数字数据。它还带有一个调谐电路，一次只聚焦于无线电频谱中相对狭窄的一段。dongle 输出的数据是一串成对的数字。这些数字代表无线电波中互相垂直的两个独立分量：一个余弦波（也称「同相分量」，in-phase component）和一个正弦波（称为「正交分量」，quadrature）。dongle 以连续的无符号字节流形式提供它们。代码会将其居中并缩放，得到介于 -1 与 +1 之间的浮点数。把它们组合成一个复数，就得到了「I/Q」信号。一个 I/Q 采样点到原点的距离就是幅度（amplitude），而相邻采样点绕原点旋转的速度则是频率（frequency）。

Eckert 说，dongle 里的硬件使用的芯片原本是为电视接收机设计的。它只把信号按其原样数字化；它没有任何用于检测幅度调制（AM）或频率调制（FM）信号的电路。信号的全部解码都发生在代码里。

解码具体是什么样子，取决于正在解释的是哪种信号。dongle 每秒产生数百万个采样点，覆盖无线电频谱中 960 千赫兹的一段。举例来说，这个带宽足以并排容纳五个 FM 频道。要只聚焦于某一个电台，代码需要分离出某个特定频率分量来分析。实践上，这意味着使用一个低通滤波器（low-pass filter）来衰减掉不感兴趣的信号。对于最简单的那种 AM 广播，音频随后被编码进信号幅度的变化中。每个采样点被转换成到原点的距离，然后整个信号被平移并重新缩放，以落入声卡所期望的信号范围。之后，数据就可以放进供声卡使用的环形缓冲区（ring buffer），直接播放出来。

FM 广播则稍微复杂一些：其数据来自频率的变化。因此，解码实现必须考察前一个采样点与当前采样点之间的相位（角度）差。这份数据可以重新缩放并直接播放，但听起来会刺耳而单薄。这是因为 FM 对信号中的细微变化更为敏感，往往引入更多噪声，尤其是在高频声音上。因此，FM 广播电台会提升信号中的高频（treble）分量来盖过噪声，而收音机接收端则必须撤销这一变换，以还原原始声音。在北美这一提升值是「75 µs」，在欧洲则是「50 µs」。这个度量实际上并不代表一个时间偏移；它只是一种约定俗成的简写，用来描述如何调校一个电阻—电容（resistor-capacitor）电路以塑造信号。不过，一旦对提升做了校正，输出就可以再次直接作为音频采样使用。

Eckert 接着解释道，他之所以选择 Rust，是因为这个 dongle 每秒提供超过一百万个采样点，因此每个采样点他只有一微秒的时间来完成任何必要的分析。而声卡会不断从环形缓冲区播放采样——无论是否已经提供了新的数值——这是一个实时任务，要求使用具有良好且可预测性能的语言。哪怕仅仅暂停几毫秒，都会在输出中造成可听见的空隙。他说，用 Rust 处理这样一条简单的解码流水线，过程很愉快。

他想分享的最后一个演示是观察一个数字信号，而非模拟信号。每一架装有广播式自动相关监视（automatic dependent surveillance-broadcast）应答机的飞机——也就是绝大多数飞机——每秒会广播两次遥测信息。这些数据以 1090 MHz 的频率发送，需要一根对天空视野良好的小型天线。该信号像 AM 广播一样是幅度调制的，但它传达的不是声音，而是由数字脉冲构成的模式。每条消息以一个可识别的、持续八微秒的前导码（preamble）开始，总共持续 120 µs，编码 112 位。每一位持续一微秒，并被分成两部分，称为半时隙（half-slot）。从高到低的跳变表示 1，从低到高的跳变表示 0。这样一来，无论是高还是低的恒定信号，都不会被解释为真实数据。

在 Eckert 的 dongle 可采样的最高频率 2.4MHz 下，每个半时隙只有 1.2 个采样点宽，这正好处在他能正确解码的信号的边界上。他的代码在信号上扫描，寻找与前导码匹配的内容，然后对每一位的两个半时隙进行采样并相减，以消除信号中的任何恒定偏置（bias）。随后，得到的比特被解析进一个 Rust 结构体，该结构体封装了各种可能的消息类型。代码再把这份结构化数据发送给一个小型 Web 应用，该应用把收到的信息绘制在地图上，显示每架飞机的身份、位置和速度。

不过，Eckert 说，他第一版解码逻辑效果并不好；它只能找出信号中大约六分之一的信息。要做出一个对干扰和采样误差都稳健的实现，需要大量思考。他解释说，这正是这项爱好之所以有趣的一点：有太多东西在使用无线电频谱，这意味着永远都有新东西可看。对模拟信号的基本解码足够简单，不用费太多力气就能跑通，但你总可以更深入地研究更好的解码方法，或者去观察新类型的信号。

到目前为止，Eckert 已经尝试过接收 AM 和 FM 广播、授时同步信号以及飞机应答机，但外面的世界远不止于此。还有天气预报（连带着天气图）、偏振调制（polarization-modulated）数字信号、HAM 业余无线电，以及更多更多。上手所需的全部家当，不过是一款相对廉价的硬件 dongle、一点关于复数的实用知识，以及一门编程语言——在他这里是 Rust。

KDE 如何获得资金来添加企业级功能

作者：Joe Brockmeier 2026年9月25日 英文原文

主权科技机构（Sovereign Tech Agency，STA）正通过 2027 年向 KDE 投资近 130 万欧元。在奥地利格拉茨举行的 Akademy 2026 上，帮助促成这笔投资的两名贡献者 Nate Graham 和 Kevin Ottens 解释了资金是如何争取到的，为各项目应如何接触 STA 这类机构提供了建议，并谈到了这笔钱将如何为所有人改进 KDE。除了让社区了解这些工作之外，两人还希望把他们学到的经验传授出去，以鼓励其他人也帮助为开发筹集资金。

Graham 是一家专注于 KDE 的软件开发咨询公司 Techpaladin Software 的共同所有者和 CEO，该公司专门承接 KDE 相关的工作。他说自己还撰写「This Week in Plasma」博客，做其他 KDE 推广工作，并尽可能多地继续做软件开发。Ottens 自 2000 年代初就参与 KDE，是一家软件开发机构 enioka Haute Couture 的技术负责人、经理和合伙人。

事情是怎么开始的

Graham 说，STA 对 KDE 的资助是该项目的长期以来最大的一笔外部投资之一。来自 STA 的资金并不是「必需品」，他说：「我们在座的各位多年来一直在做着了不起的 KDE 事情。外部投资的目的不是让我们所做的事成为可能，而是加速它。」他希望通过分享他和 Ottens 学到的经验，「你们所有人都能受益，去为 KDE 争取到多得多的外部投资」。

在 Techpaladin 这边，寻找资金的起点是 Harald Sitter 创建的 KDE Linux 项目。Graham 说，公司内部以及更大社区里有很多人都对 KDE Linux 及其在未来改变 KDE 的潜力感到兴奋。「我们意识到，要实现我们为它设想的宏伟目标，需要更多来自外部的投资。」

Ottens 说，他的公司也在做与 KDE 相关的项目。它收到的需求往往集中在 KDE Plasma、Frameworks 和办公应用上；然而，来自客户的与 KDE PIM 相关的需求并不多。KDE PIM 提供 Kontact 应用套件，其中包括 KMail 电子邮件客户端、KOrganizer 日历与待办管理器，以及该套件所使用的一系列库。

「但事实证明，我们喜欢 KDE PIM。我们和它有一段历史渊源。我们中的一些人过去甚至在业余时间都为它做过贡献。」

Ottens 说，它曾经很受欢迎，「但我们看到人们正在放弃［它］，转而使用 Thunderbird」。因为 enioka 的人喜欢 KDE PIM，他们一直在讨论如何找到资金，重新专注于它的开发。他们最初向 NLnet 基金会申请资助，作为试水之举，但没有成功。

Ottens 说，enioka 决定为 STA 准备一份提案，随后通过与被支持 KDE 的非营利组织 KDE e.V. 董事会的讨论，他们了解到「有更大的事情正在酝酿」。「于是我们想，我们应该联合起来」，与 e.V. 和 Techpaladin 一起。

提案

Graham 说，社会关系是争取资金过程中重要的一部分。STA 位于德国，在那里 KDE 已经是一个声誉良好的成熟机构，所以 STA 早已了解 KDE。「他们也喜欢［KDE］，因为我们做出了不起的工作，而且我们既友善又好相处。」STA 的人被邀请参加了 2025 年的 Akademy，这开启了关于资助的对话。

各方希望找到一个角度，既能资助 KDE Linux 的工作，又能资助 KDE PIM 的工作；经过一番讨论后，很明显，更大型的机构才最关心操作系统和 KDE PIM 中的生产力软件。「如今大多数孩子只是在手机上用 Gmail，但公司关心这两个话题」，Graham 说。「不只是公司，还有更大型的机构」——那些拥有受管环境、希望一切都易于搭建、并且「不会被技术可能不太过硬的普通用户弄坏」的机构。

于是这就引出了提案的愿景：聚焦于更大规模的部署，即企业向其员工发放运行基于镜像的 KDE Linux 发行版的笔记本电脑，并由移动设备管理（MDM）系统进行配置。这些系统会在员工首次开机、输入电子邮件和密码后自动完成配置，包括邮件、日历和默认应用。

Graham 说，一旦团队有了为更大规模部署改进 KDE 的愿景，就到了明确将要提出的具体工作的时候了。

这是真正困难的部分，因为拥有一个想做什么的愿景很容易，但把它分解成一系列可执行的步骤以及具体的项目和工作包，可能非常具有挑战性。所以这花了很长时间。我们必须把一切都组织得看起来合理可信，让目标显得可以实现。

他说，为每个可交付成果估算工作量并附上价码，是一项巨大的投入，但这是必要的，用以表明申请资金的团队「有能力调动那些正在做这项工作的人的技能」，并且有能力交付成品。

Ottens 描述了确定需要做哪些工作、然后估算其成本的过程。项目愿景以一组要点表示，指明了「工作包」将是什么。下一步是把工作包拆分成任务，然后可以对任务进行评估，估算工作需要多长时间。

到了计算估算值的时候，「这通常就是我们开发者大喊着冲出房间的时候」。但事情不必如此；有一些技巧能帮上忙，比如三点估算（three-point estimates）。他说自己有一个模板电子表格，用来大致了解任何任务需要多少工作量。与前面的阶段不同，这一步需要做一些「轻量研究」，弄清实现某个东西需要什么：「你不必真的去做实现工作，但你需要进入分析状态。」

对每个任务，他都做三点估算来得出实现成本，从而根据最佳情况、最差情况和最可能情况，得出完成一个任务所需的时间。举例来说，他可能估算出为 KDE PIM 中基本的 CalDAV 支持编写一整套测试，在最可能情况下需要五天，如果一切顺利只需三天——而如果出问题则要七天。

Ottens 解释说，他会和另一个人一起做分析，以帮助挑战自己的假设，并且他会留意其他人估算中的模式，这些模式可能表明他们偷工减料了。他说，有些开发者可能只是给出他们预计某项工作所需工作量的估算，然后把这个数字除以二作为最佳情况，再乘以三作为最差情况。

他说，STA 并不要求 Ottens 习惯产出的全部估算，但他们确实希望提案提交者提供成本估算。他说，STA 提供了一份他遇到过的「最友好」的提案模板之一。该机构有意确保其资金有助于公共利益和社区，而它的模板正是为帮助论证这一点而设计的。

这不是把关设卡。他们希望你能成功，主权科技机构的工作人员实际上会尽其所能帮助你达成目标。我没有感觉到我们是在自己的角落里做自己的事、然后努力向他们证明它的合理性，对吧？真的感觉像是我们在共同完成这份提案。

最终，提案被 STA 接受。尽管有多个参与方参与该项目，投资只授予单一实体：在此例中是 KDE e.V.。它提供行政支持、审查工作，并负责一部分工程协助。工作完成后，KDE e.V. 向 STA 开具发票，然后把钱支付给 enioka、Techpaladin 及其他承包商。

资助了什么？

Graham 说，「关于走到今天这一路的流程，说得够多了；我知道每个人感兴趣的是资助了什么。」STA 资助的最大工作包之一，是 Plasma 和 KDE Linux 的 QA（质量保证）基础设施。「你们中有些人可能在想，我又不运行 KDE Linux，谁在乎？」他说，对 KDE Linux 做 QA 的好处在于，它相当于对一切进行集成测试。KDE 的许多部分无法很好地孤立测试，因此测试 KDE Linux 也有益于其他发行版的用户。「打个比方，这个 QA 系统已经检测到并帮助修复了 KWin、KWallet、Arch Linux 打包，甚至 GCC 自身中的问题。」Graham 说，这个工作包已接近完成。

他说，人们很容易不小心弄坏自己的 Plasma 桌面，因为它「是一个极其复杂的软件」，不过他没有展开细节。为了帮助那些把自己的配置弄坏了的用户，STA 资助了一个桌面「安全模式」（safe mode）的工作，它将让把 Plasma 恢复到可用状态变得更容易，尤其是对非技术用户而言。他说，这项工作正在进行中。还有一个工作包是为 KDE Linux 提供「恢复出厂设置」功能。

这是一个面向机构的功能：比如说你要把一台设备转给同部门或不同部门的其他人，甚至要卖掉它、处理掉它。在所有这些情况下，从头重装操作系统都极其麻烦。你不想那么做。所以我们在构建一个功能，让非技术用户［重置］起来容易得多。

组织支持是 STA 资助整体的一大主题。Graham 说，有一些资金投向了「我们这类人常常不在乎的许多无聊东西」，形式是改进用于组织用途的基础设施。这意味着诸如用于身份验证的人脸识别、多因素认证、更好的磁盘锁定与加密用户体验，以及对 Secure Boot 的完整支持等功能。「这些东西很难让志愿者感到兴奋，因为这些功能相当无聊，所以外部投资对这类事情真的很有帮助。」

Graham 说，KDE 的数据备份与恢复系统也在做大量工作，此外还有用于浏览和从 Btrfs 快照恢复的用户界面。他澄清说，Btrfs 快照虽然不是备份，但当用户想快速恢复一些曾被删除的文件时，它们很有用。「所以这有点像一种分层策略：你既有设备之外的备份，又在本地磁盘上拥有文件各个版本的快照。」这项工作已经推进得相当深入——Bharadwaj Raju 在八月底撰文介绍了它的进展。

Graham 说，KDE 对通过 NFS、Samba、SFTP 等方式访问网络共享有很好的支持，但前提是「你限制自己只用 KDE 软件」。当 KDE 用户运行 LibreOffice 或 Blender 这类软件并试图通过网络共享访问文件时，体验就会变差。因此，STA 资金的一部分专门用于改善整个 Plasma 和 KDE 技术栈中的网络共享体验。

PIM 相关话题

Ottens 说，KDE PIM 的工作与 KDE Linux 的工作之间有一个很大的共同点，「我们都是从 QA 基础设施开始的」。他说，KDE PIM 各组件原本已有测试，但也需要一个好的端到端测试套件。这项工作已基本完成，现在对 IMAP、CalDAV 等都有全面的测试。他说，在持续集成（CI）方面仍有一些痛点，「但除此之外基本都完成了」。

Ottens 说，之所以需要这套 QA 基础设施，是因为他们还在做 KDE PIM 的协议支持。「所以我们需要它，以确保在添加某些东西时不会弄坏另一些东西。」例如，有在改进 KDE PIM 对 IMAP4v2 扩展的支持，并加快 IMAP 资源同步。此外还在支持 WebDAV 推送通知，这是一个草案规范。通常 WebDAV 客户端会轮询服务器以获取更新，而对推送通知的支持将允许服务器主动通知客户端发生了变化。

STA 还资助了改进以 Flatpak 格式分发 KDE PIM 应用的工作，不过这项工作尚未开始。Ottens 说，目标是改造 KDE PIM 应用，使其在 Flatpak 打包的数据源与 Plasma 用户会话之间有更好的集成。目前，Flatpak 应用是「隔绝的」，在诸如事件通知或在 KDE PIM 中搜索用户联系人等用例上，与 Plasma 的集成很差。「所以我们会针对 Plasma 本身做一些工作，看看如何以不同方式与这类应用交互，然后我们会在 Flatpak 这边从中受益。」

行动号召

Ottens 说，与 STA 的合作有许多预期成果。有些是技术层面的，比如更好的 KDE QA、更不易被弄坏的 Plasma 会话，以及更可靠、更易配置的软件。他希望这项工作的最终结果还能带来用户对 KDE 社区所产出内容的更多信任，以及商业用户对 KDE 的更多使用。

如果我们在这里做的事真的成功了，那就意味着 KDE 是一个生态，而且［意味着］ KDE 是一个你能从中赚到钱来还房贷、付账单的生态，［它］会变成一块更大的蛋糕，对吧？所以就会有更多机会，让更多人真正进入这个生态并靠它谋生。这是因为你会得到更多的部署，于是就会有更多需求。如果有更多需求，就会有更多改进请求，对吧？然后希望它能像滚雪球一样发展。

STA 项目将持续到 2027 年第三季度，之后资金就结束了。Ottens 说，KDE 社区在那之后仍需继续推进，尽管他希望到那时「最艰苦的工作」已经做完。

提问环节

第一个提问的人询问是否计划为 KDE PIM 提供即时通讯支持。Ottens 说，提案中没有关于即时通讯的计划，部分原因是服务器端的情况正处于「动荡之中」。当时不清楚 KDE 应该支持哪些即时通讯协议，他也没有信心去挑出一个赢家。

另一个人问到了用户身份验证方法；由于部分工作是为了支持企业级认证，这位听众想知道是否计划给随机的 KDE 贡献者发放智能卡，以帮助测试这些功能。Graham 说，这一点并没有专门写进 STA 提案，「但我认为那样做很有道理，尤其是因为它是相当冷僻的硬件，我们中的许多人个人并不会拥有」。

一位听众问，在 Akademy 的「常规圈子之外」，是否有任何具体计划来突出 STA 资助下正在开展的工作。Graham 说，他们正在 KDE Blogs 上撰写一个名为「This Quarter in Digital Sovereignty」的季度博客系列。该系列在 Planet KDE 上联合发布，他鼓励所有感兴趣的人帮忙推广它。「把它发到 Mastodon 上，发到 Reddit 上，发到你姑姑的智能手机上」。除此之外，并没有具体的推广计划，「但我们可能会通过手头可用的渠道来推广它」。

Ottens 补充说，参与这项工作的公司将把它加入自己的作品集，并分享给未来的客户。Graham 说，这就引出了帮助 KDE 贡献者支付账单这个话题。

我认为这一切都相当重要，尤其随着社区变老、变得更成熟，人们有经济上的需求。为人们创造机会，让他们能留在 KDE 里、靠做 KDE 的工作谋生，这真的非常重要，而这是其中的一部分。

最后一个问题是，作为 STA 工作的一部分，是否有计划为 KDE PIM 添加 JMAP 支持。Ottens 说，他愿意添加 JMAP 支持，但代价太高了，因为「我们得从零开始」。不过他说，他肯定想在某个时候探索 JMAP 支持。Graham 补充说，重要的是要记住，「当你做这样的工作时，你不能把它变成一个大杂烩，想做什么就做什么。你必须坚持提案」。

开源 / Chromium

对比 Google 与 Igalia 的 Chromium 开发

作者：Jake Edge 2026年9月30日 英文原文

Sharon Yang 是一名 Chromium 开发者，她曾在 Google 做浏览器相关的工作，如今在 Igalia 继续做这方面的工作。在 FOSSY 2026 的最后一天，她做了一场演讲，讲述自己在这两家公司的经历，比较并对照它们各自的运作方式，以及这对代码库上的工作有何影响。她喜欢在 Google 工作，对 Igalia 也是同样的感受，所以这场演讲并不是为了发牢骚——而是想让人感受一下两家相当不同的公司。

这场演讲题为「From Corporate to Co-op」（从公司到合作社），突出了巨型公司 Google 与 Igalia 这家员工所有的合作社之间的一大区别。她来自温哥华，就读于不列颠哥伦比亚大学，而 FOSSY 正是在那里举办的。学生时代，她曾在 Google 实习，做 Chrome 浏览器相关的工作，那是 Google 基于 Chromium 打造的产品。在她的幻灯片里，她展示了一张自己戴着螺旋桨帽、站在 Google 标志前的照片。

学生时代，她的生活以学期为刻度，但她在 Google 共事的一些人已经在 Chrome 上工作了四年，这在当时的她看来非常了不起。她最终在 Google 全职工作了六年，全部时间都在 Chrome 上。她的大部分工作是在浏览器的内容层（content layer），那是开源 Chromium 浏览器的一部分。因此，她在 Igalia 工作时使用着同一个代码仓库（GitHub 镜像），与许多在 Google 时相同的人共事。她简要回顾了自己在 Google 的时光：「我在 Chrome 上工作得很开心，大家人都很好，我很享受，很酷，有午餐，是段好日子」，她说得引来一片笑声。

最终，她觉得也许是时候往前走了，也许该离开她居住的西雅图地区，于是在 2024 年底开始四处寻找机会。她曾在代码库中见过 Igalia 的电子邮件地址，也在 BlinkOn 会议上结识过这家公司的一些人。Igalia 是一家开源咨询公司，受雇去做各种事情，包括 Chromium；事实上，它是 Chromium 最大的非浏览器厂商贡献者。她加入了 Igalia，并在演讲前不到一年搬回了加拿大。

对照

她从员工人数开始对比两家公司：Google 约有 18 万人，而 Igalia 约有 180 人。就收入而言，Google 去年超过 4000 亿美元，「Igalia 小得多，我们就说不到十亿美元吧」，这番话引来笑声。Google 由机构投资者所有，而 Igalia 由员工所有，这一点赢得了观众的掌声。Google 的薪酬范围很宽，从 CEO 高达 6 亿美元的薪酬方案，到她在 Google 工作时的薪水（大约在 10 万至 30 万美元之间）；而在 Igalia，从最高到最低、跨越全球，所有员工薪酬相同。

尽管它们是「天差地别的实体」，两家公司都有做着共同事项的团队；她自己做 Chromium，但两家公司也都有团队在做无障碍（accessibility）和 Web 标准方面的工作。

Chrome 和 Chromium「有点像一样，又有点像不一样」。Chrome 是 Google 的产品，带有 Google 的品牌和配色，而 Chromium 是一个任何人都可以用来构建浏览器的开源项目。Chromium 缺少数字版权管理（DRM）、「AI 集成」以及某些编解码器等专有部分；「而且它是蓝色的」。基于 Chromium 还有各种其他浏览器，包括 Microsoft Edge 和 Brave。

Google Chrome 团队的大多数成员，其大部分或全部工作都在 Chromium 仓库中进行。显然，专有部分在别处处理，但她和其他 Google Chrome 开发者很少需要与那部分代码打交道。在 Google 工作的后期，她不得不找人帮忙才能完成一个简单的任务，因为它需要访问专有部分所在的「完全不同的宇宙」。

接着她比较了为两家公司工作的体验。她说，第一周在任何新工作里几乎都一样。最初的步骤是认识同事、阅读内部文档、学习如何在内部沟通等等。Igalia 有一整套它使用的开源工具，这很不错。

不过也有一些差别。例如，有一个用于更快构建 Chromium 的系统，「否则你只会把所有时间都花在构建 Chromium 上」。Google 员工可以立即使用该系统，但外部用户必须申请访问权限。更大的摩擦点在于缺陷报告（bug report）的访问，这些报告本应对所有人开放，除非是安全缺陷。然而由于几年前的一次缺陷跟踪系统迁移，有些本应对外部可见的缺陷，如今却只有 Google 员工能看到。「这不是出于恶意」，修复访问权限也很容易，但这是她大约每周都得额外做一次的事。

还有其他信息本可以更容易地公开获取，却因为在 Google Docs 中未共享而无法公开。确保公众能够访问「是一件尽力而为的事，而人们会忘记」，这很遗憾。此外，像缺陷跟踪这样的任务所用的全部工具都由 Google 维护，且本质上是为 Google 而维护，所以外部人无法提供反馈或请求功能和改动。它们是「相对次要的摩擦点」，但足以让人感到「我现在和这个是分开的」。

在新工作干了一个月后，她开始看到它与前一份工作甚至有更多相似之处。团队成员仍然可以通过相同的沟通渠道（如 Slack）随时联系到，她也同样对他们可见。Igalia 做的有些工作直接或间接来自 Google；她正参与的一个 Chromium 项目是通过 Linux Foundation 来的，而 Google 是后者的成员。「我在同一个仓库上工作，用着同样的工具，从 Google 拿钱，到底有什么变了？」

项目

答案似乎是「既像什么都变了，又像什么都没变」。不过，在 Igalia，项目的类型是不同的。在 Google，她做的是对她管理链上的人重要的项目；那些通常是新功能，或是「他们想要改善的某个光鲜指标」。它们往往是为了让工程师及上报链中的人获得晋升。

交给 Igalia 做的项目直接来自技术人员，因此往往是「代码健康或技术债之类的项目」。例如，Igalia 曾参与把 Chromium 代码库组件化，它当前的项目是「改善浏览器之间的 web-platform-test 互操作性」。这是重要且值得做的工作，但「很难想象 Google 有谁会把它当作本职工作来做」；它「不是那种会被优先考虑或得到奖励的工作」。她在 Google 共事的许多 Chromium 人都很乐意能做这种工作。「这些人关心代码库，希望它变得更好，但他们的本职工作里根本没有余地去做，太可惜了。」

她最初被 Chrome 团队吸引，是因为团队里所有的人看起来都很热情友好。这一点在她 Google 的整个任期里一直如此，并延续到她在 Igalia 的工作中。「做 Chromium 的人在各个领域里总体上都友善而包容，这很好，而且不能视为理所当然。」她得以与前同事保持联系、审查他们的补丁、在共同的工作上留评论等等。「这比把代码审查发给某个陌生人要愉快得多。」

层级

她放了一张典型公司的组织架构图幻灯片，把她的照片放在一个叶节点里，作为唯一被填上的方框。在那样的图里，工程师处于层级的最底层；他们有一个经理，经理之上还有更资深的经理，依此类推。工程师关心的是技术决策，比如用哪种语言、如何测试正在编写的代码，而在顶层，人们决定的是公司方向和愿景之类的事。中间的人做着一部分技术工作，但常常不太清楚他们究竟在做什么；「谁知道呢？」，她的话引来笑声。「顶层的人挣的钱比底层的人多得多。」

在 Igalia，情况则很不一样。「组织架构是有意做成扁平的」，没有经理。有一些不同的团队，比如她所在的 Chromium 团队、一个 Linux 内核团队等等。扁平层级意味着「所有员工都会做大公司里叶节点员工通常不会做的大量工作」，其中包括做公司决策，比如承接哪些项目、是否增加人手、有多少假期。

Igalia 是一个合作社（cooperative），所以这类问题都要投票决定。「这些决策在大公司里你根本没有任何影响力。」这种安排的一个好处是，做决策的人正是受决策影响的人，而这「在标准公司里根本不是这样」。Yang 说，最明显的例子就是裁员。

当然，这样做事是有代价的。这类决策的会议很冗长，要开两天——而且是在欧洲时区。她说，她在 Google 时处于主导时区（美国太平洋时间），别处的队友不得不把会议安排在奇怪的时间，所以这对她来说有点像报应。但对一个「如此从根本上不同、让人感觉良好」的结构来说，这只是「很小的代价」。

她花了一阵子才完全认识到 Igalia 的结构有多么不同；它的影响并没有马上让她体会到。对她影响最大的是晋升，而在一个人人薪酬相同的扁平组织里，晋升并不存在。她还是应届毕业生时，晋升是她的关注点，因为这是对新员工的期望；「Meta 如果有谁没在一定时间内达到一定级别，是真的会把人开掉的」。

为了确保自己做的项目对路、「展现出正确的技能」以便获得晋升，这个过程压力很大，也很费心力。很多事并不在工程师掌控之中，而取决于他们的经理。她很幸运，在 Google 遇到了一位出色的经理，但即便经理很好，他们手下也有多个人要向自己汇报。「对你来说，这就像你的整个职业生涯，但对他们来说，这只是他们必须做的千千万万件事之一。」

扁平薪酬结构也是一个受欢迎的变化——不存在薪酬差异。作为一名女性，以及曾持签证工作的人，「这些是你真实会有的担忧，而现在这些统统消失了」。每个人都处在同一水平的公平竞技场上，这带来了更多信任与协作。「如果这听起来很有趣，那就去加入或创办一个合作社吧」，她说得赢得掌声。到这里她准备好的演讲就结束了，但她有充足的时间回答问题，而问题很多，这或许并不令人意外。

问答

第一个问题是：在扁平结构里，方向从何而来；她该做什么工作、这些决定是如何做出的？Yang 说，这取决于项目。有些项目与客户公司的工程师紧密配合，另一些项目则没那么需要亲力亲为。与客户工程师合作时，方向很可能像更典型的组织那样来自客户一方。有时项目更加开放，客户同意为某个具体任务出资，比如说一年，看看最后能做成什么样；在这种情况下，由 Igalia 团队决定要做哪些事。

另一位听众想知道，Igalia 的客户需要它在 Chromium 上做什么。她说，同样是因客户而异。她的项目是清理测试，这是 Google 想要的，却在它的团队里无处安放。其他客户想要供内部使用的定制浏览器，所以 Igalia 的 Chromium 团队有一部分人也在做下游项目。

接下来是招聘流程。一位听众想知道 Igalia 如何决定某个职位需要招聘，以及如何选定要招的人。「哪些团队获得员额是在公司层面决定的」，她说，所以如果 Chromium 团队想招人，它会向「议事会」（assembly，即投票主体）做陈述。如果获得批准，团队就会面试候选人，并选出它认为应被录用的人，这又要回到议事会。通常情况下这个选择会被批准，除非公司其他某个地方的人知道有某种危险信号。Yang 提醒听众，她在 Igalia 还相当新，不过演讲现场还坐着其他员工，可能会补充澄清；在这个问题上，她只是得到了他们的一个大拇指肯定，她说。

一位听众指出，扁平结构下已有 180 名员工，听起来已经有点难以驾驭了，是否存在某个规模，Igalia 仅仅因为体量就不得不转向层级结构？Yang 说她在面试时也问过同样的问题，「大家都同意这确实是个问题，但还没有明确的解决方案」。她的伴侣建议，蜜蜂或许能提供一个合理的拆分模型；当蜂巢变得太大时，一部分蜂群会离开，去建立一个新的蜂巢。

来自另一家员工所有制合作社的一位员工提出，开源和合作社之间存在协同效应，这在需要拆分时也许会有帮助。他想知道 Igalia 是否有计划把其内部工具和合作社运营文档作为开源发布，这样如果有需要，就能促成一家新的独立公司。Yang 提到，她的同事 Danielle Mayabb 在紧接着的下一个时段有一场关于用 FOSS 工具经营公司的演讲。

一位研究扁平结构公司的研究者问，是否存在某些组织结构在各自的团队内部又回到了画面中。Yang 说，团队负责决定是否承接某个项目这类事情，而且有产品经理在各团队之间协调。产品经理与客户紧密协作，但他们并没有像典型工作中的经理那样的固有额外权力。

她在演讲过程中提到自己还不是议事会成员，于是有听众问这是如何运作的、需要多长时间、是否需要投票等等。Yang 推荐了 Valerie Young 在 2023 年首届 FOSSY 上演讲的视频，其中讲得更详细。Yang 说，大约在满一年的节点上，会决定一名员工是否加入议事会，不过她没有具体说明究竟怎么做。「如果你干得特别糟糕，你就不会被允许加入。」

这很好地引出了下一个问题：什么能阻止合作社里的员工干脆不干活了？在扁平层级里，谁来监督员工在做什么？有人能不被发现地停止工作吗？她开玩笑说她会试一试，明年再回来做一场关于这个的演讲。更认真地讲，确实有人在为同事的绩效提供反馈；每个人在公司里都有一位导师（mentor），承担着其他公司中经理的部分角色，包括收集对正在完成的工作的评估。「有人在监督你的绩效，而这是所有与你共事的人共同参与的集合。」

一位听众指出，合作社运动中有句老话：「你见过一个合作社，就只是见过一个合作社。」正因如此，合作社之间分享各自的内部结构才会有很大帮助；就像开源软件一样，其他合作社可以借鉴创办这家合作社时经历过的试错。Yang 提到，FOSSY 过去曾有一个合作社专区，而且有消息说明年可能会恢复。

针对 Linux 文件通知机制的攻击研究

来自 格拉茨工业大学（Graz University of Technology）一个研究小组的成员 Sudheendra Raghav Neela 宣布，公开了针对文件通知（file-notification）攻击的研究。这类攻击可被用来窥探 Android、Linux、macOS 与 Windows 上的用户活动。该团队发表了相关论文，并上线了展示这些漏洞的网站。

在 Linux 上，攻击者可以借助 inotifywatch 监视某个目录，即便没有该目录内文件的读权限，也能实施按键间隔时序攻击（inter-keystroke timing attack）。该团队还发现在 KDE 5 与 KDE 6 上实施 UI-redress 攻击（即"点击劫持"攻击）的方法：通过监视 /usr/bin/pkexec 来探测 Polkit 何时弹出认证提示，攻击者便可在真实窗口之上绘制伪造的密码窗口，从而收集用户凭据。

这两个缺陷至今仍然存在，不过 Linux 内核已通过一个修复做了部分缓解；该修复包含在今年 1 月发布的 5.10.248、5.15.198、6.1.160、6.6.120、6.12.65 与 6.18.3 内核中。更多信息以及防止密码提示窗口失去焦点的缓解措施，请见该项目网站。
