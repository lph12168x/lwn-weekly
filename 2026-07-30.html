为内核引入 Hazard Pointers（危险指针）

作者：Jonathan Corbet 发布日期：2026年7月27日 英文原文

内核的读-复制-更新（RCU）子系统确保：在已知没有任何线程仍持有对某一对象的引用之前，该对象不会被删除。RCU 工作良好，并被广泛用于整个内核，但它会增加内存占用，并且在未使用的内核对象被清理之前引入显著的延迟。Hazard pointers（危险指针）是无锁数据更新的一种替代方案，至少在某些场景下能提供更好的性能。内核社区目前正在考虑由 Mathieu Desnoyers 与 Paul McKenney 提出的一个 hazard-pointer 实现。

与 RCU 类似，hazard pointers 旨在成为一种对不可变对象持有短生命周期引用的方式，该对象在所有引用消失后可能被释放。持有 RCU 保护数据引用的代码必须禁用抢占（disable preemption）；而 hazard pointers 看起来被设计为允许抢占，尽管这种用法可能并非完全最优。

hazard-pointer API

在 API 层面，使用 hazard pointers 的代码必须为每个同时使用的指针分配一个上下文（struct hazptr_ctx）；该结构通常放置在栈上。如果有一个指向受 hazard pointer 保护对象的指针（我们称之为 resource），且代码需要访问该对象，则必须首先通过调用以下函数获取该指针：

void *hazptr_acquire(struct hazptr_ctx *ctx, void * const *address);

其中 ctx 为上述描述的上下文，address 在此例中为 resource 的地址。该调用将返回 resource 的当前值（受保护对象的地址），并确保在引用保持期间该对象不会被修改或删除。当对受保护对象的工作完成后，代码必须调用：

void hazptr_release(struct hazptr_ctx *ctx, void *address);

其中 address 为 resource 旧副本的地址；此调用后，之前受保护的对象不再可用。

通常，hazard pointer 必须在获取它的同一执行上下文中释放——即同一线程或中断处理程序中。但有时可能需要在不同环境中释放该指针。这可以做到，但仅当 hazard-pointer 上下文被传递给此函数时：

void hazptr_detach(struct hazptr_ctx *ctx);

该调用显然必须在指针实际释放之前进行。

在生产者侧，当需要用新对象替换受保护对象时，代码应创建并初始化新对象，将 resource 指针指向该新副本，然后调用：

void hazptr_synchronize(void *address);

该调用必须在可抢占上下文（preemptible context）中进行，它将等待直到给定 address 不再有任何 hazard-pointer 引用，然后返回调用者。此时该地址处的对象可被释放。

实现

hazard pointers 背后的核心思想相对简单：hazptr_acquire() 调用将指针添加到一个特殊列表，而 hazptr_release() 将其从该列表移除。当进行 hazptr_synchronize() 调用时，扫描该列表查找相关地址；若找到该地址，函数将等待直到它被移除。该算法本可用一个由锁保护的简单链表实现，但此举目的在于最大化性能，因此实际实现更为复杂。

hazard-pointer 代码维护一个全局每 CPU 数组，每个 CPU 上有四个槽位（slots）。过于简化的算法解释是：在 hazptr_acquire() 调用时，找到一个空槽，并将相关地址存入其中。hazptr_synchronize() 调用随后可简单扫描这些槽（在每个 CPU 上）并等待直到其中无一包含受保护地址。但同样，这里存在复杂性。

其中一个是顺序问题（ordering problem）。hazptr_acquire() 必须先读取要获取的指针，然后将其存入槽中。在同步侧，必须先更改该指针，然后搜索槽中先前的值。如果同步代码在两个 acquire 操作之间运行——即指针被读取后、但存入槽之前——它将断定无引用并释放仍在使用中的对象。这不是这段代码作者愿意面对的某种 hazard。

为解决此问题，槽被维护为三种不同状态。若槽中存储的地址为 NULL，则该槽空闲且未保护任何指针。若包含非 NULL 指针值，则该槽被占用并保护该指针。但存在第三种值 HAZPTR_WILDCARD（其值为 0x1UL）用于表示槽正在被分配过程中。hazptr_acquire() 首先找到一个空闲槽并将其值设为 HAZPTR_WILDCARD；只有在这之后它才读取地址值，并随后存入槽中。hazptr_synchronize() 将任何包含 HAZPTR_WILDCARD 的槽视为包含其正在查找的指针，因此它将等待直到真实指针值出现在该槽中才返回。这一额外检查防止了上述竞争条件（race）。

另一个复杂性是：如果需要超过四个槽怎么办？任何给定函数可能不需要这么多槽，但无法知晓更深调用链中的函数会使用多少。hazard-pointer API 本可在此时返回错误，但这似乎是制造难以发现的 bug 的可靠方式。相反，处理此情况正是 hazptr_ctx 结构的目的。

该结构包含一个备用槽（spare slot），若每 CPU 槽均不可用时可用其持有 hazard pointer。此时，代码使用上下文结构中的槽，然后将该结构链接到一个每 CPU 列表。当发生 hazptr_synchronize() 调用时，它必须搜索那些每 CPU 列表以及每 CPU 槽，以确保地址未受保护。作为额外转折，实际存在两个每 CPU 链表；一个可用于添加，另一个可用于搜索，再次防止竞争条件。列表遍历有拖慢一切的风险，但这些列表几乎总为空。

溢出槽（overflow slot）除了扩展四个每 CPU 槽外还有若干用途。上述 hazptr_detach() 调用会立即将给定指针移至溢出槽（若尚未在其中），从而释放每 CPU 槽供其他使用。调度器（scheduler）中还添加了一个特殊回调，在上下文切换（context switches）时调用；该回调将所有每 CPU 槽移至其对应溢出槽。这样，若线程在使用 hazard-pointer 槽时被抢占，它将释放更快的每 CPU 槽给随后运行者。

这段代码仍处于相对早期状态，在进入主线前可能还会演变。重要的是，该补丁系列未包含任何 API 使用者，而这通常是对此类新子系统的要求。这些使用者的创建很可能揭示 API 缺陷，以便在合并上游前解决。因此很难猜测（hazard a guess）hazard pointers 何时可供内核开发者使用。

Debian 新 DFSG 团队工作纪实

作者：Joe Brockmeier 发布日期：2026年7月28日 英文原文

DFSG、许可与新包团队（通常简称为 "DFSG team"）创建于 2025 年 10 月，作为 ftpmaster 团队拆分的一部分。其工作是在包进入 Debian archive 前，审查 new queue 中的包是否符合 Debian 自由软件准则（DFSG）等要求。这一变更酝酿已久，拆分后仍存在些许疑问：这是否是正确举措。Andrew McMillan 在 DebConf26 期间概览了该团队的活动与当前状态。虽下结论为时尚早，但他的报告表明新的职责划分运作良好。

我未参加 DebConf26，但观看了 McMillan 演讲的录像，提供 WebM 格式（HD quality、low-resolution video）。演示幻灯片尚未提供。

Ftpmaster 的拆分

二十多年来，Debian 的 ftpmaster 团队负责允许新包进入 Debian、移除旧包，以及维护 Debian 的 archive。有时，包在 new queue 中滞留时间长于 Debian 开发者预期，该团队被一些人视为需要关注的瓶颈。

重构团队的想法在 DebConf24 的 "meet the ftpteam" BoF 中被提出。2025 年 10 月 3 日，Debian 项目领导人（DPL）Andreas Tille 宣布计划将 ftpmaster 团队拆分为两部分：Archive Operations Team（负责支持 Debian archives 的基础设施）和 DFSG team。Tille 于 2025 年 10 月 26 日启动变更；他创建新团队的代表团并撤销 ftpmaster 团队的代表团，从而解散之。

DFSG team 的 首个代表团完全由前 ftpmaster 成员组成：Thorsten Alteholz、Ansgar Burchardt、Joerg Jaspert 和 Luke Faraone，他们也均 被任命至新 Archive team。2026 年 1 月 19 日，Tille 任命新代表团给 DFSG team：McMillan、Emmanuel Arias、Nicolas Mora、Mechtilde Stehmann 和 Reinhard Tartler。

团队介绍

McMillan 表示演讲本应由 Arias 和 Tartler 共同进行；但 Tartler 需飞回纽约，Arias 在场但未演讲，因他 "出了名地害羞"，不过他乐意用西班牙语答疑。"In English, I'll do the talking, I guess." Mora 和 Stehmann 原计划远程加入，但演讲房间的网络问题使之不可能。

他承认团队名称冗长，但 "DFSG team" 易读却也遗漏了部分职责。他指出团队除确保打包软件符合 Debian 自由软件准则外，还审查包是否符合打包标准等。

DFSG team 不替代 ftpmaster team，他说："We just do a very specific task, which was largely done by Thorsten Alteholz in the past." Alteholz 做得很好，"but it was more than one person can handle"。DFSG team 更多并行工作，尽量避免被任何特定包阻塞。"And if somebody's not available, then we can work around that." McMillan 也谈了团队不做的事：不完全替代 ftpmaster。进入 Debian stable 发布、security 与 backports 仓库及其他 archives 的包处理由 Archive team 负责。

他展示幻灯片文字："Thesis: a package isn't free until someone checks"。McMillan 说 DFSG team 必须在包进入 archive 前检查是否为自由软件；也审查前往 contrib 和 non-free 仓库的包。"We review those as well with less-stringent requirements, as is appropriate for non-free."

经 DFSG team 之手的有两类包：从未或当前不在 Debian 中的全新 source 包；以及 "binary new" 包（他解释因版本递增等改名）"We tend to review the binary new packages much more leniently, but we still find packages that have been around in Debian for 15 years that have issues with their licensing"。

此类情况，团队常带备注接受包，请打包者修改。"We would rather accept a package which has some minor changes needed, and we'll just ask you to make the minor changes after it's entered the archive." 这省去大量往返（round-tripping）。

McMillan 详述审查内容：debian/copyright 中许可与源码头不同、捆绑非自由资源等。有时 "people put something into the Debian copyright [file] that seems to be a license, but it actually is just verbiage about the license that's put on a web page or something"。团队须请打包者将实际许可放入 debian/copyright。

多数包使用 copyright format 1.0 规范（机器可解释格式）。该格式即 DEP-5，2007 年作为 Debian Enhancement Proposal (DEP) 提出。McMillan 希望观众熟悉 DEP-5；观众示意熟悉后他说 "good, we want to make it mandatory for new packages to be DEP-5"。

他说 DEP-5 要求可能在年底前引入。"We might actually make it actually apply retroactively that it is a bug for a package not to have the copyright in DEP-5 format." 这有助于管理大量计算机者了解许可。"Software bill of materials people, and that sort of thing." 目前不合 DEP-5 的包数未知。

仪表盘

开发者可通过 DFSG team 的 Dashboard 跟踪包进度。McMillan 说 dashboard 是队列的简单 web 展示，底层极复杂。

Archive team 使用 Debian Archive Kit (dak) 脚本管理 archive。DFSG team 讨论也用 dak，但决定用独立软件与界面。"So we interact with dak, our software interacts with dak, but we don't have to learn how dak works. That can be somebody else's problem."

他说团队用专注其流程的软件。展示 dnq 用例：如 dnq list 显示待审包，dnq fetch 获取包，dnq assign packagename 分配审阅者等。dnq complete accept 最终化审阅并交 dak 发邮件。"Or, now and again, somebody might get a reject [email]. Hopefully nobody in this room."

他说团队仍互相学习："We kind of all have slightly different workflows because we're a new team and we're evolving." 成员技能不同：Stehmann 有法律背景，善读许可。

优先级与成果

成员自选审阅包，McMillan 说："The ones that come to the top of my list tend to be languages that I'm more familiar with, like Go. And the ones that go to the bottom of my list tend to be languages that I'm less familiar with, like Python." 反之 Arias 熟 Python。棘手包（如 1990 年代大包）指定团队审。

他说新团队接手时队列超 750 包；现通常少于 30。团队优先最旧包，"but also with a balance to get important packages"。新 binary 包优先于新 source 包。高 popularity contest (popcon) 分也优先。

团队通常 2–3 天处理完，"if it takes more than a week for your package to get through, you've hopefully had some communication with the reviewer in that process"。鼓励打包者邮件联系。

虽更快，McMillan 说团队需更多人，邀请有意者加入。他期望系统将更多负载给普通 Debian 开发者："some kind of quorum sort of structure" 允许有上传权者背书，够票即接受。

他说去年 DebConf 大量讨论 "about the difficulty with getting [new] packages accepted into Debian, and I think this year we're not talking about that"。他开放提问，观众无问题，提早结束。

内核 / 内存管理

为交换设备引入操作结构体

作者：Jonathan Corbet 发布日期：2026年7月23日 英文原文

在 2026 Linux 存储、文件系统、内存管理与 BPF 峰会（LSFMM+BPF）上提出的一个想法是为 swap 子系统创建 一个操作结构体。像内核许多部分一样，swap 层随时间演变，所需即加；最终结果罕如今日设计。swap 层与其使用设备间的接口即一例。swap 子系统演变的一个结果——缺乏对接底层存储的抽象层——似乎将很快被解决，但以不同于最初设想的方式。

早期，内核只能 swap 到本地磁盘专用分区。若分区太小（最终总是如此），通常需重分区整盘。后来能使用文件系统中文件作 swap 减轻了管理员负担；再后内核获得 swap 到网络文件系统能力。在 swap 层内，这些后端各编码为特殊案例。缺乏抽象使子系统难维护改进。

Baoquan He 创建的 补丁系列已酝酿有时。swap 层与后端接口由下结构定义：

struct swap_ops {
    void (*read_folio)(struct swap_info_struct *sis, struct folio *folio,
                       struct swap_iocb **plug);
    void (*write_folio)(struct swap_info_struct *sis, struct folio *folio,
                        struct swap_iocb **plug);
    void (*unplug)(struct swap_iocb *sio);
};

read_folio() 和 write_folio() 目的明显：在内存与底层 swap 设备间移动页。unplug() 用于启动一批累积 I/O 操作。这组操作向 swap 子系统其余部分隐藏后端差异。

He 系列定义了三种 swap_ops 结构：

  • bdev_async_swap_ops：常规 swap 到块设备。操作异步。注意 swap 到本地文件系统文件也通常由这些操作处理。加 swap 文件时，内核请文件系统指定块位置，然后绕过文件系统做 I/O。
  • bdev_sync_swap_ops：本地块设备但同步；函数至操作完成才返回。即 "swap bypass" 案例（见 此文）；对快速内存设备，操作即内存拷贝，无异步必要。
  • bdev_fs_swap_ops：调用文件系统做实际 I/O。非本地文件系统，为网络文件系统 swap 所需。

该系列经七版，似将合并。但 LSFMM+BPF 后 Christoph Hellwig 提出 不同方案，聚焦增加 swap-I/O 批处理性能。其添加受 He 启发但不同的操作结构：

struct swap_ops {
    unsigned int flags;
    bool (*can_merge)(struct folio *folio, struct folio *prev_folio,
            size_t prev_folio_size, int rw);
    void (*submit_write)(struct swap_io_ctx *ctx);
    void (*submit_read)(struct swap_io_ctx *ctx);
};

can_merge() 判定两 folio 的 I/O 能否合并为更大操作。须判定存储是否逻辑相邻，故不同后端计算不同。submit_write() 和 submit_read() 发起 I/O，细节聚于 ctx。仅一 flags 值 SWAP_OPS_F_REQUIRE_NOFS，指示回收操作不得调用文件系统，以免递归调用。

Hellwig 补丁仅定义两种结构：swap_bdev_ops（块设备）和 swap_fs_ops（文件系统后端）。同步 bypass 由块设备实现中测试处理。

该系列第五版，似就绪，但可能赶不上 7.3 合并窗口。问题：Sashiko 审查工具对补丁本身少抱怨，但 发现补丁修改的代码中若干已有问题。自然欲修，但延迟新工作不总受欢迎。此事未定。

内核 / BPF · 网络

netkit 进展与 BPF 在用户空间的应用

作者：Daroc Alden 发布日期：2026年7月24日（LSFMM+BPF 峰会） 英文原文

Daniel Borkmann 在 2026 Linux 文件系统、内存管理与 BPF 峰会上领导了关于 netkit 进展的会议；netkit 允许运行于 Linux 的虚拟机（VMs）高效联网。时间有余时，他讨论了用 BPF live-patch（热补丁）用户空间应用的想法。netkit 正进展，已支持零拷贝收包至网络命名空间内 VM，但用 BPF 补丁用户程序仍纯属推测。

长期有 VM 加速网络或访物理设备之法，但不兼容网络命名空间。该组合为 KubeVirt 所需（Kubernetes 用 VM 隔离、网络命名空间设策略）。最终 Borkmann 欲使 VM 做真零拷贝网络。关键步是最近 合并的 queue leasing 支持。

Queue leasing 允许 VMM 在 VM 虚拟网络设备建队列，绑到主机设备真实队列，实现零拷贝。目前仅收队列工作：包到物理 NIC 时驱动直放 VM 队列内存，VM 直接访。

收队列 leasing 健壮；已与 huge pages 或 BIG TCP 等优化共作（若 NIC 支持）。需自测确保。发队列侧更复杂。

发队列 leasing 底层设计近似：VM 直放包至物理 NIC 可访内存。John Fastabend 问发侧是否需 BPF 程序强制策略。Borkmann 答 netkit 即便无 queue leasing 也装此类 BPF。非所有物理设备支持直访内存。Bobby Eshleman 补丁（5 月 18 合并）扩展 device memory transmit 属性示物理设备支持否；netkit 只需传该属性。

直传数据不避网络命名空间策略，因包头仍走正常流程含 BPF 过滤。仅数据部分直给。发队列 leasing 可用后适多数场景。

一观众问何组件设收队列 leasing，何防 VM 耗尽主机队列。Borkmann 说其用例由 Cilium 设。对应总由 VMM 软件设；VM 不能自决。同一人问为何每 VM 需独立发队列；收侧因需导向不同 VM，发侧不必。Borkmann 说或可用共享发队列，但曾见 XDP 分配队列映射致物理 NIC 状态 bug。分离防干扰。该人提建议 Borkmann 允查。

用 BPF 对用户空间热补丁

Borkmann 另一话题是用 BPF live-patch 用户程序。想法来自 Fastabend 早先演讲：用户程序难及时补安全漏洞。若内核生 trampolines 或 JIT 代码直跑用户空间？可做参数验证或返回值改。也可优化 uprobes 性能。

当然可直接改用户程序 text 页补丁，但错补易毁程序。BPF 可能因同内核原因有用：BPF 程序可验证不崩。诸多关键用户程序欢迎不崩 live-patching。

Borkmann 设想：内核验 BPF 程序、编为位置无关代码、注入运行用户程序可执行内存。用户进程直跑。复杂处：BPF 程序无内核专用接口（如多数 BPF maps），但简单补丁用 BPF arenas 足够。

Song Liu 认为许多重要属性无法验证，用户空间 BPF 仍可能崩。Borkmann 认为类 Fastabend "shields" 小程无碍。Liu 说内核 verifier 有明确允许集，用户空间无，故 verifier 是否够用不明。

Jakub Sitnicki 问 BPF 补丁较 uprobes 何优。Borkmann 说 BPF 直跑用户空间免陷内核开销。Andrii Nakryiko 认同 uprobes 性能有限。Liu 建议部分 uprobe 功能移用户空间无需 BPF。

Nakryiko 指如何挂钩生成代码入用户可执行：uprobes 用断点指令内核模拟；补长跳至 BPF trampoline 更复杂："this rewriting of generic instructions is very hard"。我问包含特殊目标位易补否，Nakryiko 说 uprobes 益在可跑任意函数。

将尽时另一观众请抽 verifier 为独立库。其类型系统检查跨上下文有益。

总体开发者觉 BPF 用户补丁因故难，但无不反对。是否值当未定。

为内联函数补充调试信息

作者：Daroc Alden 发布日期：2026年7月29日（LSFMM+BPF 峰会） 英文原文

BPF 程序用 BPF type format（BTF）调试信息确定如何与内核函数交互。追踪内核函数涉及在 BTF 节找地址——但对内联（inlined）函数无效，因其无单地址。Alan Maguire 想在 BTF 加内联函数信息以允追踪，在 2026 Linux 存储、文件系统、内存管理与 BPF 峰会上领导此会议。

内核超 100,000 内联函数，散于五倍位置。部分半内联（部分正常调、部分内联），致今似追踪成功但漏调用。

好消息：追踪内联基础设施已备 kprobes。仅须将内联位置数据入可用格式。"The story is actually pretty complete."

BTF 存何？DWARF 有内联指示但难用。BTF 方案应紧凑、可去重（deduplication）。理想存独立节或模块。

具体 Maguire 提三新信息：一为 inline-site 特定信息（何函数内联于何调用点、若未内联如何调）称 "location section"。难去重，故尽量指可去重数据。二、三为所指数据："location prototype" 与 "location parameter"。location prototype 指定参数如何表为 location parameters 列表，各存单参访问法。编译器理论每内联点（538,090）异位，实有限变换，现去重后仅 57,141 条 location prototype 引 17,535 条 location parameter。

故 location sections 占多数。总增 BTF 约 11MB，每内联点 21 字节。分离压缩后 3.5MB。

Maguire 举例：

int foo(int a, void *b, bool c);

若内联消 a、升 b 入寄存器、c 为常数，BTF 表现为单 location section 条：存 foo() BTF type ID、调用点偏移、指 location-prototype。后者为长度标记数组引 location-parameter：首空（a 不可复）、次指寄存器标志与号、末常标志与值。

Alexei Starovoitov 问 location-section 条目序。Maguire 原想按地址排，后改按函数名排便二分搜。

两前置问题：location-section 条数需长度字段扩至 24 位；现工具有不识新 tag 问题。Maguire 将 BTF 解析信息加进 BTF 自身，工具可跳未知 tag。

他更新 poke-a-hole (pahole) 排序新 tag。Andrii Nakryiko 问树外模块；需 resilient module BTF 重定位，设计允但繁。

写时 Maguire 补丁未合。值否未定。

发行版 / Fedora

Fedora 批准一款更精简的 GRUB

作者：Joe Brockmeier 发布日期：2026年7月29日 英文原文

Leo Sandoval 和 Marta Lewandowska 为 Fedora 45（预计 10 月）提 change proposal：提供单独精简 GRUB 版用于小众场景。新包附加于主 GRUB 包不替代之。有贡献者抵制建议用 systemd-boot。但 Fedora Engineering Steering Council（FESCo）投票接受于 7 月 7 日。

已签名、已封印、已启动

提案指定建 UEFI-only GRUB 含最小模块启 unified kernel images（UKIs）用 boot loader specification（BLS）文件。目标为虚环境（如公有云 VM）启 sealed bootable container 做 confidential computing。

LWN 曾 覆盖 bootable containers（bootc），sealed bootc 较新。sealed image 含全验证链：固件、UKI、composefs 启 fs-verity 非 OSTree。仅 x86_64/aarch64 UEFI 支持。

主用户为 Fedora CoreOS。因 CoreOS 最小自动更新，精简 GRUB 减攻击面。提案想 "a minimal UEFI bootloader for virtual environments"。

有趣 Lewandowska 曾论替 GRUB 现拥之。她 2024 DevConf.cz 讲 nmbl（"no more bootloader"）用内核自启。其 博文概览。她指 Red Hat 背 "hundreds of downstream patches" 及 GRUB 复杂、多漏洞。

讨论中 Lewandowska 解释改观："This year GRUB upstream moved to GitLab, has much better [continuous integration], become more accessible and much more lively." nmbl 停滞；仓库 2025 年 8 月更。提案未提 nmbl。

为何不用 systemd-boot？

原 sealed bootc 想用 systemd-boot。提案说考虑后因：systemd-boot "has not been widely tested or fuzzed, like GRUB has been" 及维护多 bootloader 增债。早期版称 systemd 团队视新特性为 no-go。

论坛 Zbigniew Jędrzejewski-Szmek 说反 systemd-boot 论 "divorced from reality"。其 "fairly widely used"、经 OSS-Fuzz fuzz、常加新特性。

邮件 Lennart Poettering 评"really irritated" 评不加法特性："We are adding new stuff to systemd-boot/systemd-stub all the time, including stuff contributed by Red Hat's [confidential computing] folks"。Lewandowska 说提案赞助者被 "RHEL/Fedora systemd maintainers" 告知不加法特性。该点后由 Kashyap Chamarthy 移除。

Michael Gruber 说不反对但弃 systemd-boot 念遗憾。Alberto Ruiz 亦想拒 systemd-boot 理由错："the burden of maintaining a GRUB variant is likely higher than the burden of supporting systemd-boot in an additional use case that is very limited in scope"。

Lewandowska 说若 GRUB 不广用 "I would agree adopting it for this use case does not make sense"。但投资多故用 GRUB。

提案提 测试包。Gerd Hoffman 观测试包 "does not look very stripped down to me"，比标准 4MB 仅小 64KB。Sandoval 认需工链 ticket。

Neal Gompa 说普赞成但欲 Btrfs/ext4/XFS。Timothée Ravier 答加文件系统悖目标。Gompa 亦说上游探 GRUB 安全特；"With the revived upstream and our patches getting merged at a rapid clip now, I'm very optimistic about the future of the GRUB project." Poettering 不热扩文件系统："It's hard enough for the Linux storage people to maintain that as part of the Linux kernel, and now you expect the handful of Grub maintainers to keep up with this in their own codebase?"

Oron Peled 建议类 nmbl 用中间内核启另一内核。Jędrzejewski-Szmek 指曾论有弊如内核 CVE 流更。

通过

FESCo Simon de Vlieger 说难投；虚环境无值但或他景有用。"This stripped down version is at odds though with what I've seen people expect this to turn into (having filesystem drivers, that sort of stuff)." 弱 +1。Ravier 说戴多帽，CoreOS/RHEL 用，但 FESCo 视角 "I don't think this change brings a lot of value to Fedora and we should focus on using systemd-boot instead"。终 +1 因附加不阻未来。

终无热情但无反对，五赞成零反对。新包应现 Fedora 45。

内核 / Rust · 工具链

用 gccrs 编译 Linux 内核的进展

作者：Arshal Aromal（贡献） 发布日期：2026年7月28日 英文原文

gccrs 项目为 GCC 创建 Rust 前端，2026 上半年聚焦编译 Linux 内核。借测内核 crates，团队近正确码。据 周报与 月报，揭解属性处理（二月报）、名解析、资源管理（五月报）问题。现仅处独立程序，数月可变。

驱因：内核引入 Rust 需新工具链。现须 LLVM rustc（实验 rust_codegen_gcc）。GCC 版支持非 LLVM 架构及插件生态。

重组里程碑

三月报改三能力里程碑：一 "embedded Rust compiler" 编 no_std 依赖 core；二 "Rust for Linux compiler" 支持 alloc 及内核 crates；三 "general purpose compiler"。

一近完。三月加 compiler_builtins、修 ffi crate。Zhi Heng 五月 Open Source Security 实习修 bug 建 CI。

但需正确码。Drop 语义关键。

Drop 基础设施

Rust 用 RAII。值出域编译器插 Drop 调。变量初始化态随控制流变，需动态 drop flags。gccrs 缺 Drop elaboration。内核中漏 Drop 致锁不释等。GSoC Janet Chien 五月建 Drop 基础设施。

名解析工作

测标准库揭名解析 bug。Rust 有三四命名空间：value/macro/type/lifetime。原 gccrs 在目标类型命名空间解路径错，因模块在 type 命名空间。五月改数据结构访客，深嵌套 core 导入解。

元数据与属性处理

二月 Pierre-Emmanuel Patry 重做属性管线，分 cfg 两遍。三月加 -frust-crate-attr 等 -Zcrate-attr 注 #![no_core]。链内核 crates 揭元数据漏嵌套模块，改元数据系统。

当前能力与上游化的挑战

今成 no_core 独立程、近 core crate。全编内核抽象进行中。上游合补丁难，但两 dev 升 GCC maintainers 可暂存树推。

下一步

GSoC Enes Çevik 五月实 alloc。内核转自 alloc 模块，故标准 alloc 非严需。Patry 与 Arthur Cohen 将 RustConf 与 EuroRust 讲。

更正：关于 alloc 与 compiler_builtins 状态已更正。
